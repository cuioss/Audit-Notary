= Use Cases: Access (UC-ACC)
:toc: left
:toclevels: 2
:nofooter:

xref:../UseCases.adoc[Use Cases] » Access

A person gets into the application with the organisation's login and out of it again, confirms a release with a fresh
multi-factor login, keeps the own entry of the person directory current, and loses access as soon as the organisation
withdraws it. Nobody needs an account on the Git server: the identity of a change comes from the login and is signed
into the commit (xref:../concepts/authentication-and-identity.adoc[Authentication and Identity]).

[#principles]
== Principles

[#no-token-in-browser]
The browser holds no token:: The server is the confidential client of the identity provider; the browser holds only
cookies, and the server decides every right (xref:../specification/authentication.adoc#AUN-AUTH-1[AUN-AUTH-1]).
[#rights-from-groups]
Rights come from groups only:: What a user may do on a repository comes from the groups of the identity provider,
mapped in the configuration; never from a directory role (xref:../specification/authentication.adoc#AUN-AUTH-2[AUN-AUTH-2]).
[#session-layer]
The session is Token Sheriff's:: The login, the session, its end and the step-up run on Token Sheriff's session layer;
Audit Notary supplies what is its own through the layer's hooks: the canonical return addresses, the mapping of groups
to rights, and the first login with the directory entry (<<change-session>>). The layer is proposed, not built
(`TokenSheriff/doc/client_addendum.md`); the use cases describe the behaviour, whichever code carries it.

[#UC-ACC-1]
== UC-ACC-1: Log In and Come Back to Where I Was

Status:: `DRAFT`
Actor:: any user, in the web app.
Goal:: log in with the organisation's identity provider and land on the address I opened, with the rights my groups
give me.
Trigger:: the user opens an address of the web app without a session, or the session ended
(xref:#UC-ACC-6[UC-ACC-6]).
Preconditions:: the identity provider is configured (`oidc` in `audit-notary.yaml`); the user has an account there.
Flow::
+
[source,text]
----
  [S] session.missing          a request of the web app is answered
       │                       UNAUTHENTICATED with the login address
       ▼
  [S] login.start              the current canonical address is kept as
       │                       the return address; a login transaction
       │                       is opened (state, nonce, PKCE verifier)
       ├── provider metadata unreadable ─► IDENTITY_PROVIDER_UNAVAILABLE
       ├── too many pending logins ──────► TOO_MANY_LOGINS, retry later
       ▼
  [P] login.authenticate       the user authenticates at the provider
       ▼
  [S] login.callback           code exchanged, issuer, state and nonce
       │                       checked; a session this browser still
       │                       holds is ended; the new session is
       │                       created and the rights are mapped from
       │                       the groups
       ├── transaction unknown ────────► done, a new login offered
       ├── no directory entry yet ──► ↳ UC-ACC-4, then back here
       ├── entry due for confirmation ─► ↳ UC-ACC-5, then back here
       ▼
  [S] login.return             the return address, if it is a canonical
       ▼                       address of the app; otherwise the Due lens
  done
----
Variations::
* *A foreign return address* is replaced by the *Due* lens; the login never sends the user to another origin.
* *A user with no mapped right* is logged in, and every request on a repository is refused as `FORBIDDEN`; the app
  says so. The shell's own requests and, with the default person directory, the first login of
  xref:#UC-ACC-4[UC-ACC-4] still work: they act on no repository, and the first-login allow-list admits them.
* *Many logins from one source*: each source (a client address) holds a bounded share of the pending logins; a source
  that starts more drops its own oldest pending login, whose callback then finds no transaction and offers a new
  login. Only when every place is taken is a start answered `TOO_MANY_LOGINS`, and the logins already started are kept
  (<<change-session>>).
* *A second login in the same browser* ends the session the browser still holds before the new one is created; the
  earlier session does not live on beside it.
* *Too many sessions of one user*: one user holds a bounded number of sessions, one per browser; a login beyond the
  bound ends the user's oldest session, whose browser learns it with its next request
  (xref:#UC-ACC-6[UC-ACC-6]).
* *Changed groups* take effect when the session's tokens are refreshed, without a new login, where the refreshed
  tokens carry the groups (<<change-provider-end>>); otherwise at the next login.
* *Who builds what*: the login, the callback, the session and its limits come from Token Sheriff's session layer;
  Audit Notary adds the canonical return addresses, the mapping of groups to rights, the first-login gate and the
  session request of the shell. Until the layer exists, the bootstrap's own login carries this flow, without the
  shares per source and the bounds per user.
Outcome:: the user has a session, held by the server, with the rights of their groups, and sees the address they
opened.
Open points:: which claims (`sub`, `acr`, `amr`, `auth_time`) and groups reach the application, whether groups arrive
by token claim or by SCIM, and whether refreshed tokens carry them
(xref:../concepts/authentication-and-identity.adoc#_open_questions[Authentication and Identity, Open Questions]).
Requirements:: xref:../specification/authentication.adoc#AUN-AUTH-1[AUN-AUTH-1] (login, cookies, return address,
pending logins), xref:../specification/authentication.adoc#AUN-AUTH-2[AUN-AUTH-2] (rights from groups),
xref:../specification/web-app.adoc#AUN-WEB-9[AUN-WEB-9] (the shell's requests and the refusals),
xref:../specification/web-app.adoc#AUN-WEB-3[AUN-WEB-3] (canonical addresses).
Changes:: <<change-auth-2>>, <<change-session>>, <<change-provider-end>>.
Design:: xref:../concepts/web-app.adoc#_authentication[Web App, Authentication]; Token Sheriff's session layer,
proposed: BFF-1, BFF-2, BFF-5 to BFF-7, SESSION-1, SESSION-2, SESSION-4 and CLIENT-31
(`TokenSheriff/doc/client_addendum.md`).

[#UC-ACC-2]
== UC-ACC-2: Log Out

Status:: `DRAFT`
Actor:: any logged-in user, in the web app.
Goal:: end my session here and at the identity provider, so nobody can go on in my name from this browser.
Trigger:: the user chooses to log out.
Preconditions:: the user has a session, or had one in this browser.
Flow::
+
[source,text]
----
  [U] logout.request           the user logs out
       ▼
  [S] logout.end-session       the session ends here first: its cookie
       │                       is cleared, its tokens are taken out of
       │                       the store, its event streams are closed
       ▼
  [S] logout.revoke            the taken tokens are revoked, best
       │                       effort; a refused or failed revocation
       │                       is logged and does not stop the logout
       ▼
  [P] logout.provider          the browser goes to the provider's end of
       ▼                       session, which ends the provider's session
  done
----
Variations::
* *The provider is slow or unreachable*: the session here has already ended; the revocation waits no longer than the
  timeouts of the back channel, and without a usable end-session address the browser lands on the start page, while
  the provider's session stays.
* *The session had already ended*: the logout clears the cookie and lands on the start page; there is nothing to
  revoke, and the provider's session stays (xref:#UC-ACC-6[UC-ACC-6]).
* *Other open tabs* of the session lose their event stream at once; their next request is answered
  `UNAUTHENTICATED`.
* *Who builds what*: Token Sheriff's logout step takes the tokens only after the session has ended here, so the order
  cannot be reversed; until the layer exists, the bootstrap's own logout keeps the same order.
Outcome:: no session is left in the application; the provider's session ends too, wherever the provider offers an end
of session.
Requirements:: xref:../specification/authentication.adoc#AUN-AUTH-1[AUN-AUTH-1] (RP-initiated logout, revocation).
Changes:: <<change-logout>>, <<change-events>>.
Design:: xref:../concepts/web-app.adoc#_authentication[Web App, Authentication]; Token Sheriff's session layer,
proposed: SESSION-6, SESSION-7 and CLIENT-33 (`TokenSheriff/doc/client_addendum.md`).

[#UC-ACC-3]
== UC-ACC-3: Confirm a Transition with Step-Up

Status:: `DRAFT`
Actor:: an approver, in the web app.
Goal:: confirm a release, or any transition whose workflow asks for it, with a fresh multi-factor login, so that the
signed commit records how I was authenticated.
Trigger:: a transition whose workflow requires step-up is requested: under the delivered workflows every release
(xref:02-documents.adoc#UC-DOC-7[UC-DOC-7]).
Preconditions:: the user holds the right the transition needs (`approve` for a release).
Flow::
+
[source,text]
----
  [S] stepup.check             the session's acr or amr and auth_time
       │                       against the configured step-up setting
       ├── met ────────────────► stepup.write
       ▼ not met
  [S] stepup.required          nothing is written; the requested
       │                       transition is kept as the pending action;
       │                       STEP_UP_REQUIRED with the step-up address
       ├── too many pending logins ─► done, TOO_MANY_LOGINS, nothing
       │                              written
       ▼
  [P] stepup.reauthenticate    the provider asks for the second factor
       │                       (acr_values and max_age)
       ├── cancelled or failed ─► done, nothing written
       ▼
  [S] stepup.verify            acr or amr, auth_time, and that issuer and
       │                       sub are those of the session
       ├── another user or not met ─► done, nothing written
       ├── session ended meanwhile ─► done, nothing written; ↳ UC-ACC-1
       ▼
  [S] stepup.recheck           the fresh values kept in the same session;
       │                       the pending action checked again: the
       │                       right and the checks of the transition
       ├── no longer valid ────► done, the transition's refusal
       │                         (FORBIDDEN, CHANGED_SINCE_REVIEW);
       │                         nothing written
       ▼
  [S] stepup.write             the transition is written, signed, with
       ▼                       the passing values in the trailers
  done
----
Variations::
* *Through an agent*: a transition that requires step-up returns `STEP_UP_REQUIRED` and writes nothing; the user
  completes it in the web app (xref:02-documents.adoc#UC-DOC-8[UC-DOC-8]).
* *Another rule*: which transitions require step-up is data of the category's workflow, so a category can ask it for
  other transitions without code.
* *A second transition soon after*: the fresh values stay in the session, so a transition within the configured age
  (`step-up.max-age`, default `PT5M`) passes `stepup.check` without a new second factor.
* *Logged out meanwhile*: a logout in another tab ends the session; the return of the step-up finds none and writes
  nothing, because a logout always wins over a step-up still running.
* *The document changed meanwhile*: a release merges only the reviewed revision, so a save during the step-up makes
  the return answer `CHANGED_SINCE_REVIEW` (xref:02-documents.adoc#UC-DOC-7[UC-DOC-7]).
Outcome:: the transition is written only with a fresh, verified multi-factor authentication of the same user, only if
it is still valid when the user returns, and the commit says so.
Requirements:: xref:../specification/authentication.adoc#AUN-AUTH-4[AUN-AUTH-4] (step-up),
xref:../specification/authentication.adoc#AUN-AUTH-3[AUN-AUTH-3] (trailers),
xref:../specification/configuration.adoc#AUN-CONF-1[AUN-CONF-1] (the `step-up` setting); library:
https://github.com/cuioss/git-document-repository/blob/main/doc/specification/git-forms.adoc#GDR-FORMS-7[GDR-FORMS-7].
Changes:: <<change-step-up>>.
Design:: xref:../specification/web-app.adoc#AUN-WEB-6[AUN-WEB-6] (the control says "confirm with MFA"); Token Sheriff:
CLIENT-12 (step-up), and proposed SESSION-3, SESSION-8, BFF-6 (`StepUpRequirement`) and CLIENT-34
(`TokenSheriff/doc/client_addendum.md`).

[#UC-ACC-4]
== UC-ACC-4: Complete the First Login

Status:: `DRAFT`
Actor:: a user logging in for the first time, in the web app, with the default person directory (`git`).
Goal:: give my name, team and role once, or take over the entry an administrator prepared for me, so my changes are
attributed to a pseudonym and documents can name me.
Trigger:: the login finds no person entry for the user's issuer and `sub` (xref:#UC-ACC-1[UC-ACC-1]).
Preconditions:: the person directory provider is `git`; with a provider for the organisation's own source there is no
first login.
Flow::
+
[source,text]
----
  [S] firstlogin.gate          every request outside the first-login
       │                       allow-list answers FIRST_LOGIN_REQUIRED
       ▼
  [S] firstlogin.prefill       the name from the token; team candidates
       │                       from the groups; the information text
       ▼
  [U] firstlogin.enter         name, team and role, picked from the
       │                       catalogs
       ▼
  [S] firstlogin.match         are there prefilled entries with one of
       │                       these memberships, and has the user a
       │                       mapped right?
       ├── no ────────────────► firstlogin.save (new entry)
       ▼ yes
  [U] firstlogin.bind          BINDING_CANDIDATES shown with name and
       │                       memberships: bind to one, or create new
       ├── not a candidate ───► NOT_BINDABLE, back to firstlogin.bind
       ▼
  [S] firstlogin.save          the entry is saved under its pseudonym,
       │                       signed by the application, valid at once
       ▼
  done                         the gate opens; the return address
----
Variations::
* *Left unsaved*: no pseudonym is kept; the next login gets a new one and the form again.
* *A user without any mapped right* creates a new entry and learns nothing about prefilled entries.
* *Through an agent*: a tool call of such a user answers `FIRST_LOGIN_REQUIRED`.
Outcome:: the user has a person entry under a pseudonym, which every commit of the user names in its trailers.
Open points:: confirming and undoing a binding (the library's
https://github.com/cuioss/git-document-repository/blob/main/doc/concepts/directory-and-catalogs.adoc#_open_questions[Directory
and Catalogs, Open Questions]).
Requirements:: xref:../specification/directory.adoc#AUN-DIR-2[AUN-DIR-2] (first login, binding, allow-list),
xref:../specification/directory.adoc#AUN-DIR-1[AUN-DIR-1] (the provider), xref:../specification/directory.adoc#AUN-DIR-8[AUN-DIR-8]
(prefilled entries); library:
https://github.com/cuioss/git-document-repository/blob/main/doc/specification/git-directory.adoc#GDR-DIR-2[GDR-DIR-2].
Design:: xref:../concepts/web-app.adoc#_structure_of_the_app[Web App, Structure of the App] (first login as a
`WizardPage`); the gate hooks into Token Sheriff's session layer as its `SessionAugmentor`, proposed BFF-6
(`TokenSheriff/doc/client_addendum.md`); the allow-list stays Audit Notary's.

[#UC-ACC-5]
== UC-ACC-5: Keep My Directory Entry Current

Status:: `DRAFT`
Actor:: any user with the default person directory, in the web app (lens *Settings*).
Goal:: change my name, team or role when they change, and confirm them when the application asks, so that documents
show who is responsible.
Trigger:: the user opens *Settings*, or the login finds the last confirmation older than the configured interval
(default 12 months).
Preconditions:: the user has a person entry (xref:#UC-ACC-4[UC-ACC-4]).
Flow::
+
[source,text]
----
  [S] entry.show               the own entry; after the interval, "Is this
       │                       still right?"
       ▼
  [U] entry.edit               change name, team or role, or confirm
       ▼
  [S] entry.save               validated against the catalogs, saved and
       ▼                       signed; confirming writes the date
  done
----
Variations::
* *No step-up*: changes of the own entry never need one.
Outcome:: the entry is current and its confirmation date is recent.
Requirements:: xref:../specification/directory.adoc#AUN-DIR-3[AUN-DIR-3] (changing and confirming the entry).
Design:: xref:../concepts/web-app.adoc#_structure_of_the_app[Web App, Structure of the App] (lens *Settings*); the
check at login hooks into Token Sheriff's session layer like the first-login gate (xref:#UC-ACC-4[UC-ACC-4]).

[#UC-ACC-6]
== UC-ACC-6: The Session Ends Without Me

Status:: `DRAFT`
Actor:: any logged-in user, in the web app; the identity provider; the application.
Goal:: lose access as soon as the organisation withdraws it or the session runs out, and learn it with my next step
instead of working on in a session that no longer counts.
Trigger:: one of: the identity provider ends the session (a logout at the provider or in another application, an
account disabled), the provider refuses to refresh the session's tokens, the idle time or the lifetime runs out, the
user's bound of sessions is reached, or a new login in the same browser replaces the session.
Preconditions:: the user has a session.
Flow::
+
[source,text]
----
  [P] provider.logout          the provider ends the user's session by a
       │                       back-channel logout token, which acts
       │                       once
       ▼
  [S] session.end              the session ends: its tokens are
       │                       dropped, its event streams are closed;
       │                       the same step ends a session whose
       │                       refresh is refused, whose idle time or
       │                       lifetime ran out, or that a bound or a
       │                       new login replaced
       ▼
  [S] session.missing          the next request of every open tab is
       │                       answered UNAUTHENTICATED
       ▼
  ↳ UC-ACC-1                   log in again, back to the same address
       ▼
  done
----
Variations::
* *A refused refresh*: the provider refuses the session's refresh token (an account disabled, a grant withdrawn), and
  the session ends. A provider that cannot be reached ends nothing: the session goes on with the tokens it holds.
* *What counts as activity*: only a request the application lets through renews the idle time; a refused request does
  not, and an open event stream counts once, when it starts.
* *Unsaved work*: drafts are kept on the server (xref:02-documents.adoc#UC-DOC-3[UC-DOC-3]), so an ended session
  loses only the changes made since the last draft was written.
* *One instance*: the application runs as one instance, so a back-channel logout reaches every session of the user
  (xref:../adr/0001-Authentication_is_delegated_to_Token_Sheriff_with_a_server-side_session_for_the_web_app.adoc[ADR-0001]).
* *Through an agent*: an agent's bearer token is no session; a logout at the provider does not end it, and it stays
  valid until it expires, since the MCP server checks signature, expiry, issuer and audience only
  (xref:../specification/mcp-server.adoc#AUN-MCP-3[AUN-MCP-3]; xref:08-agents.adoc#UC-AGT-1[UC-AGT-1]).
Outcome:: the session ends when access is withdrawn at the provider or by a refused refresh, not only at its own
expiry, and every tab learns it with its next request.
Open points:: whether the provider sends back-channel logouts and issues refresh tokens (both settings of the provider);
without back-channel logout, the lifetime of the access token decides how late a disabled account is noticed.
Requirements:: xref:../specification/authentication.adoc#AUN-AUTH-1[AUN-AUTH-1] (idle time, lifetime); the end by the
provider: none yet.
Changes:: <<change-provider-end>>, <<change-session>>, <<change-events>>.
Design:: Token Sheriff's session layer, proposed: SESSION-2, SESSION-5 to SESSION-7, CLIENT-32 and CLIENT-35
(`TokenSheriff/doc/client_addendum.md`).

[#changes-to-the-specification]
== Changes to the Specification

Each change is the fix of a gap these use cases need; it is written into the specification once they are `AGREED`.

[[change-auth-2]]AUN-AUTH-2, the requests a right guards:: Gap: "a request without a mapped right must be refused"
reads as every request, which would also refuse the shell's own requests and the first login that
xref:../specification/directory.adoc#AUN-DIR-2[AUN-DIR-2] grants a user without any mapped right. Fix: a request on a
repository without a mapped right is refused (deny by default); requests that act on no repository, the shell's own and
those on the first-login allow-list of AUN-DIR-2, are checked by their own rules.

[[change-session]]AUN-AUTH-1, the session layer:: Gap: xref:../specification/authentication.adoc#AUN-AUTH-1[AUN-AUTH-1]
names Token Sheriff's client as the engine and leaves the session to the application, which bounds neither the
sessions nor the pending logins of one source, and renews a session on every request, refused ones included. Fix: the
login, the callback, the session and the logout run on Token Sheriff's session layer (`token-sheriff-session` and
`token-sheriff-bff-quarkus`, proposed in `TokenSheriff/doc/client_addendum.md`), and AUN-AUTH-1 keeps only Audit
Notary's choices. It adds: a bounded share of the pending logins per source; a bound of sessions in total and per
user, the oldest ending first; a login ends the session the browser still holds; only a request that is let through
renews the idle time. Decided with it: the lifetime of a pending login (10 minutes today, 5 in API Sheriff) and whether
the session cookie stays `SameSite=Strict`. The layer is a new dependency and needs the owner's approval; ADR-0001 is
amended with it.

[[change-provider-end]]AUN-AUTH-1, a session the provider ends:: Gap: nothing ends a session before its idle time or
lifetime; there is neither a back-channel logout nor a refresh, so an account disabled at the provider keeps working
for up to 8 hours, and changed groups take effect only at the next login. Fix: the application receives back-channel
logouts (https://openid.net/specs/openid-connect-backchannel-1_0.html[OpenID Connect Back-Channel Logout 1.0]) and ends
the sessions they name; it refreshes the session's tokens, ends the session when the provider refuses the refresh
token and keeps it when the provider cannot be reached; a refresh whose tokens carry the groups maps the rights again.

[[change-logout]]AUN-AUTH-1, the order of the logout:: Gap: "held tokens revoked first" leaves open whether the session
here ends before the revocation or after it, and what a logout without a session does. Fix: the session here ends
first, then the held tokens are revoked (the refresh token in any case; the access token as Token Sheriff's logout
step settles it), then the browser goes to the provider's end of session; a failed revocation never stops the logout;
a logout without a session clears the cookie and lands on the start page.

[[change-step-up]]AUN-AUTH-4, the return of the step-up:: Gap:
xref:../specification/authentication.adoc#AUN-AUTH-4[AUN-AUTH-4] does not say what is kept across the redirect to the
provider, whether the fresh values reach the session, and what happens when the session ended or the document changed
meanwhile. Fix: the requested transition is kept as the pending action of the step-up; the verified values are written
into the same session, never into a new one, and a session ended meanwhile writes nothing; on the return the right and
the checks of the transition run again before it is written.

[[change-events]]AUN-WEB-5 and AUN-WEB-9, the event stream and the session:: Gap: the event stream is one stream for
every connection, bound to no session, so it stays open after a logout or the end of the session, and it would carry
the saves of every repository to every user. Fix: each event stream belongs to the session that opened it and is closed
when that session ends; it carries only the events of repositories the session may read
(xref:../specification/web-app.adoc#AUN-WEB-5[AUN-WEB-5], xref:../specification/web-app.adoc#AUN-WEB-9[AUN-WEB-9]).
