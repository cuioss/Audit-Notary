= Use Cases: Categories and Document Types (UC-KND)
:toc: left
:toclevels: 2
:nofooter:

xref:../UseCases.adoc[Use Cases] » Categories

What Audit Notary keeps is configured on two levels. A *category* (SAMM, Threat models, Incident reports, ISMS) is
the unit an organisation switches on, sees as a lens and receives with the application or writes itself. Below it, a
*document type* (`kind` in identifiers and files, the library's term,
https://github.com/cuioss/git-document-repository/blob/main/doc/specification/git-forms.adoc#GDR-FORMS-1[GDR-FORMS-1])
is one kind of document: a JSON Schema, a workflow, a template where it has generated output, and the repository it
lives in. The ISMS category has five document types (`policy`, `isms-scope`, `audit-report`, `management-review`,
`risk`), SAMM two (`scope`, `assessment`). A schema is one file of a document type, not a level of its own.

Audit Notary delivers four categories with the application. An organisation needs further ones, an exception
approval, a supplier assessment, an access review, and should not need a release of the application for them. So
categories come from two places: the *delivered* categories inside the application, and the *custom* categories of
the organisation from a directory mounted at run time. The configuration says which categories, and which of their
document types, are switched on. A category administrator creates and changes custom categories in an editor in the
web app; an operator can also supply them as files.

[#principles]
== Principles

[#two-levels]
Two levels, one switch each:: The configuration switches a category on or off, and within a category that is on,
single document types off. A category declares which of its document types need each other, so that none is switched
off while another that needs it is on.
[#the-operator-switches]
The operator switches:: Which categories and document types are on is the operator's configuration, read at start; the
editor creates and changes categories, but a new custom category stays off until the operator switches it on. So no
category reaches the users without the operator's decision.
[#delivery-apart-from-custom]
Delivery apart from custom:: The delivered categories ship in the `categories` module and are read-only in the
application; they change only with a release of the application. The custom categories live in the categories
directory of the deployment, and only they can be created and changed at run time.
[#add-never-override]
A custom category adds, never overrides:: A custom category has its own id and its own document type ids; it never
replaces or extends a delivered one, and no custom document type is added to a delivered category. To start from a
delivered category, it is copied under a new id (<<UC-KND-2>>). This keeps the one rule of the configuration concept:
there is no second layer of overrides
(xref:../concepts/application-architecture.adoc#_configuration[Application Architecture, Configuration]).
[#configuration-never-code]
Configuration, never code:: A custom category consists of files only; it uses the generic document use cases and
cannot bring an extension point of its own. Whatever its schema cannot express it does not have.
[#same-layout]
One layout for both:: A custom category has the layout of a delivered one, so that a copied delivered category is a
valid custom category as it is.
[#documents-survive]
Documents survive:: Neither a change of a schema nor switching a document type off rewrites or deletes a document; a
released document stays as it was released.

[#layout]
== Layout of a Category

The layout is the same in the `categories` module (`categories/<category>/`) and in the categories directory
(`<categories-dir>/<category>/`):

[source,text]
----
<categories-dir>/                 the categories directory of the deployment,
                                  audit-notary.yaml → categories-dir;
                                  default /app/data/categories on the
                                  persistent volume
  <category-id>/                  one directory per custom category; the id
                                  differs from every delivered category id
    category.yaml                 the category: which document types need
                                  which others (requires), so that they are
                                  switched together
    kinds.yaml                    the library's kinds configuration: per
                                  document type its id, repository alias
                                  (one of repositories), collection,
                                  optional numbering, and its files below
    <kind>/schema.json            JSON Schema of the document type, with
                                  the markers the form knows: x-person,
                                  x-catalog, x-asciidoc, x-free-text, and
                                  format gdr-link for references
    <kind>/workflow.yaml          states, transitions, step-up, deadlines
    <kind>/template.adoc          the template of the generated output;
                                  optional for a numbered document type
    recipes/<id>.yaml             optional recipes that guide the filling in
    messages_en.properties        the category's texts: names of the
    messages_de.properties        category, its document types, fields and
                                  states; both languages hold the same keys
  .drafts/<category-id>/          the editor's unactivated changes, in the
                                  same layout (UC-KND-3, UC-KND-4)
----

The switch is in `audit-notary.yaml`, one list for delivered and custom categories (<<UC-KND-5>>):

[source,yaml]
----
categories:
  - id: samm                          # delivered; all its document types
  - id: isms                          # delivered; one document type off
    exclude-kinds: [management-review]
  - id: supplier-assessment           # custom, from the categories directory
----

[#UC-KND-1]
== UC-KND-1: Supply a Custom Category at Run Time

Status:: `DRAFT`
Actor:: the operator.
Goal:: add a category the organisation wrote or received as files, without a new release of the application.
Trigger:: the organisation needs document types the delivered categories do not have.
Preconditions:: the repository each of its document types names is configured in `repositories`; the application
creates no repository (xref:../specification/data-protection.adoc#AUN-DP-1[AUN-DP-1]).
Flow::
+
[source,text]
----
  [O] category.place           the operator places the category's
       │                       directory in the categories directory
       ▼
  [O] category.enable          the operator lists it in categories of
       │                       audit-notary.yaml (UC-KND-5)
       ▼
  [O] config.validate          --validate-config, offline, also checks
       │                       the categories directory
       ├── violations ─► one record per violation; exit 1
       ▼
  [S] boot.load                at start: every category of the list,
       │                       delivered or custom, validated with its
       │                       document types
       ├── a category invalid ─► the boot stops, one record per violation
       ▼
  [S] categories.ready         the enabled document types are known to
       ▼                       the index, the forms, the workflows and
  done                         the MCP tools
----
Variations::
* *What is checked*: every file against its meta-schema; an id that clashes with a delivered or another custom
  category or document type; a repository alias that is not configured; a reference marker naming an unknown catalog;
  messages missing in one of the two languages; a template that does not parse.
* *Present but not listed*: a custom category in the directory that the list does not name is validated by
  `--validate-config` but not loaded; it is off.
* *A file changed on disk* while the application runs takes effect at the next start; changes in the running
  application go through the editor (<<UC-KND-4>>).
* *No categories directory*: the application runs with the delivered categories only.
Outcome:: the custom category is on beside the delivered ones, and its documents are created, saved and released like
any other (xref:02-documents.adoc[UC-DOC]).
Changes:: <<change-gen-1>>, <<change-conf-1>>, <<change-category-yaml>>, <<change-modules>>.
Requirements:: xref:../specification/architecture-and-modules.adoc#AUN-GEN-1[AUN-GEN-1] (categories as
configuration, the test category from resources only), xref:../specification/configuration.adoc#AUN-CONF-1[AUN-CONF-1]
(boot validation, `--validate-config`); the categories directory: none yet; library:
https://github.com/cuioss/git-document-repository/blob/main/doc/specification/git-forms.adoc#GDR-FORMS-1[GDR-FORMS-1]
(kinds as configuration, in a directory chosen by the application).
Design:: none; an operator works with files.

[#UC-KND-2]
== UC-KND-2: Inspect the Categories and Copy One

Status:: `DRAFT`
Actor:: a category administrator (`administer-categories`), in the web app.
Goal:: see how a category is defined, its document types with their schema, workflow, template and recipes, and start
a custom category from it.
Trigger:: the administrator wants to understand a category, or to build a similar one.
Preconditions:: the user has `administer-categories`.
Flow::
. *The categories*: delivered and custom, each marked as such and as on or off, with its document types, each marked
  on or off, the repository of each and the number of its documents.
. *A document type*: its `schema.json`, `workflow.yaml` and `template.adoc`, read-only for a delivered category, with
  the form the schema generates.
. *Copy*: a category is copied under a new id; every document type id gets the new id's prefix, and the copy opens in
  the editor as an unactivated custom category (<<UC-KND-3>>).
Variations::
* *A delivered category* can be read and copied, never changed.
* *Off categories* are shown too, so that the administrator sees what exists before asking the operator to switch it
  on.
Outcome:: the administrator knows the category's definition, or holds an unactivated copy of it.
Changes:: <<change-auth-2>>, <<change-web-3>>.
Requirements:: none yet.
Design:: none yet.

[#UC-KND-3]
== UC-KND-3: Create a Custom Category in the Editor

Status:: `DRAFT`
Actor:: a category administrator (`administer-categories`), in the web app.
Goal:: write a new category, its document types with their schemas, workflows and templates, and its texts, and see
the form and the output it produces before anyone uses it.
Trigger:: the organisation needs new document types.
Preconditions:: the user has `administer-categories`; the repositories its document types will name are configured.
Flow::
+
[source,text]
----
  [U] category.new             blank, with a minimal document type, or
       │                       a copy (UC-KND-2); the id
       ├── id taken ─► category.new
       ▼
  [U] editor.edit              category.yaml, kinds.yaml, per document
       │                       type schema.json, workflow.yaml,
       │                       template.adoc, the recipes and the
       │                       messages, as text
       ▼
  [S] editor.check             while typing: each file against its
       │                       meta-schema, the ids, the repository
       │                       aliases, the catalogs named, requires,
       │                       the messages of both languages; errors
       │                       at their line
       ▼
  [S] editor.preview           the form generated from the schema, with
       │                       sample data the administrator types into
       │                       it; the output generated from the sample
       │                       data and the template, rendered by the
       │                       server
       ▼
  [U] editor.keep              the unactivated change kept in .drafts
       ├── go on later ─► done, nothing active
       ▼ activate
  ↳ UC-KND-4                   activation
       ▼
  done                         the definition is current; the category
                               stays off until the operator switches it
                               on (UC-KND-5)
----
Variations::
* *Sample data* lives only in the preview; it is never saved as a document.
* *The workflow*: states, transitions, which transition requires step-up and the deadline rules are data; the
  editor checks them against the library's workflow format.
* *A further document type* is added to a custom category in the same editor; a delivered category takes none.
* *An agent* cannot create or change a category.
Outcome:: a new custom category, checked and previewed, waits for activation in the editor's drafts, or is activated
and waits for the operator to switch it on.
Open points:: <<open-points>>.
Changes:: <<change-auth-2>>, <<change-web-3>>, <<change-web-7>>, <<change-gen-3>>, <<change-category-yaml>>.
Requirements:: xref:../specification/web-app.adoc#AUN-WEB-4[AUN-WEB-4] (the form generated from the schema, the same
validation in browser and server), xref:../specification/web-app.adoc#AUN-WEB-8[AUN-WEB-8] (output rendered and
sanitised by the server); the editor: none yet.
Design:: none yet.

[#UC-KND-4]
== UC-KND-4: Change and Activate a Custom Category

Status:: `DRAFT`
Actor:: a category administrator (`administer-categories`), in the web app.
Goal:: change a custom category that may be in use, a schema above all, and know before activating it what the change
does to the documents that exist.
Trigger:: a field is added, renamed or removed, a workflow or a template changes, or a new category is ready
(<<UC-KND-3>>).
Preconditions:: the user has `administer-categories`; the category is custom.
Flow::
+
[source,text]
----
  [U] editor.edit              the change, in the editor of UC-KND-3,
       │                       with its checks and preview
       ▼
  [S] change.compatibility     every saved document of each changed
       │                       document type validated against the new
       │                       schema (required excepted, as a save
       │                       does); released documents listed apart,
       │                       never changed
       ▼
  [U] change.review            the diff of the category's files against
       │                       the active version, and the documents
       │                       that would fail, with the fields
       ├── back ─► editor.edit
       ▼ activate
  ↳ UC-ACC-3                   step-up
       ├── not confirmed ─► done, nothing activated
       ▼
  [S] change.activate          the files moved from .drafts into place
       │                       at once; if the category is on, its
       │                       document types reloaded without a
       │                       restart; one audit record with pseudonym,
       │                       category and the files changed
       ├── invalid by now ─► done, nothing activated, the violations
       ▼
  done                         new forms and saves use the new schema
----
Variations::
* *A document that fails the new schema* stays as it is; its next save asks for the fields the new schema needs.
* *An open draft* of a changed document type is validated against the new schema at its next save.
* *A document type with documents* cannot be removed from the category's files, because its documents must stay
  readable; to stop using it, the operator switches it off (<<UC-KND-5>>).
* *A delivered category* cannot be changed; copy it (<<UC-KND-2>>).
Outcome:: the new version of the category is active, the change is on record, and no document was rewritten.
Open points:: <<open-points>>.
Changes:: <<change-auth-2>>, <<change-gen-1>>, <<change-gen-3>>.
Requirements:: xref:../specification/authentication.adoc#AUN-AUTH-4[AUN-AUTH-4] (step-up, when a workflow declares it;
here asked of an activation, which no requirement names yet), xref:../specification/architecture-and-modules.adoc#AUN-GEN-5[AUN-GEN-5]
(the audit record); the compatibility check and the activation: none yet.
Design:: none yet.

[#UC-KND-5]
== UC-KND-5: Switch Categories and Document Types On or Off

Status:: `DRAFT`
Actor:: the operator.
Goal:: decide which categories, delivered or custom, and which of their document types the organisation uses.
Trigger:: the application is set up; a custom category is ready (<<UC-KND-3>>); the organisation starts or stops
using a category or a document type, for example the ISMS without management reviews.
Preconditions:: the categories to switch on exist, delivered or in the categories directory.
Flow::
+
[source,text]
----
  [O] categories.edit          the list categories in audit-notary.yaml:
       │                       per category its id, and optionally the
       │                       document types to leave out
       │                       (exclude-kinds)
       ▼
  ↳ UC-OPS-1                   validated offline and at start
       ├── unknown category or document type ─► refused, named
       ├── a document type left out that an enabled one requires
       │       ─► refused, naming both
       ▼
  [S] categories.apply         on: lenses, forms, workflows, deadlines
       │                       and MCP tools for the enabled document
       │                       types; off: none of these
       ▼
  done
----
Variations::
* *Switched off with documents*: no new documents, no saves and no releases of that category or document type; its
  documents stay in Git untouched, references to them still resolve, and they stay readable through the references
  and the search.
* *Switched on again*: the documents are there as they were left.
* *Requires*: SAMM's `assessment` requires `scope`, so `scope` cannot be left out while assessments are on; a category
  declares this in its `category.yaml`.
* *Deadlines and reminders* of a switched-off document type are no longer computed or shown.
Outcome:: exactly the configured categories and document types are in use; nothing was deleted.
Open points:: whether a category administrator may switch categories in the application instead of the operator; that
switch would be durable state, with the same question as the editor's (<<open-points>>, point 1).
Changes:: <<change-conf-1>>, <<change-category-yaml>>.
Requirements:: xref:../specification/configuration.adoc#AUN-CONF-1[AUN-CONF-1] (`categories`, the list of enabled
categories, boot validation); the document-type switch: none yet.
Design:: none; an operator works with files.

[#open-points]
== Open Points

. *Durable state outside Git.* The editor writes the categories directory on the volume, which is durable state that
  is not in Git; xref:../specification/architecture-and-modules.adoc#AUN-GEN-3[AUN-GEN-3] allows none. Either the
  categories directory is accepted as configuration the operator backs up with the volume, or it is kept as a
  repository of its own (`categories`), whose activations are signed commits with the administrator in the trailers
  and whose history is the history of the category. To be decided in an ADR.
. *Schema evolution.* Documents saved under an earlier version of their schema, released ones above all, which are
  immutable. Whether each document records the version or checksum of the schema it was saved with, so that it can
  be shown and validated against that version, is open; the library has no notion of either.
. *Where a custom category is shown.* xref:../specification/web-app.adoc#AUN-WEB-3[AUN-WEB-3] has a fixed list of
  lenses and canonical addresses; a custom category needs a generic lens (for example *Documents*, category ›
  document type › document) and an address of its own.
. *What an agent may read.* Agents work on documents of custom document types through the generic tools; whether
  they may also read a category's definition (a tool `read_category`) is open. They never change one.
. *Blocking or confirming.* Whether a change that would make saved, unreleased documents invalid is refused, or
  activated after an explicit confirmation, as <<UC-KND-4>> proposes.
. *Template engine and schema dialect.* The editor checks templates and schemas with the engine and dialect the
  library has not chosen yet
  (https://github.com/cuioss/git-document-repository/blob/main/doc/concepts/schema-driven-documents.adoc#_open_questions[Schema-Driven
  Documents, Open Questions]).
. *Switching in the application.* Whether a category administrator may switch categories and document types on and
  off in the application, instead of the operator in the configuration (<<UC-KND-5>>).

[#changes-to-the-specification]
== Changes to the Specification

Each change is the fix of a gap these use cases need; it is written into the specification once they are `AGREED`.

[[change-gen-1]]AUN-GEN-1, two levels and two places:: Gap: a category comes only from the `categories` module, and
the terms category and kind of document are not set apart. Fix: a category is a set of document types (`kind`), and
the prose says "document type"; a category comes from the `categories` module (delivered, read-only) or from the
categories directory (custom); a custom category has its own ids, never extends a delivered one, and has no extension
point; the test category `test-note` also passes from the categories directory.
[[change-conf-1]]AUN-CONF-1, the categories and their switch:: Gap: `categories` lists only delivered categories, by
id, no key names a categories directory, and the boot validation does not check categories. Fix: `categories-dir`
(default `/app/data/categories`); `categories` is a list of `{id, exclude-kinds}` naming every enabled category,
delivered or custom, and anything not listed is off; the boot validation and `--validate-config` check every listed
category with the rules of <<UC-KND-1>> and refuse an unknown id, an unknown document type in `exclude-kinds`, and a
document type left out that an enabled one requires.
[[change-category-yaml]]Category declaration, `category.yaml`:: Gap: the library's `kinds.yaml` describes each
document type alone; nothing says which document types need each other. Fix: a file `category.yaml` per category,
owned by the application, with `requires` per document type; the library's `kinds.yaml` stays unchanged.
[[change-auth-2]]AUN-AUTH-2, a right for categories:: Gap: no action permits changing a category. Fix: the action
`administer-categories`, not bound to a repository; with a repository for categories (<<open-points>>, point 1),
bound to that repository.
[[change-web-3]]AUN-WEB-3, a lens for custom categories:: Gap: the lenses are fixed. Fix: a lens for the documents of
custom categories, the canonical addresses `/categories/<category>` (the definition and the editor) and the documents'
addresses (<<open-points>>, point 3); a lens of a switched-off delivered category is not shown.
[[change-web-7]]AUN-WEB-7, texts of custom categories:: Gap: the message catalogue has one source, the `web-app`
JAR (xref:../specification/web-app.adoc#AUN-WEB-7[AUN-WEB-7]). Fix: the catalogue merges the messages of each enabled
custom category under its own key prefix (`category.<id>.`); both languages hold the same keys.
[[change-gen-3]]AUN-GEN-3, the categories directory as state:: Gap: durable state only in Git. Fix: as decided in
<<open-points>>, point 1: either the categories directory is named as the one durable state outside Git, backed up
with the volume, or the custom categories live in a repository of their own.
[[change-modules]]Architecture and Modules, the run-time directory:: Gap: the open question of
xref:../concepts/application-architecture.adoc#_open_questions[Application Architecture] whether the categories ship
inside the application or as a mounted directory. Fix: both; the delivered ones inside, the custom ones mounted, as in
<<layout>>.
