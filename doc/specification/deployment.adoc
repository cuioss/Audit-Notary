[#AUN-OPS-1]
== AUN-OPS-1: Native Image and Container

* The application must compile with `release` 25 and ship as a Quarkus native image.
* The image must be based on a digest-pinned distroless image, run as `nonroot`, carry OCI labels for version,
  revision, source and licence, and answer its health check through the binary.
* The image must be published as one index for `linux/amd64` and `linux/arm64` at `ghcr.io/cuioss/audit-notary`.

[cols="1,3"]
|===
|Property |Value

|Builder
|`quay.io/quarkus/ubi9-quarkus-mandrel-builder-image:jdk-25` (`quarkus.native.builder-image`)

|Dockerfile
|`audit-notary/src/main/docker/Dockerfile.native`

|Base image
|`quay.io/quarkus/quarkus-distroless-image:2.0@sha256:<digest>`; the digest is updated by a dependency bot

|User and binary
|`nonroot`, declared numerically as `65532:65532`, its id in the base image's `/etc/passwd`; `/app/application`

|Health check
|`HEALTHCHECK CMD ["/app/application","--health-probe"]`; the binary probes its own management port and exits `0`
or `1` before Quarkus boots

|Labels
|`org.opencontainers.image.{title,description,version,revision,vendor,licenses,source,base.name}`; version and
revision from build arguments `APP_VERSION`, `APP_REVISION`

|Platforms
|`linux/amd64`, `linux/arm64`, each built natively on its own runner and joined into one index

|Name
|`ghcr.io/cuioss/audit-notary:<version>`
|===

[#AUN-OPS-2]
== AUN-OPS-2: Ports and Readiness

* The application must serve HTTPS on 8443 and the management interface (readiness, liveness, metrics) on 9000.
* Readiness must report `UP` only when the configuration repository and every repository of the configuration applied at the start
  have a valid local repository (fetched in this process or kept from an earlier fetch), a configuration is applied, the person
  directory is loaded and the index is built; a later fetch failure, or a new configuration that is not applied
  (xref:configuration.adoc#AUN-CONF-4[AUN-CONF-4]), must not drop readiness.

[cols="1,1,2"]
|===
|Port |Protocol |Serves

|`8443`
|HTTPS
|Web app, `/api/v1`, `/mcp`, `/.well-known/oauth-protected-resource/mcp` and `/.well-known/oauth-protected-resource`

|`8080`
|HTTP
|Redirect to `8443` only

|`9000`
|HTTP (management)
|`/q/health/live`, `/q/health/ready`, `/q/metrics`
|===

Readiness checks, all required for `UP`: `configuration`, `repositories`, `persons`, `index`. A repository without a
local copy keeps its check `DOWN` until its first fetch succeeds, so the application can start from the volume while
the Git server is unreachable. A repository added by a new configuration keeps readiness `UP` while it is cloned and
is served once its clone is complete.

Volume: `/app/data` holds the local repositories, the configuration repository's included, and the drafts. It is mounted from a persistent volume; the image
declares no volume. `/app/data/config` (`XDG_CONFIG_HOME` of the image) holds the user config of JGit, which caches the
file-time resolution of the file store there; the root file system is read-only, so the cache lives on the volume and
survives restarts. The image seeds the file with `gc.auto = 0` and `gc.autoDetach = false`: the bare repositories are
fetched, never worked in, and a background gc on a fresh clone would race with the move of the clone out of its staging
directory. The
application sets no other value there.

== Secrets

[cols="1,2"]
|===
|Secret |Mount or reference

|TLS key and certificate
|`/run/secrets/tls/{tls.key,tls.crt}`

|OIDC client credential
|`audit-notary.oidc.client-credential-ref`: the client secret or the `private_key_jwt` key; only with the login provider `oidc`

|Users file of the local users
|`audit-notary.login.local.users-ref`: the users, their password hashes and roles in Quarkus' format;
`audit-notary.login.local.cookie-key-ref`,
a separate secret: the key of the login cookie. Only with the login provider `local`, which is for evaluation
and tests, not for production (xref:authentication.adoc#AUN-AUTH-6[AUN-AUTH-6])

|Git credential of the technical user
|`audit-notary.git.credential-ref`, one for every repository, the configuration repository included

|Commit-signing key
|`audit-notary.signing.key-ref`: a `kms:` key id or a `file:` reference

|Anchor key of the own timestamp
|`audit-notary.anchor.signed-key-ref`: a `kms:` key id or a `file:` reference, never the commit-signing key

|Credentials of an RFC 3161 timestamp authority
|`audit-notary.anchor.timestamp.credentials-ref`; only with the anchor provider `rfc3161`
|===

The two `allowed_signers` files and the trust of a timestamp authority hold public keys only and are no secrets, but
they are trust anchors: they are mounted read-only and named by `audit-notary.signing.allowed-signers`,
`audit-notary.anchor.signed-allowed-signers` and `audit-notary.anchor.timestamp.trust`, never read from a repository
(xref:configuration.adoc#AUN-CONF-3[Configuration, AUN-CONF-3], which also lists the reference forms each key
accepts).

[#AUN-OPS-3]
== AUN-OPS-3: Compose Sample

* The deployment module must provide a compose sample that runs the published image with Keycloak and Gitea, and a
  check script that logs in, saves and releases a document.

Location: `deployment/compose-sample/`. Never builds an image; the image is `${AUDIT_NOTARY_IMAGE}`.

[cols="1,3"]
|===
|Service |Role

|`audit-notary`
|The application, named volume `audit-notary-data`; the service-level settings as environment variables, the
configuration repository in Gitea

|`keycloak`
|Realm `audit-notary` with users of each group, a confidential client for the web login and a client for an MCP
agent

|`gitea`
|Git server with the configuration repository and the repositories of the default cut
|===

Scripts in `scripts/`: `start-sample.sh`, `stop-sample.sh`, `check-sample.sh` (logs in as a test user, writes a SAMM
draft, saves it, releases it with step-up, and verifies the release tag in Gitea).
