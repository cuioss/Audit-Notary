== Owned by the Libraries

The application builds on the libraries of `git-document-repository` and on Token Sheriff. Their behaviour is
referenced here, never restated:

[cols="1,2"]
|===
|Behaviour |Owner

|Drafts, saving, compare-and-swap, release by merge and tag, in-memory index, post-commit listeners, commit
signature, identity trailers, signature check, anchoring with the own timestamp
|https://github.com/cuioss/git-document-repository/blob/main/doc/specification/git-store.adoc[`git-store` specification]

|Schemas, templates, workflows, step-up check, deterministic serialisation, running numbers, generated output
|https://github.com/cuioss/git-document-repository/blob/main/doc/specification/git-forms.adoc[`git-forms` specification]

|Person directory: pseudonyms, person entries in Git by default, erasure; catalogs and stable ids
|https://github.com/cuioss/git-document-repository/blob/main/doc/specification/git-store.adoc#GDR-STORE-19[GDR-STORE-19],
https://github.com/cuioss/git-document-repository/blob/main/doc/specification/git-directory.adoc[`git-directory` specification]

|Repositories, remote policy, transport
|https://github.com/cuioss/git-document-repository/blob/main/doc/specification/git-core.adoc[`git-core` specification]

|OIDC confidential client, step-up (RFC 9470), logout, token validation
|Token Sheriff (link:https://github.com/cuioss/TokenSheriff/tree/main/doc/client[client],
link:https://github.com/cuioss/TokenSheriff/tree/main/doc/validation[validation])

|The session, its bounds and its end, CSRF, the session view, the step-up into the session
|Token Sheriff's planned session layer, `token-sheriff-session` and `token-sheriff-bff-quarkus`; until then the
application's own code carries the session, without its bounds, refresh, back-channel logout or the end of the session
the browser held, and gains no new capability
(xref:../adr/0004-Login_and_session_are_designed_against_Token_Sheriffs_planned_session_layer.adoc[ADR-0004])
|===

[#AUN-GEN-1]
== AUN-GEN-1: Categories as Configuration

* Each category (SAMM, threat models, incident reports, ISMS) must be defined as one or more kinds of documents of
  the library (https://github.com/cuioss/git-document-repository/blob/main/doc/specification/git-forms.adoc#GDR-FORMS-1[GDR-FORMS-1]), each with a JSON Schema, an
  AsciiDoc template where the kind has generated output, and a workflow; the only code of a category is a named
  extension point for behaviour a schema cannot express.
* Adding a category must require no Java source change: a test category supplied as resources only must pass create,
  save, release and generated output in the integration tests.

[cols="1,3"]
|===
|File |Content

|`kinds.yaml`
|The library's `kinds` configuration for the kinds of the category: kind id, repository alias, collection, the
optional numbering, and the three files below

|`<kind>/schema.json`
|JSON Schema of the kind's YAML documents; a field that names a person carries `"x-person": true` and holds a
pseudonym

|`<kind>/template.adoc`
|Template that generates the AsciiDoc output from YAML and fragments; optional for a numbered kind

|`<kind>/workflow.yaml`
|States, transitions, deadlines as data
|===

The kinds: `scope` and `assessment` (SAMM), `threat-model`, `incident`, the four document types of
xref:category-isms.adoc#AUN-ISMS-1[AUN-ISMS-1] and `risk` (ISMS).

Besides the category definitions, the `categories` module carries the catalog declarations
(xref:directory.adoc#AUN-DIR-4[AUN-DIR-4]) and the threat-model recipes `categories/threat-models/recipes/<id>.yaml`
(xref:category-threat-models.adoc#AUN-TM-5[AUN-TM-5]); both are resources, not code.

The only extension point is `ScoreCalculator` (SAMM scores), a named CDI interface in `service`. The test category
`categories/test-note/` exercises create, save, release and output generation without it.

[#AUN-GEN-2]
== AUN-GEN-2: One Rule Set for Both Interfaces

* Every operation offered by the MCP server must be executed by the same application service as the web app's
  equivalent operation, with the same rights check, schema validation and step-up check.
* For every MCP tool that has an equivalent web-app operation, a test must show that the web-app request and the tool
  call with the same user and input produce the same outcome (success, validation error, conflict, forbidden).

Web-app equivalents: `list_documents` the document lists of the lenses and `read_catalog` the *Catalogs* lens
(xref:web-app.adoc#AUN-WEB-3[AUN-WEB-3]), `list_due` the *Due* lens, `search` the search of the top bar
(xref:../concepts/web-app.adoc#_structure_of_the_app[Web App, Structure of the App]), `read_recipe` the recipe's
`WizardPage` (xref:category-threat-models.adoc#AUN-TM-5[AUN-TM-5]), `read_document` the document request
`GET /api/v1/documents/…`, `diff` the diff request (xref:web-app.adoc#AUN-WEB-6[AUN-WEB-6]), `write_draft` the
draft save and `save` the save (xref:web-app.adoc#AUN-WEB-5[AUN-WEB-5]). Two tools
have no web-app equivalent and are tested through the MCP server alone: `discard_draft`, because the web app offers
no discarding of a draft, and `request_release`. An agent can only request a release: `request_release` returns
`RELEASE_REQUESTED`, and completing a release is a web-app operation, which requires step-up under the shipped
workflows
(xref:mcp-server.adoc#AUN-MCP-6[AUN-MCP-6], xref:authentication.adoc#AUN-AUTH-4[AUN-AUTH-4]).

[cols="1,2,2"]
|===
|Package (below `de.cuioss.notary.audit`) |Content |May depend on

|`web`
|REST resources `/api/v1`, event stream, session and CSRF handling
|`service`, `security`

|`mcp`
|MCP endpoint, protected-resource metadata, tool adapters
|`service`, `security`

|`security`
|Rights mapping, token and session context, inbound validation
|`config`

|`service`
|Application services: documents, workflow transitions, deadlines, dashboards, directory flows
|`config`, the `git-document-repository` modules

|`config`
|Configuration model, boot validation rules
|—
|===

Commit signing, anchoring and the person directory belong to the libraries; `service` configures them from
`audit-notary.yaml`. Its only adapters are the key source behind `kms:` references, a provider of the library's
`SigningKeySource` (https://github.com/cuioss/git-document-repository/blob/main/doc/specification/git-store.adoc#GDR-STORE-12[GDR-STORE-12]), and the resolution of
`vault:` references. Outbound calls go to the Git server, the identity provider, the KMS or Vault and, with the anchor
provider `rfc3161`, the timestamp authority; there is no other.

ArchUnit rules of the unit lane: no class outside `service` depends on a `git-document-repository` package;
`web` and `mcp` do not depend on each other. Every MCP tool delegates to exactly one service method; for a tool with
a web-app equivalent, a web resource calls the same method.

[#operation-outcomes]
=== Operation Outcomes

Each operation of the application services has one closed set of outcomes, the same for the web app and the MCP
server. Every operation can also end with `FORBIDDEN` (no mapped right,
xref:authentication.adoc#AUN-AUTH-2[AUN-AUTH-2]) and `FIRST_LOGIN_REQUIRED`
(xref:directory.adoc#AUN-DIR-2[AUN-DIR-2]).

[cols="1,1,3"]
|===
|Operation |Tool |Outcomes

|Write a draft
|`write_draft`
|`DRAFT_SAVED`; validation errors per field

|Discard a draft
|`discard_draft`
|`DISCARDED`

|Save
|`save`
|`SAVED`; `CONFLICT` (per file, with the fields that differ and both values); validation errors per field, among them
`REFERENCE_NOT_FOUND` (xref:data-protection.adoc#AUN-DP-2[AUN-DP-2]); `DOCUMENT_RELEASED`
(xref:category-samm.adoc#AUN-SAMM-4[AUN-SAMM-4]); `REJECTED` (the Git server refused the push,
xref:authentication.adoc#AUN-AUTH-5[AUN-AUTH-5]); `GIT_UNAVAILABLE` (<<AUN-GEN-6>>); `STEP_UP_REQUIRED` when the
workflow requires step-up for the transition (xref:authentication.adoc#AUN-AUTH-4[AUN-AUTH-4])

|Transition into review
|—
|The new state; `MANDATORY_FIELDS_MISSING` with the JSON Pointers of the missing fields
(xref:category-incident-reports.adoc#AUN-IR-3[AUN-IR-3]); `STEP_UP_REQUIRED` when the workflow requires step-up for
the transition

|Release
|—
|`RELEASED`; `STEP_UP_REQUIRED` with the step-up address (xref:authentication.adoc#AUN-AUTH-4[AUN-AUTH-4]);
`MANDATORY_FIELDS_MISSING`; `REJECTED`; `GIT_UNAVAILABLE`

|Request a release
|`request_release`
|`RELEASE_REQUESTED` with the request id; `REJECTED`; `GIT_UNAVAILABLE` (an open request is a document saved in Git,
<<AUN-GEN-3>>)

|Read, list, search, diff
|`read_document`, `list_documents`, `search`, `diff`, `list_due`, `read_catalog`, `read_recipe`
|The result
|===

[#AUN-GEN-3]
== AUN-GEN-3: No Database of Its Own

* The application must persist durable state only in Git repositories.
* The in-memory index and computed reminders must be rebuilt from Git at start; a restart test must show identical
  dashboard results before and after restart.
* The application must not configure a datasource.

[cols="1,1,2"]
|===
|State |Built |Rebuild trigger

|Index
|At start, per repository
|Save, release, periodic fetch

|Person directory (`git`)
|At start, from the persons' repository
|Fetch that moves its `main`, own save of an entry, binding, prefilled entries, erasure

|Pending release requests
|From the index (open requests are documents)
|As index

|Reminders
|From the index
|Every minute

|Drafts
|Not in memory: `refs/drafts/<pseudonym>/…` in the local repository on the persistent volume
|Not rebuilt; survive a restart only with the volume

|Web sessions
|On login
|Not rebuilt; lost on restart
|===

No `quarkus-datasource` or Hibernate extension is on the class path; an enforcer rule bans them.

[#AUN-GEN-4]
== AUN-GEN-4: Persistence Only Through the Libraries

* Application packages must reach Git only through the `git-document-repository` modules; an ArchUnit rule must fail
  the build when an application package imports `org.eclipse.jgit`.

[#AUN-GEN-5]
== AUN-GEN-5: Logging and Metrics

* Every message at INFO and above must use a `LogRecord` documented in `LogMessages.adoc`.
* The application must expose Prometheus metrics on the management port.

Logger: `de.cuioss.tools.logging.CuiLogger`; one `LogMessages` class per package root, DSL style, identifiers
`AUDIT-NOTARY-<n>`. `LogMessages.adoc` lists every record (identifier, level, template, parameters, trigger) and is
created with the code. Metrics: `quarkus-micrometer-registry-prometheus` at `/q/metrics`, names below
`audit_notary_`.

[#AUN-GEN-6]
== AUN-GEN-6: Unreachable Git Server

* When the Git server is unreachable, reads must be served from the local repositories and the web app must show the
  degraded state.
* A save must then fail with `GIT_UNAVAILABLE` and leave the draft unchanged; no change may be reported as saved
  before its push succeeded.

[cols="1,2"]
|===
|Condition |Behaviour

|Fetch fails
|The index serves the last fetched state; the health check `git-remote` (health group
`/q/health/group/git-remote`) reports `DOWN` with the fetch state per repository; readiness
stays `UP`

|Push fails during a save
|The save result is `GIT_UNAVAILABLE`; nothing is kept on the local working branch, the draft holds the work, and the
user saves again later

|Git server unreachable at start
|See xref:deployment.adoc#AUN-OPS-2[Deployment, AUN-OPS-2]
|===
