= Audit Notary: Authentication
:toc: left
:toclevels: 2
:toc-title: Table of Contents
:source-highlighter: highlight.js

xref:../README.adoc[Audit Notary documentation] » Specification

Login, rights, the identity values written into commits, step-up, the Git credential and the local users. Reasoning:
xref:../concepts/authentication-and-identity.adoc[Authentication and Identity].

A deployment has exactly one login provider, `login.provider` in `audit-notary.yaml`: `oidc` (the default), the
organisation's identity provider through Token Sheriff (<<AUN-AUTH-1>>), or `local`, the users of a mounted file in
Quarkus' format (<<AUN-AUTH-6>>,
xref:../adr/0005-Local_users_from_a_mounted_file_are_for_evaluation_and_testing_only.adoc[ADR-0005]).
<<AUN-AUTH-2>> to <<AUN-AUTH-5>> apply to both; where a value comes from a token claim, <<AUN-AUTH-6>> names its
source with local users. The library contract for the
signature, the trailers and the step-up check is in https://github.com/cuioss/git-document-repository/blob/main/doc/specification/git-store.adoc#GDR-STORE-12[GDR-STORE-12],
https://github.com/cuioss/git-document-repository/blob/main/doc/specification/git-store.adoc#GDR-STORE-13[GDR-STORE-13] and
https://github.com/cuioss/git-document-repository/blob/main/doc/specification/git-forms.adoc#GDR-FORMS-7[GDR-FORMS-7].

[#AUN-AUTH-1]
== AUN-AUTH-1: Web Login

With the login provider `oidc`:

* The web login must use the authorization code flow with PKCE `S256` as a confidential client through Token Sheriff.
* No access, refresh or ID token may be sent to the browser, with one exception: the ID token as `id_token_hint` in
  the address of the RP-initiated logout, after the held tokens are revoked and the session is ended.
* During login the browser must hold only a short-lived login-transaction cookie, afterwards only the session cookie,
  both `HttpOnly` and `Secure`; the session must end after a configurable idle time (default 30 minutes) and absolute
  lifetime (default 8 hours).
* The `return` address of the login must be accepted only as a same-origin relative path that matches a canonical
  address (xref:web-app.adoc#AUN-WEB-3[AUN-WEB-3]); any other value must be replaced by `/`.
* Logout must be RP-initiated and revoke the held tokens.

[cols="1,3"]
|===
|Item |Value

|Engine
|`token-sheriff-client-quarkus`, confidential client; the session, its bounds, its end and the endpoints are designed
against Token Sheriff's planned session layer
(xref:../adr/0004-Login_and_session_are_designed_against_Token_Sheriffs_planned_session_layer.adoc[ADR-0004])

|Flow
|Authorization code, PKCE `S256`, session-bound `state` and `nonce`, issuer check; PAR when the provider supports it

|Endpoints
|`GET /api/v1/auth/login?return=<address>`, `GET /api/v1/auth/callback`, `POST /api/v1/auth/logout`

|Response mode
|`response_mode=query`: the provider sends the browser back to the callback with `code`, `state` and `iss` in the
query, a top-level `GET` navigation that carries the transaction cookie. Token Sheriff's default is `form_post`,
whose callback is a cross-site `POST` without `SameSite=Lax` cookies
(link:https://www.ietf.org/archive/id/draft-ietf-httpbis-rfc6265bis-22.html#section-5.6.7.1[draft-ietf-httpbis-rfc6265bis-22, §5.6.7.1]);
the application asks for `query` through `AuthorizationRequestOptions` with `ResponseMode.QUERY` (Token Sheriff
CLIENT-27, since 0.9.10), as API Sheriff does. Accepted cost: the code appears in the callback
address; PKCE, the single use of the code, the transaction with `state` and `Referrer-Policy: no-referrer` bound it

|Provider metadata
|From Token Sheriff's discovery cache (`CachingDiscoveryResolver`, CLIENT-29): refreshed one hour after it was read;
while the provider cannot be reached, the last document serves logins for 24 hours more, and a failed refresh is
retried after one minute at the earliest (`sheriff.client.discovery-cache.*` in `application.properties`)

|Transaction cookie
|`__Host-audit-notary-login`; `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, `Max-Age=600`; carries only an opaque
reference to the server-side login transaction (`state`, `nonce`, PKCE verifier); taken once and deleted by the
callback. `Lax`, because the browser does not send a `SameSite=Strict` cookie on the cross-site redirect back from the
identity provider

|Session cookie
|`__Host-audit-notary-session`; `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`; set by the callback

|Callback response
|A small same-origin page that navigates to the checked `return`, not a `302`: a `302` continues the navigation that
the identity provider's page started, and `Strict` cookies are not sent with top-level navigations triggered from a
cross-site document context
(link:https://www.ietf.org/archive/id/draft-ietf-httpbis-rfc6265bis-22.html#section-5.6.7.1[draft-ietf-httpbis-rfc6265bis-22, §5.6.7.1];
a request is same-site only if its URL is same-site with its client's "site for cookies", §5.2;
link:https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie[MDN]: `Strict` cookies are sent
only for requests originating from the same site). The navigation started by the same-origin page is same-site and
carries the session cookie.

|Idle timeout, lifetime
|`web.session.idle-timeout` (default `PT30M`), `web.session.max-lifetime` (default `PT8H`)

|Logout
|RP-initiated at the provider's `end_session_endpoint`; held tokens revoked first. Revocation is best effort: a
provider without `revocation_endpoint` or a refused revocation (logged, `AUDIT-NOTARY-104`) does not stop the logout;
provider metadata that cannot be read does not stop it either: the logout then ends only the session here and lands on
the start page (logged, `AUDIT-NOTARY-106`). The
session ends and the tokens are dropped from the application in every case, and the end-session request ends the
provider's session. The address carries the ID token as
`id_token_hint`, which OpenID Connect RP-Initiated Logout recommends
(link:https://openid.net/specs/openid-connect-rpinitiated-1_0.html#RPLogout[RP-Initiated Logout 1.0, §2]: the RP
redirects the user agent to the logout endpoint; `id_token_hint` RECOMMENDED); with it the provider ends its session
without asking again. The application accepts no token from the browser, only the session cookie

|Pending logins
|At most 10,000 login transactions at once, each for 10 minutes; a start beyond that answers `503 TOO_MANY_LOGINS`
with `Retry-After: 60` (the login is reachable without a session). Every transaction has the same lifetime, so each
start drops the expired and taken transactions in the order of their expiry, without scanning the others. A start
whose authorization request cannot be sent (PAR refused) frees its place at once

|`401` from `/api/v1`
|Response body names the login address; the web app follows it with the current canonical address as `return`
|===

[#AUN-AUTH-2]
== AUN-AUTH-2: Rights

* Rights must be derived from identity-provider groups through a configured mapping to repositories and the actions
  *read*, *edit*, *approve* and *administer catalogs*.
* Every request must be checked; a request without a mapped right must be refused (deny by default).
* No right may be derived from a directory role.

Input with the login provider `local`: the user's roles in the users file (<<AUN-AUTH-6>>).

Input with the login provider `oidc`: the `groups` claim (or the claim configured as group source) of the session or
bearer token, read from the
JSON payload of the validated token as the provider wrote it: an array yields its strings, a single string one group,
anything else none, so a group name that contains a comma stays one group; Token Sheriff's planned groups accessor of
the ID token, which keeps such a name whole, replaces this read (ADR-0004). Mapping: `audit-notary.yaml` → `rights`.

[cols="1,3"]
|===
|Action |Permits

|`read`
|Reading documents, index views and diffs of the repository

|`edit`
|Drafts, saves and transitions that are no release

|`approve`
|Releases, with step-up (<<AUN-AUTH-4>>)

|`administer-catalogs`
|Changes of the catalogs; erasure of persons; deletion of expired repositories
|===

A request is permitted only if one of the user's groups maps the action on the target repository. No other source
(directory role, token scope alone) grants a right.

[#AUN-AUTH-3]
== AUN-AUTH-3: Signed Commits and Identity Trailers

* Every commit must be signed by the application; there must be no unsigned commit and no other kind of signature.
* Every commit of a user's save or release, an erasure included, must carry that user's pseudonym, never the `sub`,
  and the issuer, the authentication time and the authentication context in the library's trailers. Checkpoint
  commits, which the library writes without a user's action, carry no identity trailers.

[cols="1,2"]
|===
|Trailer |Source

|`Actor`
|The pseudonym from the person directory, looked up by (`iss`, `sub`)

|`Actor-Issuer`
|`iss`; with local users `web.origin`

|`Auth-Time`
|`auth_time`; with local users as AUN-AUTH-6 states: the time of a step-up's renewed password check, otherwise the
time of the request

|`Auth-Context`
|`acr` and `amr`, in the library's format; with local users `amr=pwd`
|===

[#AUN-AUTH-4]
== AUN-AUTH-4: Step-Up

* `step-up.enabled` must switch step-up on or off for every transition; it defaults to `true` with the login provider
  `oidc` and to `false` with `local`. With `false` no transition may require step-up, whatever its workflow declares,
  and the transition is written with the session's values in the trailers.
* With `step-up.enabled: true` a transition must require step-up exactly when the workflow of its category declares it
  (https://github.com/cuioss/git-document-repository/blob/main/doc/specification/git-forms.adoc#GDR-FORMS-7[GDR-FORMS-7]); the workflows of the shipped categories keep the
  library default: every release requires step-up, and no save and no other transition does.
* With the login provider `oidc`, before a transition that requires step-up the application must check `acr` or `amr`,
  and `auth_time`, against the configured `step-up` values, and re-drive authorization with `acr_values` and `max_age`
  (link:https://www.rfc-editor.org/rfc/rfc9470[RFC 9470]) when they are not met.
* With the login provider `local` step-up is a renewed password check of the same user, sent with the transition
  request, not a second factor (<<AUN-AUTH-6>>); `step-up.amr` is `pwd` and `step-up.acr` is not set.
* The transition must be written only when the session's values pass the check, or when the values of the re-driven
  authorization or the renewed password check pass it; without such values nothing is written. With the login provider
  `local` the session's values never pass: only the renewed password check sent with that request does.
* The re-driven authorization or the renewed password check must be for the same issuer and `sub` as the session that
  requested the transition; for another one nothing is written.
* Through the MCP server a transition that requires step-up must return `STEP_UP_REQUIRED` and write nothing; the
  user completes it in the web app.

Configuration: which transitions require step-up comes from the category's `workflow.yaml`
(xref:architecture-and-modules.adoc#AUN-GEN-1[AUN-GEN-1]); what counts as MFA and its age is `audit-notary.yaml` →
`step-up` (`enabled`, `acr`, `amr`, `max-age`, default `PT5M`), one setting for all categories
(xref:configuration.adoc#_audit_notary_yaml[Configuration]). The library has no switch for all transitions yet: GDR-FORMS-7
decides per transition from the workflow, so `step-up.enabled: false` needs a library setting that turns the check off;
the request is filed with the library
(xref:../concepts/authentication-and-identity.adoc#_open_questions[Authentication and Identity, Open Questions]).

. The request of a transition that requires step-up checks the session's `acr` or `amr` and its `auth_time`.
. Not met: the service result is `STEP_UP_REQUIRED`; nothing is written.
. The REST API returns it with a step-up address, and the web app redirects there. The client re-drives authorization
  with `acr_values` and `max_age` and verifies the returned `acr` or `amr`, as configured, `auth_time`, and that issuer
  and `sub` are those of the session. With local users there is no step-up address: the web app asks for the password and repeats the request with it (<<AUN-AUTH-6>>).
. The transition is written with the values that passed the check in the trailers.

The MCP server offers no tool that completes a release: an agent can only request one with `request_release`, which
returns `RELEASE_REQUESTED`, and a user completes the release in the web app with step-up
(xref:mcp-server.adoc#AUN-MCP-6[MCP Server, AUN-MCP-6]).

[#AUN-AUTH-5]
== AUN-AUTH-5: Git Credential

* The application must reach every Git server only as the technical user configured per repository.
* The application must merge every release itself and push it as the technical user.

Per repository: `credential-ref`, the credential of the technical user, an access token of a bot account used over HTTPS
(https://github.com/cuioss/git-document-repository/blob/main/doc/specification/git-core.adoc#GDR-CORE-2[GDR-CORE-2] admits no SSH remote, so an SSH deploy key is not
usable); there is no other kind of Git credential. A refused push returns `REJECTED` and the draft stays.

Protecting `main` is a duty of the operator, not of the application: the operator configures the Git server so that
only the technical user may push to `main` and nobody may force-push. The application cannot verify this setting.

[#AUN-AUTH-6]
== AUN-AUTH-6: Local Users

WARNING: Local users are for evaluation, development, tests and demonstrations, not for production. They have no
second factor, no protection against guessing, passwords as an unsalted digest, and a login cookie that the server
cannot withdraw. Production uses the identity provider (login provider `oidc`,
xref:../adr/0005-Local_users_from_a_mounted_file_are_for_evaluation_and_testing_only.adoc[ADR-0005]).

Local users follow Quarkus' own mechanisms for this purpose and add as little as possible: the embedded realm of
`quarkus-elytron-security-properties-file`, which Quarkus calls "intended for development and testing purposes"
(link:https://quarkus.io/guides/security-properties[Quarkus, Using security with .properties file]), Quarkus' form
authentication for the web app and its Basic authentication for the MCP server.

With the login provider `local`:

* The login provider must be chosen by `login.provider` in `audit-notary.yaml`, at runtime; there is one build for
  both providers.
* Every start must log one `WARN` record that local users are not meant for production; `--validate-config` must print
  the same warning.
* The login page and the shell of the web app must show a notice that the installation uses local test accounts
  (xref:web-app.adoc#AUN-WEB-9[AUN-WEB-9]: `GET /api/v1/status` names the login provider).
* The users must come only from the users file that `login.local.users-ref` references; a change must take effect
  only at the next start.
* No password, hash or `Authorization` header may be logged.

With the login provider `oidc` no local user may exist: a user of the embedded realm from any source, the environment
included, must stop the boot.

Nothing more is built: no throttling, no lockout, no password rules, no second factor, no change of the own password,
no own password hashing.

=== Configuration at Runtime

Quarkus fixes only the switches of its mechanisms at build time (`ConfigPhase.BUILD_AND_RUN_TIME_FIXED` of
`SecurityUsersConfig` and `VertxHttpBuildTimeConfig` in the Quarkus 3.40.1 source); the users, roles and password
format of the embedded realm are runtime configuration (`MPRealmRuntimeConfig`, `ConfigPhase.RUN_TIME`). The one build
therefore sets in `application.properties`:

[source,properties]
----
quarkus.security.users.embedded.enabled=true
quarkus.http.auth.form.enabled=true
quarkus.http.auth.basic=true
----

With `oidc` the realm stays empty and authenticates nobody. With `local`, the application's `ConfigSourceFactory`
(the documented SmallRye way to derive a config source from other configuration,
link:https://quarkus.io/guides/config-extending-support#config-source-factory[Quarkus, Extending configuration
support, ConfigSourceFactory]) reads the users file of `login.local.users-ref` and offers its entries to Quarkus, as it
offers Token Sheriff's keys derived from `audit-notary.yaml` (xref:configuration.adoc#AUN-CONF-1[AUN-CONF-1]). It also
derives the HTTP permissions that bind Basic to `/mcp` and form authentication to every other protected path
(`quarkus.http.auth.permission.<name>.auth-mechanism`), `quarkus.http.auth.realm=audit-notary` and the key of the login
cookie, both runtime configuration (`AuthRuntimeConfig`, `ConfigPhase.RUN_TIME`).

[source,yaml]
----
login:
  provider: local
  local:
    users-ref: file:/run/secrets/audit-notary/local-users.properties
----

=== The Users File

Quarkus' own keys of the embedded realm, in a properties file mounted like every other secret
(xref:deployment.adoc[Deployment]):

[source,properties]
----
# password: HEX( SHA-512( username ":Quarkus:" password ) ), Quarkus' default algorithm
quarkus.security.users.embedded.users.alice=<128 hex digits>
quarkus.security.users.embedded.roles.alice=isms-editors,isms-approvers
quarkus.security.users.embedded.users.bob=<128 hex digits>
quarkus.security.users.embedded.roles.bob=isms-readers
----

* Only keys under `quarkus.security.users.embedded.` with the runtime names `users.*`, `roles.*`, `algorithm` and
  `plain-text` are accepted; any other key in the file must stop the boot, so the file cannot change other
  configuration.
* The password is Quarkus' default, the hex digest `digest-sha-512` of `username:realm:password` with the realm name
  `Quarkus`; Quarkus' own example computes it as `echo -n "alice:Quarkus:<password>" | sha512sum`
  (`MPRealmRuntimeConfig` in the Quarkus 3.40.1 source). `plain-text=true` is accepted, as Quarkus accepts it, and
  the start warning then says that the passwords are in clear text. There is no command of the application for it.
* The roles are the groups and map to rights through `rights` exactly as identity-provider groups (<<AUN-AUTH-2>>).
* To withdraw a user, the operator removes the user's lines and restarts.

=== Identity and Claims

[cols="1,3"]
|===
|Value |Source with local users

|`iss`
|`web.origin`; the person directory and the trailers name it

|`sub`
|The username

|`auth_time`
|With a step-up, the time of its renewed password check; at the MCP server, the time of the request, whose Basic
credential is checked. Otherwise the time of the request: Quarkus' login cookie records no login time, so with local
users `Auth-Time` without step-up states when the login was last valid, not when the password was checked

|`amr`
|`pwd`, "Password-based authentication"
(link:https://www.rfc-editor.org/rfc/rfc8176#section-2[RFC 8176, §2])

|`acr`
|none

|groups
|The user's `roles` entry in the users file
|===

There is no `name` and no e-mail address: the first login asks for the name (xref:directory.adoc#AUN-DIR-2[AUN-DIR-2]).

=== Web Login, Step-Up and Logout

Quarkus' form authentication keeps the authenticated user in an encrypted cookie, not in a server-side session
(link:https://quarkus.io/guides/security-authentication-mechanisms#form-auth[Quarkus, Authentication mechanisms,
Form-based authentication]). Local users therefore run beside Token Sheriff's planned session layer, not on it
(xref:../adr/0004-Login_and_session_are_designed_against_Token_Sheriffs_planned_session_layer.adoc[ADR-0004] covers the
login provider `oidc` only).

[cols="1,3"]
|===
|Item |Value

|Login page
|The web app's `/login?return=<address>`, with the notice above; the `login` member of a `401` names it
(xref:web-app.adoc#AUN-WEB-9[AUN-WEB-9]). The `return` rule of <<AUN-AUTH-1>> applies; the web app navigates itself

|Login
|Quarkus' `POST /j_security_check` with `j_username` and `j_password` as a form. `login-page`, `landing-page` and
`error-page` of `quarkus.http.auth.form` are empty, so Quarkus answers `200` on success and `401` on failure instead of
redirecting (`FormAuthenticationMechanism` in the Quarkus 3.40.1 source); an unknown user and a wrong password get the
same answer

|Login cookie
|`quarkus-credential`, encrypted with `quarkus.http.auth.session.encryption-key`, which the config source derives from
the secret `login.local.cookie-key-ref`, never from the users file (without it Quarkus uses a temporary key and logs a
warning, so a restart ends every login). On every request Quarkus looks the user up in the realm again
(`ElytronTrustedIdentityProvider` in the Quarkus 3.40.1 source): after a restart a removed user's cookie is refused
and changed roles apply; a changed password leaves existing cookies valid. `http-only-cookie` `true`, `SameSite`
`Strict` (the default), idle timeout `web.session.idle-timeout` (default `PT30M`). There is no absolute lifetime: the
cookie is renewed while it is used

|CSRF
|xref:web-app.adoc#AUN-WEB-8[AUN-WEB-8] applies to every request after the login; with local users the anti-CSRF token
of `GET /api/v1/session` is bound to the login cookie instead of a server-side session. The login request
`POST /j_security_check` cannot carry that token: it is the one exception, and it is refused unless its `Origin`
header is present and is `web.origin`, by a check that runs before Quarkus handles the request

|Mechanism per path
|Form authentication on every protected path except `/mcp`, Basic only on `/mcp`: the config source derives one HTTP
permission per side with `auth-mechanism` `form` or `basic`, so a Basic header elsewhere authenticates nobody. An
integration test must show that Basic credentials work on `/mcp` and authenticate no request to another protected
path

|Step-up
|With `step-up.enabled: true` (<<AUN-AUTH-4>>) the web app asks for the password in a dialog and sends it with the
transition request (`{"password"}` in the body of the release, xref:web-app.adoc#AUN-WEB-6[AUN-WEB-6]); the application
checks it for the user of the login cookie, never one the request names, and writes the transition with a fresh
`auth_time` and `amr` `pwd`. A wrong password is `401 INVALID_CREDENTIALS` and writes nothing

|Logout
|`POST /api/v1/auth/logout` removes the login cookie (Quarkus' `FormAuthenticationMechanism.logout`) and answers
`{"redirect"}` with the start page. The cookie is not withdrawn on the server: a copy stays valid until its idle timeout
|===

=== MCP Server

The MCP server takes HTTP Basic with username and password instead of bearer tokens
(xref:mcp-server.adoc#AUN-MCP-8[MCP Server, AUN-MCP-8]); the local MCP gateway keeps the credential
(xref:../concepts/local-mcp-gateway.adoc#_basic_connections[Local MCP Gateway, Basic Connections]).
