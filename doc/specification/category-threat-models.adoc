The threat-model category as configuration (`categories/threat-models/`). Reasoning:
xref:../concepts/category-threat-models.adoc[Threat Models]. Repository: `threat-models`.

[#AUN-TM-1]
== AUN-TM-1: Place of a Threat Model

* Every threat model must be stored in the central repository `threat-models` as a document of the per-document kind
  `threat-model` in the library's layout (https://github.com/cuioss/git-document-repository/blob/main/doc/specification/git-forms.adoc#GDR-FORMS-3[GDR-FORMS-3]), at
  `models/<ulid>/`, and saved and released like every other document. The service is a field of the document, not a
  part of its path, so a reference needs no service id and a renamed service moves no file.

[#AUN-TM-2]
== AUN-TM-2: Open Format

* A threat model must be stored as one file in an open, published threat-model format.
* Diagrams must be stored as data; images must be generated.

Files of a threat model:

* `models/<ulid>/document.yaml`: `service`, `owner` (`role:`), `state`, `last-review`.
* `models/<ulid>/model.yaml` or `model.json`: the threat model in the chosen format. The kind's schema validates the
  parts the application reads; unknown fields are preserved on write. The serialisation is decided with the format:
  https://github.com/cuioss/git-document-repository/blob/main/doc/specification/git-forms.adoc#GDR-FORMS-3[GDR-FORMS-3] stores structured data as YAML, which OTM allows;
  Threat Dragon JSON needs a JSON file in the layout, which the library does not offer yet. Both are open questions
  of the concept.

The candidate formats are Threat Dragon JSON, the file format OWASP Threat Dragon saves and opens
(link:https://github.com/OWASP/threat-dragon/blob/v2.6.2/td.vue/src/service/save.js[`td.vue/src/service/save.js` of
Threat Dragon v2.6.2]), and Open Threat Model
(link:https://github.com/iriusrisk/OpenThreatModel[OTM on GitHub]); which one is used is an open question of the
concept (xref:../concepts/category-threat-models.adoc#_open_questions[Threat Models, Open Questions]).

[#AUN-TM-3]
== AUN-TM-3: Review Due Date

* A threat model must be due for review one review interval after its last review; the interval must follow the
  highest of the service's effective protection needs.

The intervals are data of the kind, not code: `very-high` `P6M`, `high` `P12M`, `normal` `P24M`, applied to the highest
of the three effective protection needs (confidentiality, integrity, availability) of the service
(xref:directory.adoc#AUN-DIR-5[AUN-DIR-5]) and counted from `last-review`, which a completed review sets. The
deadline rules of https://github.com/cuioss/git-document-repository/blob/main/doc/specification/git-forms.adoc#GDR-FORMS-6[GDR-FORMS-6] cannot express this yet: none
selects a period by a value of a referenced catalog entry or counts from a date field. The rule the library needs is
an open question of
https://github.com/cuioss/git-document-repository/blob/main/doc/concepts/schema-driven-documents.adoc#_open_questions[Schema-Driven Documents, Open Questions].

[#AUN-TM-4]
== AUN-TM-4: Links and Evaluation

* Every threat model must refer to exactly one `service:` entry.
* An accepted or untreated threat must be transferable into an ISMS risk entry.
* The application must show per service: open threats, untreated threats and the age of the model.

Transfer, issues and evaluation:

* "Transfer to risk register" creates a draft risk in `isms-register` with the reference
  `threat-models:threat-model/<ulid>#<threat-id>`.
* A countermeasure records the ids of its issues, entered by the user or the agent.
* Evaluation per service: open threats, untreated threats (without countermeasure and not transferred to the risk
  register), days since `last-review`, review due date.

[#AUN-TM-5]
== AUN-TM-5: Recipes

* The application must guide the filling-in of a threat model by a recipe: an ordered list of steps, each naming the
  part of the model it fills.

A recipe is `categories/threat-models/recipes/<id>.yaml`: `title`, ordered `steps`, each with `title`, `guidance`
(AsciiDoc fragment) and `fills` (JSON Pointer into the model file). The web app renders a recipe as `WizardPage`
(decided provisionally: as a sheet in the last column of the lens, see <<_open_questions,Open Questions>>); the MCP
server exposes recipes through the tool `read_recipe` (xref:mcp-server.adoc#AUN-MCP-6[MCP Server, AUN-MCP-6]).

[#_open_questions]
== Open Questions

Decided provisionally with the Reports lens (UC-TM-4), recorded with the bodies in
xref:rest-api.adoc#_decided_reports[REST API Register, Open Questions]; the owner may change each one:

. *Evaluation* (AUN-TM-4): `GET /api/v1/reports/threat-evaluation` returns one row per threat model with `open`, `untreated`
  and `transferred` threats, `lastReview`, `daysSinceReview`, `reviewDue`, `dueInDays` and a `status` (`ok`, `due-soon`,
  `overdue`, `unreleased`); "due soon" is 30 days. The services of the catalog that are not retired and have no model are
  listed beside it.
. *Untreated* (AUN-TM-4): a threat with the status `open` that has no countermeasure and carries no reference into the risk
  register.
. *Review due date* (AUN-TM-3): counted from the `last-review` of the last released version, with `P6M`, `P12M` or `P24M` by
  the highest effective protection need; a model that was never released has none.

Decided provisionally with the threat models (UC-TM-1, UC-TM-2, UC-TM-4), recorded with the bodies in
xref:rest-api.adoc#_decided_threat_models[REST API Register, Open Questions]; the owner may change each one:

. *Format and layout* (AUN-TM-2): OTM as YAML in `models/<ulid>/model.yaml`, declared by `gdr-split` on the property `model` of
  the kind's schema; `document.yaml` holds `service`, `owner`, `last-review` and `recipe`. The subset the application reads and
  writes is in xref:rest-api.adoc#_threat_model_data[REST API Register, The Data Shape of a Threat Model].
. *Treatment* (AUN-TM-4): the status of a threat (`open`, `mitigated`, `accepted`), the countermeasures with their issue ids and
  the reference of the transfer are `attributes` of the threat and of the mitigation; an untreated threat is open, named by no
  countermeasure and not transferred.
. *Recipes* (AUN-TM-5): a step also has an `id`, the recipe a `description`, and every text may be given per language; the `fills` of a step is a JSON Pointer to an array or an object of the model file's schema. A recipe is read with
  `GET /api/v1/categories/threat-models/recipes` and `…/recipes/{recipe}`.
. *Review date* (AUN-TM-3): `last-review` is set by the act of starting the review (the web app prefills today), the interval
  table is served as `reviewIntervals`.
. *Draft of a new model* (UC-TM-1): the recipe wizard keeps its steps in a draft of a model that does not exist yet, one per
  person, service and recipe, until the last step creates it.

Decided provisionally with the transfer (UC-TM-3), recorded in
xref:rest-api.adoc#_decided_isms[REST API Register, Open Questions]; the owner may change each one:

. *Transfer* (AUN-TM-4): `GET /api/v1/isms/risks/draft?origin=threat-models:threat-model/<id>%23<threat>` prepares a risk (the `#` is
  percent-encoded, otherwise it starts the URL fragment and the server never receives the threat; nothing is stored); the first save of the risk, `POST /api/v1/documents/isms-register` with `origin`, creates it with the reference
  and sets `transferred` on the threat in a second commit. An `accepted` threat is transferable, with or without a
  countermeasure; an `open` threat with a countermeasure, a mitigated threat and a threat that is transferred already are
  refused (`ORIGIN_NOT_TRANSFERABLE`, `ORIGIN_HAS_RISK`).
