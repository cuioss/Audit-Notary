xref:../README.adoc[Audit Notary documentation] » Specification

The register of every request of `/api/v1` that the web app makes or that a requirement names: one table, one row per
request. It is the contract between the web app, the mock server (`web-mock`) and the application: a screen is built
against a row, a mock profile answers a row, and a requirement that fixes a row is linked from it. The shell requests
and the common refusals are fixed in xref:web-app.adoc#AUN-WEB-9[AUN-WEB-9]; the outcomes of the operations are in
xref:architecture-and-modules.adoc#operation-outcomes[Architecture and Modules, Operation Outcomes].

[#_reading_the_register]
== Reading the Register

* *Status* is that of the request, its method, path, body and outcomes:
** `SPECIFIED`: a requirement fixes it; the row links to it.
** `PROVISIONAL`: the specification is silent. The request is the one the web app and the mock use today; it is
decided provisionally so that no screen is blocked, and the owner may change it. A requirement that fixes it later
turns the status into `SPECIFIED` and links it.
* Where only the shape of an answer is open, the *Answer* column marks it "shape PROVISIONAL"; the request stays
`SPECIFIED`.
* *Outcomes* lists those of the request beyond the common refusals below. A refusal names its `outcome` in the JSON
body, and the web app decides by it, never by the status code alone
(xref:web-app.adoc#AUN-WEB-9[AUN-WEB-9]); a `401 INVALID_CREDENTIALS` is therefore no lost session
(see <<_open_questions>>). Statuses are given only where a source fixes them.
* *Login* is required for every request except `GET /api/v1/status`, `GET /api/v1/messages` and the login endpoints.
* Every request that changes state carries the anti-CSRF header (xref:web-app.adoc#AUN-WEB-8[AUN-WEB-8]), except
`POST /j_security_check` of the local login. It is the one row that is no `/api/v1` request; it is in the register
because the web app posts it.
* The pages of the web app outside the shell (`/login`, `/signed-out`, `/login-problem`) are no requests of the API;
<<_addresses_outside_the_shell>> lists them with the requests they make.
* The control routes of the mock (`/mock/*`) are no part of the API.

[#_common_refusals]
== Common Refusals

Every request can end with these outcomes (xref:web-app.adoc#AUN-WEB-9[AUN-WEB-9], Refusals):

[cols="1,1,3"]
|===
|Status |`outcome` |When

|`401`
|`UNAUTHENTICATED`
|No session; the body carries `login`

|`403`
|`CSRF_REJECTED`
|Anti-CSRF header missing or wrong, or a foreign `Origin`

|`403`
|`FORBIDDEN`
|No mapped right (xref:authentication.adoc#AUN-AUTH-2[AUN-AUTH-2])

|`403`
|`FIRST_LOGIN_REQUIRED`
|Outside the first-login allow-list (xref:directory.adoc#AUN-DIR-2[AUN-DIR-2])

|`404`
|`NOT_FOUND`
|The addressed object does not exist, or the user may not read it (PROVISIONAL: xref:data-protection.adoc#AUN-DP-2[AUN-DP-2]
reports a reference into a repository the user may not read as not found; the form kit's requests use the outcome)

|`422`
|`VALIDATION`
|`errors`: a list of `{"pointer", "code"}` with a JSON Pointer into the request body

|`503`
|`GIT_UNAVAILABLE`
|The Git server is unreachable (xref:architecture-and-modules.adoc#AUN-GEN-6[AUN-GEN-6]); a write keeps the draft
|===

              "required": ["what"],

                "what": { "type": "string", "maxLength": 200 },
                "who":  { "type": "string", "x-person": true },
                "due":  { "type": "string", "format": "date" },
                "done": { "type": "boolean" }
              }
            }
          }
        }
      }
    }
  ]
}
----

The schema is the content of the file, unchanged. The labels of this schema are the catalogue's keys
`category.test-note.note.field.title`, `….field.actions.what` and so on
(xref:web-app.adoc#_labels_and_texts[AUN-WEB-4, Labels and Texts]).

*The preview*, `POST /api/v1/render/asciidoc`:

[source,json]

----

and a source above 65,536 bytes answers `413`

[source,json]
----
{ "outcome": "TOO_LARGE", "limit": 65536 }
----

A body without `source`, or with a `source` that is no string, answers `422`
`{"outcome": "VALIDATION", "errors": [{"pointer": "/source", "code": "REQUIRED"}]}` (`TYPE` for a number or an object).

[#_the_step_up_handler]
== The Step-Up Handler

One module of the web app handles every request that can ask for step-up; no view has its own handling
(xref:authentication.adoc#AUN-AUTH-4[AUN-AUTH-4], xref:../use-cases/01-access.adoc#UC-ACC-3[UC-ACC-3]). The whole
section is PROVISIONAL where it says so: the requirements fix the outcomes and the method per login provider, not the
shape of the web app's handling.

*Which requests ask.* A request asks when the workflow of its category declares step-up for the transition, and
`step-up.enabled` is `true`; under the shipped workflows that is every release. The handler serves, as their rows exist:

[cols="2,3,1"]
|===
|Transition |Request |Row

|Release
|`POST /api/v1/releases/{repository}/{id}`
|above

|Any other transition a workflow declares
|`POST /api/v1/documents/{repository}/{id}/transitions/{t}`, and the save
`POST /api/v1/documents/{repository}/{id}/save`
|above

|Completion of a stage (the stage that closes the incident review)
|`POST /api/v1/documents/{repository}/{id}/stages/{stage}/complete` (PROVISIONAL, added with the incident reports)
|with its step

|Save of the configuration
|The request that writes the configuration repository (PROVISIONAL, added with the configuration editor)
|with its step

|Activation of a category
|The request that activates a category (PROVISIONAL, added with the category editor)
|with its step
|===

*The method* comes from `status.stepUp` (see `GET /api/v1/status`), read before the control is pressed:

[cols="1,3"]
|===
|`stepUp` |What the handler does

|`mfa`
|Sends the request. On `403 STEP_UP_REQUIRED` with `stepUp`, the step-up address, the web app leaves for it with the
address of the current view as `return`. It keeps nothing across the redirect (PROVISIONAL), except that a view with
unsaved changes keeps them as its draft before it leaves, and stays where it is, with its own message, when it
cannot keep them: the user comes back to the
view, the session now holds the fresh values, and the act is chosen again, which passes `stepup.check`. Token Sheriff's
planned pending action (SESSION-8) would complete the act itself; the handler is to be replaced by it. A step-up that
was cancelled or failed at the provider, or was met by another user, comes back without fresh values, and the same
request answers `STEP_UP_REQUIRED` again; the handler has no page for it

|`password`
|Asks first, in a dialog titled "Confirm your identity", and sends the password as the member `password` of the JSON
body of the request (PROVISIONAL generalisation: the release's `{"password"}` is the body member of any request that
can ask; the other members stay). `401 INVALID_CREDENTIALS` keeps the dialog open with the error and writes nothing; any
other answer closes the dialog and is the view's. The password is never kept, logged or shown

|`off`
|Sends the request; there is no dialog and no line in the margin
|===

*Where it lives in the web app.* `src/lib/stepup/stepUp.ts` (`StepUpHandler`: `run(request)` answers `done`, `refused` with
the view's own refusal, or `handled`) and `StepUpDialog.svelte` (the dialog and the notice). The release, the submit
for review (`transition`) and the save for everyone of a SAMM practice send through it; `POST
/api/v1/documents/{repository}/{id}/transitions/{t}` and `.../save` carry the member `password` like the release. The
rows of stage completion, configuration save and category activation use it when their steps add them.

*The line in the margin* ("You confirm your identity once more before the release.") is shown whenever `stepUp` is not
`off` and the control asks; the control itself names the domain act only
(xref:web-app.adoc#AUN-WEB-6[AUN-WEB-6]).

*The outcomes the handler owns:*

[cols="1,1,3"]
|===
|Status |`outcome` |Handling

|`403` (PROVISIONAL)
|`STEP_UP_REQUIRED`
|As above. With `stepUp: "password"` the status has already told the web app to ask; a server that answers it without
an address is answered by opening the dialog

|`401`
|`INVALID_CREDENTIALS`
|A wrong password; not a lost session: the client decides a `401` by its `outcome` first and leaves for the login only
for `UNAUTHENTICATED` (decided provisionally, see <<_open_questions>>)

|`503` (PROVISIONAL status)
|`TOO_MANY_LOGINS`
|Every place of pending logins is taken, so no step-up can start; nothing is written, `Retry-After: 60`. The view shows
a notice that many people are logging in and the act can be tried again in a minute; the draft and the view stay
as they were

|`401`
|`UNAUTHENTICATED`
|The session ended meanwhile; the normal path to the login, back to the same address; a logout always wins over a
step-up still running
|===

The outcomes after the fresh values passed are those of the transition, and they are the view's, not the handler's:
`CHANGED_SINCE_REVIEW` when the document was saved meanwhile, `FORBIDDEN` when the right was withdrawn,
`MANDATORY_FIELDS_MISSING`, `REJECTED`. Nothing is written for any of them
(xref:../use-cases/01-access.adoc#UC-ACC-3[UC-ACC-3], `stepup.recheck`).

[#_a_session_without_rights]
== A Session Without Rights

A user whom no group maps to a right is logged in; the session answers `"rights": []` and `firstLoginRequired` as
usual (xref:../use-cases/01-access.adoc#UC-ACC-1[UC-ACC-1]). Every request that acts on a repository is refused
`403 FORBIDDEN`, the lists of the lenses included (the shell cannot read a list it has no right to). The shell's own
requests work: status, messages, session, events, logout, and with the default person directory the first login. The
Due list is not a request on a repository: it answers `{"items": []}` (PROVISIONAL: nothing is due for a user without
rights). The web app decides by `rights` being empty and `firstLoginRequired` being `false`: it shows a notice that the
organisation has granted no access yet, and the empty state in place of every list, and it never asks the user for
another login.

[#_a_session_that_is_replaced]
== A Session That Is Replaced

A new login in the same browser ends the session that browser held; the tabs of the old session carry the new session's
cookie with their next request (xref:../use-cases/01-access.adoc#UC-ACC-6[UC-ACC-6]). What the web app does:

. The event stream of the old session closes (<<_requests>>, `GET /api/v1/events`).
. The tab reads `GET /api/v1/session`. `401 UNAUTHENTICATED` is the normal path to the login. A `200` with the same
`csrfToken` the tab started with is a transient break: the tab opens the stream again. A `200` with another
`csrfToken` is another session: the tab reloads at its own address, so no tab goes on showing the state of the
replaced session. The token is the identity of the session in the contract (PROVISIONAL): the session view has no
session id, and the cookie is `HttpOnly`.
. A state-changing request of the old tab, sent before it noticed, carries the old token and answers `403 CSRF_REJECTED`;
the client reads the session again, as it already does.

[#_addresses_outside_the_shell]
== Addresses Outside the Shell

Three addresses of the web app are shown without the shell (no navigation rail, no session): `/login`, `/signed-out`
and `/login-problem`. They are listed in `canonical-addresses.json` under `outsideShell`, not under `addresses`, so that
the web app routes them but the check of a login's `return` (AUN-AUTH-1) never accepts them: a login never returns to
the page that started it. They read the status and the message catalogue, nothing else, and keep the notice of local
test accounts when `status.loginProvider` is `local`. All of this is PROVISIONAL except what AUN-AUTH-6 fixes
(`/login?return=<address>` with local users).

[cols="2,4,3"]
|===
|Address |Content |Requests

|`/login?return=<address>`
|With `local`: a form with username and password and the notice of local test accounts. The `return` is checked
against the canonical addresses on the client too (`/` when it fails). With `oidc` the page is not shown: it starts the
login by navigating to `/api/v1/auth/login?return=<address>` (PROVISIONAL)
|`POST /j_security_check`: `200` navigates to the checked `return`; `401` shows "The username or the password is wrong."
and keeps the form; the password field is cleared

|`/signed-out`
|"You are signed out." and one action, "Log in", which starts the login with `return=/`. No session is needed and none
is created by opening the page
|none

|`/login-problem?reason=<reason>`
|The reasons `idp-unavailable` (the login service of the organisation cannot be reached), `too-many-logins` (many
people are logging in; try again in a minute) and `unknown-transaction` (the login took too long or was interrupted).
Another or no `reason` is shown as the general failure. One action: "Try again", which starts the login with `return=/`
|none
|===

[#_notes]
== Notes

* *The assessment is a document.* The SAMM views read and write an assessment through the generic document requests;
only the scope list, the scope, the model and the comparison are SAMM-specific.
* *The release names no reviewed revision yet.* `CHANGED_SINCE_REVIEW` is therefore answered by the state of the
server, not by a comparison with the revision the approver saw. A request that carries the reviewed revision would
make the check exact.
* *Status codes.* The register states a status only where a requirement fixes it. A view never decides by it alone.
* *Local users and the shell.* `status.loginProvider` is the only place the shell learns the provider from: the
`login` member of a `401` is `/login` with `local` and `/api/v1/auth/login` with `oidc`, and the logout lands on
`/signed-out` in both.

[#_open_questions]
== Open Questions

* *The step-up address.* The requirement names "a step-up address" without its format; the client keeps it opaque.
* *`status.stepUp`.* The shell needs to know the method of the confirmation before the release is pressed; whether the
member stays in `GET /api/v1/status` or moves into the session is open.

*Decided provisionally* with the access use cases (UC-ACC-1, -2, -3, -6, -7), so that no screen is blocked; the owner
may change each one:

. *`401 INVALID_CREDENTIALS` and the client.* AUN-WEB-9 answers a wrong step-up password with `401`; the specification
keeps it. The `ApiClient` decides a `401` by its `outcome` first and leaves for the login only for `UNAUTHENTICATED`;
the mock answers `401`, as the specification says (it answered `403` before). Replaces the earlier open question.
. *`status.loginProvider` absent* reads as `oidc`; *`status.stepUp` absent* reads as `mfa` with `oidc` and `off` with
`local`.
. *Login refusals for a browser.* A navigation (`Accept` contains `text/html`) to the login start or the callback is
answered with a `303` to `/login-problem?reason=` instead of raw JSON; the JSON, the statuses and `Retry-After` stay for
every other client. The outcome `UNKNOWN_TRANSACTION` (`400`) is new. The server's own error page for the callback
stays until the web app page exists, and goes away with the bootstrap login (ADR-0004).
. *`/signed-out` as the landing of a logout*, in place of "the start page" of AUN-AUTH-1 and AUN-AUTH-6. With the
identity provider the post-logout redirect address `/signed-out` must be registered at the provider, which is a duty
of the operator.
. *`/login` with `oidc`* starts the provider login at once; the page exists for `local` only in substance.
. *The identity of a session* in the browser is its `csrfToken`: there is no session id member, and no member would
be safe in a cookie-less answer.
. *The event stream* belongs to its session and closes with it (use case change `change-events`), and a closed stream
makes the tab read the session again.
. *The step-up carries no pending action across the redirect;* the user chooses the act again after the return. The
member `password` of the body generalises the release's `{"password"}` to every request that can ask.
. *`STEP_UP_REQUIRED` is `403`; `TOO_MANY_LOGINS` of a step-up is `503` with `Retry-After: 60`,* the status of the
login start.
. *A session without rights* gets an empty Due list and `FORBIDDEN` for every repository request; the shell decides by
`rights` being empty.
. *The refusal of `POST /j_security_check` for a foreign `Origin`* answers `403` with `CSRF_REJECTED`.

. *The pages outside the shell read the status and the texts only,* never the session; opening one neither needs nor
creates a session. A page moved into the shell without a page load reloads the tab so that the shell starts properly.
. *The local login posts by `fetch`,* not by a native form post: the page decides by `200` or `401` itself, and then
leaves by a full page load at the checked `return`. The dev server proxies `/j_security_check` to the mock.
. *The wrong-password text is general:* "The password is not right. Nothing was changed." serves every request that
asks, in place of the release's "Nothing was released."
. *A session without rights* shows both the notice and the empty state in place of every view on a repository, except
the first-login form and the settings; the empty view makes no request that the server would refuse.
. *Only a stream that had connected* makes the tab read the session again when it ends; a stream that never connected
is the ordinary retry.
. *The mascot* stands on `/signed-out` only; the login page, the login problem and the empty state without access show
none.

For the owner: whether `/signed-out` replaces the start page (4), whether `/login` should exist for `oidc` (5), and
whether the session needs an explicit identity member instead of the token (6).

[#_decided_forms]
*Decided provisionally* with the form kit (`SchemaForm` and its components), so that no screen is blocked; the owner may
change each one. The reasoning is in xref:web-app.adoc#AUN-WEB-4[AUN-WEB-4]:

. *One request for the schema of a category,* `GET /api/v1/categories/{category}/schema`, answering every document type
of the category with its repository alias and its schema file unchanged. A category with several document types
(ISMS, incident reports) is thus read once, and the request needs no query.
. *The texts of a field are catalogue keys,* `category.<category>.<kind>.field.<path>` with `.help` and
`.option.<value>`; the schema's `title` and `description` are not shown. Without a key the form shows the property name.
. *The component is chosen by an ordered rule list* (AUN-WEB-4, Choosing the Component). The additions to the
specified constructs are `format: date`, numbers, arrays of scalars (a `DataTable` of one column), sections of objects,
`format: gdr-link` without `x-catalog` as `DocumentRefField`, `x-free-text` as a text area, and `readOnly`. A
construct the form does not know is shown as plain data and kept unchanged.
. *The browser validates without Ajv,* with a hand-written check of the constraints its components can offer; the
requirement's earlier text named Ajv. No dependency is added.
. *A format error of the browser never stops a save.* The library's validator asserts no `format`
(https://github.com/cuioss/git-document-repository/blob/main/doc/specification/git-forms.adoc#GDR-FORMS-2[GDR-FORMS-2]),
so the browser's check is advice; the errors of the server replace the browser's.
. *A mandatory field is no error before a transition.* The browser lists the empty `required` fields for the transition
that needs them; the server's `MANDATORY_FIELDS_MISSING` decides.
. *The codes of a field error* are the capitalised keyword of the failing constraint, plus `REFERENCE_NOT_FOUND`
(specified) and `PSEUDONYM_UNKNOWN`; the text is the catalogue key `form.error.<code>`, with `form.error.invalid` for
another code.
. *The picker lists are whole lists:* `GET /api/v1/catalogs/{catalog}` carries `retired`, and
`GET /api/v1/directory/persons` is capped at 100 with `truncated`; the client filters locally as well, so a server that
ignores `q` works. A single pseudonym resolves with `GET /api/v1/directory/persons/{pseudonym}` to `bound`, `unbound`
or `former`.
. *`GET /api/v1/references/resolve`* resolves document and catalog references to a title and a canonical address, so
that a read view links them; it is no picker. A picker for documents waits for the document list of the document
lifecycle.
. *The preview is rendered only by the server,* in safe mode `secure`, sanitised against one allow-list, at most 65,536
bytes. The web app builds its elements from the parsed answer with the same allow-list, so no view needs `{@html}`.
. *`NOT_FOUND` is a common refusal* (`404`), for an object that does not exist and for one the user may not read.
. *The pointers of the form are those of its own value.* How the pointers of a save's answer, which name the request
body, map onto them is decided with the save of generic documents.

For the owner: whether the server renders the preview with a sanitiser that needs a dependency (the application's
implementation, not this register), whether the browser's `format` advice should stop a save, and whether the category
schema should carry the field labels instead of the catalogue.
