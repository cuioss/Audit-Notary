The register of every request of `/api/v1` that the web app makes or that a requirement names: one table, one row per
request. It is the contract between the web app, the mock server (`web-mock`) and the application: a screen is built
against a row, a mock profile answers a row, and a requirement that fixes a row is linked from it. The shell requests
and the common refusals are fixed in xref:web-app.adoc#AUN-WEB-9[AUN-WEB-9]; the outcomes of the operations are in
xref:architecture-and-modules.adoc#operation-outcomes[Architecture and Modules, Operation Outcomes].

[#_reading_the_register]
== Reading the Register

* *Status* is that of the request, its method, path, body and outcomes:
** `SPECIFIED`: a requirement fixes it; the row links to it.
** `PROVISIONAL`: the specification is silent. The request is the one the web app and the mock use today; it is
decided provisionally so that no screen is blocked, and the owner may change it. A requirement that fixes it later
turns the status into `SPECIFIED` and links it.
* Where only the shape of an answer is open, the *Answer* column marks it "shape PROVISIONAL"; the request stays
`SPECIFIED`.
* *Outcomes* lists those of the request beyond the common refusals below. A refusal names its `outcome` in the JSON
body, and the web app decides by it, never by the status code alone
(xref:web-app.adoc#AUN-WEB-9[AUN-WEB-9]); a `401 INVALID_CREDENTIALS` is therefore no lost session
(see <<_open_questions>>). Statuses are given only where a source fixes them.
* *Login* is required for every request except `GET /api/v1/status`, `GET /api/v1/messages` and the login endpoints.
* Every request that changes state carries the anti-CSRF header (xref:web-app.adoc#AUN-WEB-8[AUN-WEB-8]), except
`POST /j_security_check` of the local login. It is the one row that is no `/api/v1` request; it is in the register
because the web app posts it.
* The pages of the web app outside the shell (`/login`, `/signed-out`, `/login-problem`) are no requests of the API;
<<_addresses_outside_the_shell>> lists them with the requests they make.
* The control routes of the mock (`/mock/*`) are no part of the API.

[#_common_refusals]
== Common Refusals

Every request can end with these outcomes (xref:web-app.adoc#AUN-WEB-9[AUN-WEB-9], Refusals):

[cols="1,1,3"]
|===
|Status |`outcome` |When

|`401`
|`UNAUTHENTICATED`
|No session; the body carries `login`

|`403`
|`CSRF_REJECTED`
|Anti-CSRF header missing or wrong, or a foreign `Origin`

|`403`
|`FORBIDDEN`
|No mapped right (xref:authentication.adoc#AUN-AUTH-2[AUN-AUTH-2])

|`403`
|`FIRST_LOGIN_REQUIRED`
|Outside the first-login allow-list (xref:directory.adoc#AUN-DIR-2[AUN-DIR-2])

|`404`
|`NOT_FOUND`
|The addressed object does not exist, or the user may not read it (PROVISIONAL: xref:data-protection.adoc#AUN-DP-2[AUN-DP-2]
reports a reference into a repository the user may not read as not found; the form kit's requests use the outcome)

|`422`
|`VALIDATION`
|`errors`: a list of `{"pointer", "code"}` with a JSON Pointer into the request body; for a request without a body
(PROVISIONAL), a JSON Pointer into its query parameters read as one object, a parameter name to its value (`/q`), or to
the array of its values when it is repeated (`/ref`; an element is `/ref/3`)

|`503`
|`GIT_UNAVAILABLE`
|The Git server is unreachable (xref:architecture-and-modules.adoc#AUN-GEN-6[AUN-GEN-6]); a write keeps the draft
|===

[#_the_document_lifecycle]
== The Document Lifecycle

The requests of this section serve the use cases UC-DOC-1, -2, -3, -4, -6, -7, -8 and -9
(xref:../use-cases/02-documents.adoc[Use Cases: Documents]). Everything here is PROVISIONAL where the rows say so; the
exact bodies are in <<_document_lifecycle_requests>>, the decisions in <<_decided_lifecycle>>.

*The workflow of `test-note`.* The test category `test-note` has one document type, `note` (repository `test-notes`,
collection `notes`), released more than once. States `draft`, `in-review`, `released`; the transition
`test-note.submit` (`draft` to `in-review`, right `edit`, no step-up) and the release `test-note.release`
(`in-review` to `released`, right `approve`, step-up; the tag is `notes/<id>/v<n>`). A save is possible in every state.
The first save after a release starts the next version: the document is `draft` again, `version` is one higher and
`release` still names the last release, which the diff compares with. A document type released once (a SAMM
assessment) answers `DOCUMENT_RELEASED` instead and reads `frozen: true`.

*Versions.* `version` is the number of the working state of the document: `1` until the first release, `n+1` after the
release `v<n>` and the first save that follows. A released document has `version` equal to the number of its last
release.

*Single-file document types* have one part, named `data`; its `value` is the document's data, the value the form edits
(xref:web-app.adoc#_values[AUN-WEB-4, Values]).

*Reading while the Git server is unreachable.* Lists, reads, revisions and the search are served from the last fetched
state and answer `200`; `status.degraded` says that they may be old. Writes answer `503 GIT_UNAVAILABLE`, except the
draft, which stays in the application and is written.

change `change-web-3`).

|Route id |Address |Shows

|`categories`

|The generic categories (`GET /api/v1/categories`), one column; with one category the lens opens it

`{category}` is a category id, a segment as in the other addresses. `{document}` is a document id, a ULID: it needs its
own placeholder pattern `document`, `[0-9A-Za-z][0-9A-Za-z._-]{0,127}`, because the default pattern of a segment is
lower case and a ULID is upper case. The segments `new` and `edit` (the editor of step 10) are reserved: their routes
come before `categories.document` in the file, and no document has such an id. The address names the category and the
document, never the repository: the web app finds the document among the repositories of the category's document types
(`GET /api/v1/categories` names them) and reads `404 NOT_FOUND` as an address that does not exist. An address under
`/categories/{category}` of a category that is not `generic` shows the not-found view, and so does one of a custom
category that is not switched on and holds no documents. A custom category that is switched off but still holds
documents is listed with `"enabled": false` (the member is absent for a category that is on): its generic addresses stay
readable, because the references to its documents and the search results resolve through them
(xref:../use-cases/09-categories.adoc[UC-KND-5], _Switched off with documents_), but they are read-only: the document
sheet and the revisions offer no save, no workflow act and no release, `new` shows the not-found view, and neither the
rail entry nor the lens counts the category. The writes answer `403 FORBIDDEN`. PROVISIONAL, see
<<_open_questions>>. The delivered categories keep their own addresses.

[#_allowed_queries]
=== Allowed Queries of an Address

Until now an address was a path. An address gains an *allowed query set*: a few named parameters that belong to the
view and are part of its canonical form. `canonical-addresses.json` has two additions (data; the excerpt shows them as they are in the
file):

[source,json]
----
{
  "params":  { "year": "[0-9]{4}", "document": "[0-9A-Za-z][0-9A-Za-z._-]{0,127}" },
  "queries": { "at": "(v[0-9]{1,4}|[0-9a-f]{7,40})", "kind": "[a-z0-9][a-z0-9-]{0,63}" },
  "addresses": [
    { "route": "categories",          "pattern": "/categories" },
    { "route": "categories.category", "pattern": "/categories/{category}" },
    { "route": "categories.new",      "pattern": "/categories/{category}/new", "query": ["kind"] },
    { "route": "categories.document", "pattern": "/categories/{category}/{document}", "query": ["at"] },
    { "route": "categories.release",  "pattern": "/categories/{category}/{document}/release" }
  ]
}
----

(`queries` is a new top-level member like `params`: name to value pattern; `query` is a new optional member of an
address: the names it admits, in the order they are written. The addresses are inserted in file order: `categories.new`
before `categories.document`.) The rules:

* A path is matched first, as today. The query string is read as `name=value` pairs split at `&`, each percent-decoded
  once; a `+` stays a plus.
* *Reading an address* (`parseAddress(pathname, search)`): a name the address does not admit is ignored, so a tracking
  parameter breaks no link; a name it admits whose value does not match the pattern of `queries`, or that appears twice,
  makes the address not found (`null`). The address carries its admitted parameters as `query`.
* *Writing an address* (`formatAddress`): the admitted names that have a value, in the order of the file, each value
  checked against its pattern; nothing else is written.
* *The `return` of a login* (`checkReturn`, AUN-AUTH-1) takes path and query: the path must be a canonical address,
  and every name must be one that address admits, with a matching value, each once; anything else, a fragment included,
  falls back to `/`. Without this, the step-up of a view that shows `?at=v1` would return to the start page.
* The query string is at most 256 characters; the path stays without query in the routes of the mock
  (`CanonicalAddresses.isCanonical(path)`).
* `?at=` is allowed on `categories.document` only; later steps add it to the address of the other lenses and add
  `as-of` for the reports, each with its own pattern.

What the code does for it (built by the mock and UI steps, not by this contract):

[cols="2,3"]
|===
|File |Change

|`web-app/src/main/resources/META-INF/audit-notary/canonical-addresses.json`
|The two members above and the five addresses

|`web-app/src/lib/routes.ts`
|`CanonicalFile` gains `queries` and `query`; `compileAddresses` keeps each address's admitted names and value
patterns; `Address` gains `query?: Record<string, string>`; `parseAddress(pathname, search = '')` reads it; `formatAddress`
writes it; `checkReturn` splits the candidate at the first `?` and checks both parts; `Lens` and `LENSES` gain
`categories` (rail order: after `isms`), `routeTitleKey` gives `lens.categories`

|`web-mock/.../runtime/CanonicalAddresses.java`
|`of(JsonNode)` reads `queries` and `query`; `isCanonical(path)` stays; `checkReturn(candidate)` splits at the first
`?` and applies the rules above; the mock's login keeps redirecting to the checked `return` with its query
|===

[#_release_requests]
=== Release Requests

An agent's `request_release` (UC-DOC-8) has no web request: the web app only shows what it left. PROVISIONAL, because
the storage in Git is open (xref:../concepts/mcp-server.adoc#_open_questions[MCP Server, Open Questions]):

* The request is an item of `GET /api/v1/due` for the requesting user, `kind` `release`, with `requestId`,
  `requestedBy`, `requestedAt` and `comment`. Its `address` follows the state of the document: the document's address
  while it is in its first state (the user submits it there), the release address once it is in review.
* An approver sees the document in review as `kind` `review`; the item carries the same four members when a request
  exists, so that the comment is read before the release (decided provisionally: a pending request is shown to the
  approvers too).
* The document read carries `releaseRequest` (`null` without a request), so that the sheet and the review show the
  comment and who asked.
* The request ends with the release of the document; a document edited further keeps it. A release request carries no
  reviewed revision: see the open question in <<_open_questions>>.

|The entries of the catalog (`GET /api/v1/catalogs/{catalog}`), retired ones marked; the action *New* with the right
`administer-catalogs`. An unknown catalog is the not-found view

|`catalogs.new`
|`/catalogs/{catalog}/new`
|The form of a new entry in the catalog's schema; nothing is stored before the save (`POST`), then the page moves to

`catalogs.entry` in the file

|`catalogs.entry`
|`/catalogs/{catalog}/{id}`

|`catalogs.import`
|`/directory/import`

|`catalogs.persons`
|`/directory/persons`

There is no address `/directory` itself: it is the not-found view. The addresses admit no query.

{
  "catalog": "service", "id": "payment-api", "name": "Payment API", "retired": false,
  "value": {
    "id": "payment-api", "name": "Payment API", "description": "Payment processing for the web shop",

  },
  "effective": {
    "protectionNeeds": { "confidentiality": "very-high", "integrity": "very-high", "availability": "high" },
    "decidedBy": { "confidentiality": "service:customer-db", "integrity": "service:identity-provider",
                   "availability": "service:payment-api" },
    "dependencies": [
      { "ref": "external:psp-provider", "name": "Payment service provider", "depth": 1, "via": "service:payment-api",
        "retired": false, "counts": false, "protectionNeeds": null },
      { "ref": "service:customer-db", "name": "Customer database", "depth": 1, "via": "service:payment-api",
        "retired": false, "counts": true,
        "protectionNeeds": { "confidentiality": "very-high", "integrity": "high", "availability": "normal" } },
      { "ref": "service:identity-provider", "name": "Identity Provider", "depth": 1, "via": "service:payment-api",
        "retired": false, "counts": true,
        "protectionNeeds": { "confidentiality": "very-high", "integrity": "very-high", "availability": "high" } },
      { "ref": "external:cloud-hosting", "name": "Cloud hosting", "depth": 2, "via": "service:customer-db",
        "retired": false, "counts": false, "protectionNeeds": null }
    ],
    "cycle": null
  },
  "at": "2026-10-02T09:12:00Z",
  "history": [
    { "kind": "save", "at": "2026-10-02T09:12:00Z", "by": { "pseudonym": "p-7d2e58", "name": "Noor Haddad" } },
    { "kind": "create", "at": "2026-02-11T13:40:00Z", "by": { "pseudonym": "p-7d2e58", "name": "Noor Haddad" } }
  ]
}
----

The rules of `effective` (AUN-DIR-5; each one is also decided in <<_decided_directory>>, point 8):

* `protectionNeeds` is, per dimension, the highest value over the service itself and every dependency that counts; the
  order is `normal`, `high`, `very-high`.
* `dependencies` lists every service and external party reachable through `dependsOn`, transitively, each once, in
  breadth-first order (depth 1 first, within a depth by `ref`); `via` is the `ref` it was first reached from. A
  dependency `counts` when it is a service that is not retired and whose protection needs are known; an external party
  has none (`protectionNeeds` `null`), and a retired service is listed with the mark and does not count.
* `decidedBy` names, per dimension, the first of the service itself and then `dependencies` that counts and holds the
  highest value; the service itself is `service:<own id>`.
* `cycle` is `null`, or the `refs` of the services on a cycle in `dependsOn` that the service is on or reaches, in
  the order they depend on each other: `["service:reporting", "service:report-scheduler"]`. A cycle is a notice and
  never a refusal: the maximum is taken over every service reached once.
* For a catalog other than `service` `effective` is `null`.

Saving a service answers `{"outcome": "SAVED", "catalog": "service", "id": "payment-api", "at": "…"}`; the sheet reads the
entry again, which carries the new `effective`. A refusal is `422`:

[source,json]
----
{ "outcome": "VALIDATION", "errors": [
    { "pointer": "/owner/team", "code": "REFERENCE_NOT_FOUND" },
    { "pointer": "/dependsOn/1", "code": "REFERENCE_NOT_FOUND" },
    { "pointer": "/name", "code": "REQUIRED" } ] }
----

The pointers are into `value`, the form's own value. Creating answers `201`
`{"outcome": "CREATED", "catalog": "service", "id": "notification-gateway", "address":
"/catalogs/service/notification-gateway", "at": "…"}`, and `409 {"outcome": "ID_TAKEN"}` for an id that exists, retired
or not. Retiring answers `200 {"outcome": "RETIRED", "catalog", "id", "at"}`; a change of a retired entry answers
`409 {"outcome": "RETIRED"}` and writes nothing.

[#_backstage_import]
=== The Backstage Import

The wizard reads the files the person chooses in the browser and sends their text; the application fetches nothing
from Backstage (AUN-DIR-6). The request, preview or import:

[source,json]
----
{ "documents": [
    { "name": "catalog-info.yaml", "content": "apiVersion: backstage.io/v1alpha1\nkind: Component\n…" } ] }
----

The answer of the preview (`PREVIEW`) and of the import (`IMPORTED`) has one shape:

[source,json]
----
{
  "outcome": "IMPORTED",
  "created": [
    { "catalog": "service", "id": "checkout-ui", "name": "Checkout UI" },
    { "catalog": "system", "id": "storefront", "name": "Storefront" },
    { "catalog": "team", "id": "storefront", "name": "Storefront" }
  ],
  "updated": [
    { "catalog": "service", "id": "payment-api", "name": "Payment API", "changed": ["lifecycle", "owner.team", "dependsOn"] },
    { "catalog": "team", "id": "payments", "name": "Payments", "changed": ["parent"] }
  ],
  "unchanged": 4,
  "leftOut": [
    { "entity": "component:default/billing-batch", "field": "spec.lifecycle", "reason": "LIFECYCLE_UNMAPPED", "detail": "experimental" },
    { "entity": "component:default/search-index", "field": null, "reason": "DEFAULTS_MISSING", "detail": "owner.role, protection-needs" },
    { "entity": "component:ops/legacy-export", "field": null, "reason": "NAMESPACE_NOT_DEFAULT", "detail": "ops" },
    { "entity": "component:default/payment-api", "field": "spec.dependsOn[2]", "reason": "REFERENCE_KIND_NOT_SUPPORTED", "detail": "resource:default/payments-db" },
    { "entity": "api:default/payments-openapi", "field": null, "reason": "KIND_NOT_SUPPORTED", "detail": "API" }
  ]
}
----

* `created` and `updated` name the catalog entries; `changed` lists the fields of `value` an update changed, as dotted
  paths. `unchanged` is the number of entries the descriptors matched without a difference.
* A `leftOut` item names the Backstage entity as its entity reference (`kind:namespace/name`, written in lower case as senders should,
  link:https://backstage.io/docs/features/software-catalog/references[Backstage: Entity References]), the `field` of
  the descriptor, or `null` for the entity as a whole, the `reason` and a `detail`. The reasons are the ones AUN-DIR-6
  names: `NAMESPACE_NOT_DEFAULT`, `REFERENCE_KIND_NOT_SUPPORTED` (the entity is imported, the reference left out),
  `LIFECYCLE_UNMAPPED` (an existing service keeps its value, a new one is not created), `DEFAULTS_MISSING` (a new
  service without `directory.backstage.defaults` for `owner.role` and `protection-needs` is not created), and
  `KIND_NOT_SUPPORTED` for a kind other than `Component`, `System` and `Group`. The text of a reason is the catalogue key
  `import.reason.<reason in lower case, with hyphens>`.
* A repeated import answers the same shape with `created` empty: it updates, never duplicates, never deletes.
* A `422 VALIDATION` names the document by position: `{"pointer": "/documents/0/content", "code": "FORMAT"}`. Nothing is
  written then. A body above the limits answers `413 {"outcome": "TOO_LARGE", "limit": 2097152}`.

[#_own_entry_and_binding]
=== The Own Entry, the Confirmation and the Binding

`GET /api/v1/directory/me` of a user with an entry:

[source,json]
----
{ "name": "Alex Example", "teams": ["payments"], "informationText": "…",
  "entry": { "pseudonym": "p-4c1a9e", "name": "Alex Example",
             "memberships": [ { "team": "team:payments", "role": "role:security-champion" } ],
             "confirmedAt": "2026-01-14", "confirmationDue": false } }
----

`PUT /api/v1/directory/me` with `{"name": "Alex Example", "memberships": [{"team": "team:payments", "role":
"role:developer"}]}` answers `200 {"outcome": "SAVED", "pseudonym": "p-4c1a9e", "confirmedAt": "2026-11-26"}`.
`POST /api/v1/directory/me/confirmation` answers `200 {"outcome": "CONFIRMED", "confirmedAt": "2026-11-26"}`. Neither
needs step-up.

The first login with candidates (UC-ACC-4): `PUT /api/v1/directory/me` with `{"name": "Robin Newcomer", "team":
"payments", "role": "developer"}` and no `binding`, from a user who has a mapped right and whose membership a prefilled
entry holds, saves nothing and answers `409`:

[source,json]
----
{ "outcome": "BINDING_CANDIDATES", "candidates": [
    { "pseudonym": "p-3d7a15", "name": "Robin Newcomer",
      "memberships": [ { "team": "team:payments", "role": "role:developer" } ] },
    { "pseudonym": "p-8e2b40", "name": "Rowan Newman",
      "memberships": [ { "team": "team:payments", "role": "role:developer" } ] } ] }
----

The repeated request carries `"binding": "p-3d7a15"` (bind) or `"binding": "new"` (a new entry) and answers
`200 {"outcome": "SAVED", "pseudonym": "p-3d7a15"}`; `"binding": "p-0b0b0b"`, a pseudonym that is no candidate, answers
`409 {"outcome": "NOT_BINDABLE"}` and the form shows the candidates again. A user without a mapped right never gets
`BINDING_CANDIDATES`.

*The reconfirmation.* `GET /api/v1/session` carries `directoryConfirmationDue: true` while the own entry's confirmation is
older than the interval. The shell then shows a notice on every view with a link to `/settings/profile`, which asks "Is
this still right?" with the acts "Yes, this is right" (`POST …/confirmation`) and *Save* (a changed entry, which
confirms as well); the web app reads the session again after either, and the notice goes. The notice is no gate: nothing
else is blocked (<<_decided_directory>>, point 13).

*The event.* `catalog-changed` `{"catalog", "id", "by"}` on `GET /api/v1/events` tells an open catalog list or entry
sheet that someone saved, created or retired an entry; the web app reads the list and the entry again (PROVISIONAL).

== SAMM Requests

The requests of the use cases UC-SAMM-1 to UC-SAMM-5 beyond the ones of the first SAMM lens
(xref:../use-cases/04-samm.adoc[Use Cases: OWASP SAMM Assessments]). The rows are in <<_requests>>, *SAMM*; this section
fixes their bodies and the addresses of the new views. Every body is PROVISIONAL unless a row says otherwise; the
decisions are in <<_decided_samm>>. The values are those of the mock: the scopes `payments`, `identity`, `shop` and

`im`, `em`, `om`) and today, 2026-11-26.

=== The Addresses

The lens *SAMM* has `/samm`, `/samm/{scope}`, `/samm/{scope}/{assessment}`, `/samm/{scope}/{assessment}/release` and
`/samm/{scope}/{assessment}/{practice}`. The step adds two addresses to `canonical-addresses.json`, each before the
address whose placeholder it would otherwise be read as:

[cols="2,3,3"]
|===
|Route id |Address |Shows

|`samm.new`
|`/samm/new`
|The form of a new scope: title, subject (a team, a service or the organisation), the model version and the targets;
nothing is stored before the save (`POST /api/v1/samm/scopes`), then the page moves to the address of the scope. The
route comes before `samm.scope` in the file

|`samm.assessment.new`
|`/samm/{scope}/new`
|The form of a new assessment of the scope: title, date, model version, assessors; nothing is stored before the save

The segment `new` is reserved in `{scope}` and in `{assessment}`: the server never assigns it as an address segment (a

assessment `{x}` of a scope `new`, which does not exist: the not-found view. The targets editor, the trend and the way
to start a new assessment have no address of their own: they are parts of the scope sheet and of the frozen assessment.
The new addresses admit no query.

=== A New Scope

`POST /api/v1/samm/scopes`:

[source,json]
----
{
  "title": "Mobile Apps",
  "subject": "team:mobile",
  "modelVersion": "v2.2.0",
  "targets": {
    "sm": { "target": 2 },
    "ta": { "target": 2.5, "due": "2027-03-31" },
    "sb": { "target": 1.5 }
  }
}
----

`subject` is `team:<id>`, `service:<id>` or `organisation` (AUN-SAMM-2), the form a `CatalogPicker` stores; `title` is
1 to 200 characters; `modelVersion` is a pinned version, the default when absent; `targets` is optional: a practice of
the model maps to a `target`, one of 0, 0.5, 1, 1.5, 2, 2.5 or 3, and an optional `due`, a date `YYYY-MM-DD`. A
practice without an entry has no target. The request answers `201`

[source,json]
----
{
  "outcome": "CREATED", "id": "mobile", "document": "mobile", "address": "/samm/mobile", "at": "2026-11-26T09:30:00Z",
  "parts": {
    "data": { "blob": "c41e07d", "savedAt": "2026-11-26T09:30:00Z",
              "savedBy": { "pseudonym": "p-4c1a9e", "name": "Alex Example" } },
    "targets": { "blob": "9a02f5b", "savedAt": "2026-11-26T09:30:00Z",
                 "savedBy": { "pseudonym": "p-4c1a9e", "name": "Alex Example" } }
  }
}
----

`id` is the address segment the server derives from the title (lower case, a number appended on a collision),
`document` the document id (a ULID in the application; the mock uses the same text as `id`). The refusals, `422`, with
pointers into the body, like the create of a catalog entry:

[source,json]
----
{ "outcome": "VALIDATION", "errors": [
    { "pointer": "/title", "code": "REQUIRED" },
    { "pointer": "/subject", "code": "REFERENCE_NOT_FOUND" },
    { "pointer": "/targets/ta/target", "code": "ENUM" },
    { "pointer": "/targets/rt/due", "code": "PATTERN" } ] }
----

The other codes: `MAX_LENGTH` and `TYPE` for `/title`, `PATTERN` for a `/subject` of none of the three forms,
`ENUM` for `/modelVersion` and for a practice id the model does not have (`/targets/<practice>`). A subject that does not
resolve is the refusal AUN-SAMM-2 asks for: the pointer names the reference. A user without `edit` on `samm-assessments`
gets `403 FORBIDDEN`.

It answers `{"outcome": "SAVED", "at": "2026-11-26T09:45:00Z", "parts": {"targets": {"blob": "a41f09c", "savedAt": "…",
"savedBy": {"…": "…"}}}}`. Per-field refusals, `422`, with the part and the pointer into the value of the part, which is
the map of the practices:

[source,json]
----
{ "outcome": "VALIDATION", "errors": [
    { "part": "targets", "pointer": "/ta/target", "code": "ENUM" },
    { "part": "targets", "pointer": "/rt/due", "code": "PATTERN" } ] }
----

A conflict, `409`, per practice with the whole entry of both sides:

[source,json]
----
{ "outcome": "CONFLICT", "conflicts": [
    { "part": "targets", "blob": "c05e92a", "fields": [
        { "pointer": "/ta", "own": { "target": 3, "due": "2027-03-31" }, "other": { "target": 2 },
          "by": { "pseudonym": "p-2b7f10", "name": "Jordan Weber", "role": "Team Lead" } } ] } ] }
----

A scope is no workflow: no draft (`PUT /api/v1/drafts/…` is not used for it), no submit, no release, never frozen. A save
writes one signed commit to `main`. The event `document-saved` (`part` `targets`) and, after a create, `document-created`
(`kind` `scope`) reach the other tabs; the lists and an open scope sheet read again.

=== A New Assessment

`POST /api/v1/samm/shop/assessments`:

[source,json]
----
{ "title": "Web shop 2026 Q4", "date": "2026-11-26", "modelVersion": "v2.2.0", "assessors": ["p-2b7f10"] }
----

`title` is 1 to 200 characters, `date` a date `YYYY-MM-DD`, `modelVersion` a pinned version (the default when absent),
`assessors` zero to 30 further pseudonyms of the person directory, bound or not yet bound (UC-SAMM-2); the user who
creates the assessment is always its first assessor, so a user can start one in an installation whose directory lists no
one else. The assessment starts empty. It answers `201`

[source,json]
----
{
  "outcome": "CREATED", "id": "2026-q4", "document": "shop-2026-q4", "scope": "shop",
  "address": "/samm/shop/2026-q4", "state": "draft", "at": "2026-11-26T09:35:00Z", "parts": {}
}
----

`id` is the address segment the server derives from the title within the scope (lower case, a number appended on a
collision), `document` the document id, `parts` empty: no practice file exists before its first save. The refusals:

[source,json]
----
{ "outcome": "VALIDATION", "errors": [
    { "pointer": "/date", "code": "PATTERN" },
    { "pointer": "/modelVersion", "code": "ENUM" },
    { "pointer": "/assessors/1", "code": "PSEUDONYM_UNKNOWN" } ] }
----

and `404 NOT_FOUND` for an unknown scope. A scope that has an assessment in `draft` or `in-review` refuses a second one,
`409`:

[source,json]
----
{ "outcome": "ASSESSMENT_OPEN", "assessment": "2026-q4", "state": "draft" }
----

The web app links the open assessment from this refusal. The event `document-created` (`kind` `assessment`) reaches the
other tabs.

=== The Assessment

`GET /api/v1/documents/samm-assessments/payments-2026-q4` keeps the SAMM shape of the first lens and gains `evidence`
(shortened):

[source,json]
----
{
  "id": "payments-2026-q4", "repository": "samm-assessments", "scope": "payments", "slug": "2026-q4",
  "title": "Payments 2026 Q4", "date": "2026-11-24", "modelVersion": "v2.2.0", "state": "draft",
  "assessors": [ { "pseudonym": "p-4c1a9e", "name": "Alex Example", "role": "Security Champion" } ],
  "answers": { "sb": { "sb-b-1": { "answer": 1,
      "comment": "Dependency scanning runs in *every* pipeline.\n\n* Scanner: the template of the platform team\n* The SBOM is not yet published." } } },
  "evidence": {
    "sb": [ { "question": "sb-b-1", "title": "Pipeline of the payment service", "url": "https://ci.example/payments/pipeline" },
            { "question": null, "title": "Dependency policy", "url": "https://wiki.example/payments/dependency-policy" } ]
  },
  "parts": { "sb": { "blob": "4f10c8e", "savedAt": "2026-11-25T09:48:00Z",
                     "savedBy": { "pseudonym": "p-9e33a1", "name": "Sam Okafor", "role": "Developer" } } },
  "history": [ "…" ],
  "release": null
}
----

* `comment` is an AsciiDoc fragment of at most 8,000 characters, shown with the preview of `POST /api/v1/render/asciidoc`.
* `evidence` maps a practice id to its links in the order they were entered; a practice without a link is absent, an
  assessment without any has `"evidence": {}` (the member is always present). `question` is a question id of the
  practice or `null` for the practice as a whole; `title` is 1 to 200 characters; `url` is an absolute `https` address of
  at most 2,048 characters; a practice holds at most 50 links. Evidence is a link, never a file (AUN-SAMM-7).
* The blob of a practice covers its answers, its comments and its evidence: they are one file per practice,
  `answers/<practice-id>.yaml`, as the use case change `change-evidence-per-practice` fixes (no separate evidence file),
  read and written together.
* A released assessment reads `"state": "released"`, `release` set; it is frozen.

*A save with a comment and evidence*, `POST /api/v1/documents/samm-assessments/payments-2026-q4/save`, the generic body:

[source,json]
----
{ "parts": { "sb": { "blob": "4f10c8e", "fields": {
    "sb-b-1/answer": 1,
    "sb-b-1/comment": "Dependency scanning runs in *every* pipeline.",
    "evidence": [ { "question": "sb-b-1", "title": "Pipeline of the payment service",
                    "url": "https://ci.example/payments/pipeline" } ] } } } }
----

The keys of the practice are `<question>/answer`, `<question>/comment` and `evidence`, which holds the whole list; an
empty list or `null` removes the evidence of the practice. The answer is the generic `SAVED` with the new blob of `sb`.
The draft takes the same body. The per-field refusals name the pointer into the assessment as the SAMM read shows it,
`/answers/<practice>/<question>/answer`, `…/comment` and `/evidence/<practice>/<n>/<member>`:

[source,json]
----
{ "outcome": "VALIDATION", "errors": [
    { "part": "sb", "pointer": "/evidence/sb/1/url", "code": "PATTERN" },
    { "part": "sb", "pointer": "/evidence/sb/0/title", "code": "REQUIRED" },
    { "part": "sb", "pointer": "/answers/sb/sb-b-1/comment", "code": "MAX_LENGTH" } ] }
----

`PATTERN` is a `url` that is no absolute `https` address (`http://…`, a relative path, a `file:` address), `REQUIRED` an
empty `title` or `url`, `MAX_LENGTH` a text above its limit, `MAX_ITEMS` the pointer `/evidence/<practice>` with more
than 50 links, `ENUM` a `question` the practice does not have. A conflict on the evidence is one field,
`/evidence/<practice>`, whose `own` and `other` are the two lists.

*A frozen assessment.* Every write to a released assessment, the draft, the save, the submit and the release alike,
answers `409`

[source,json]
----
{ "outcome": "DOCUMENT_RELEASED", "tag": "assessments/payments-2026-q2/v1" }
----

and nothing is written. The web app does not offer a write for it: the sheets are read-only with the release as seal and
one act, *Start a new assessment*, which opens `/samm/{scope}/new` (the scope of the assessment). That form prefills the
model version of the frozen assessment when it is pinned and refuses with the reason when `ASSESSMENT_OPEN` is the answer.
An assessment released while it was open elsewhere answers the save with the same `409`; the draft stays and the sheet
reads the assessment again.

=== The Comparison and `MODEL_VERSIONS_DIFFER`

`GET /api/v1/samm/payments/compare?from=2026-q2&to=2026-q4` for two assessments taken with different versions of the model
answers `422`

[source,json]
----
{
  "outcome": "MODEL_VERSIONS_DIFFER",
  "from": { "assessment": "2026-q2", "modelVersion": "v2.1.0" },

[#_the_step_up_handler]
== The Step-Up Handler

One module of the web app handles every request that can ask for step-up; no view has its own handling
(xref:authentication.adoc#AUN-AUTH-4[AUN-AUTH-4], xref:../use-cases/01-access.adoc#UC-ACC-3[UC-ACC-3]). The whole
section is PROVISIONAL where it says so: the requirements fix the outcomes and the method per login provider, not the
shape of the web app's handling.

*Which requests ask.* A request asks when the workflow of its category declares step-up for the transition, and
`step-up.enabled` is `true`; under the shipped workflows that is every release. The handler serves, as their rows exist:

[cols="2,3,1"]
|===
|Transition |Request |Row

|Release
|`POST /api/v1/releases/{repository}/{id}`
|above

|Any other transition a workflow declares
|`POST /api/v1/documents/{repository}/{id}/transitions/{t}`, and the save
`POST /api/v1/documents/{repository}/{id}/save`
|above

|Completion of a stage (the stage that closes the incident review)
|`POST /api/v1/documents/{repository}/{id}/stages/{stage}/complete` (PROVISIONAL, added with the incident reports)
|with its step

|Save of the configuration
|The request that writes the configuration repository (PROVISIONAL, added with the configuration editor)
|with its step

|Activation of a category
|The request that activates a category (PROVISIONAL, added with the category editor)
|with its step
|===

*The method* comes from `status.stepUp` (see `GET /api/v1/status`), read before the control is pressed:

[cols="1,3"]
|===
|`stepUp` |What the handler does

|`mfa`
|Sends the request. On `403 STEP_UP_REQUIRED` with `stepUp`, the step-up address, the web app leaves for it with the
address of the current view as `return`. It keeps nothing across the redirect (PROVISIONAL), except that a view with
unsaved changes keeps them as its draft before it leaves, and stays where it is, with its own message, when it
cannot keep them: the user comes back to the
view, the session now holds the fresh values, and the act is chosen again, which passes `stepup.check`. Token Sheriff's
planned pending action (SESSION-8) would complete the act itself; the handler is to be replaced by it. A step-up that
was cancelled or failed at the provider, or was met by another user, comes back without fresh values, and the same
request answers `STEP_UP_REQUIRED` again; the handler has no page for it

|`password`
|Asks, in a dialog titled "Confirm your identity", only where the server requires the confirmation for that step, and
sends the password as the member `password` of the JSON body of the request (PROVISIONAL generalisation: the release's
`{"password"}` is the body member of any request that can ask; the other members stay). The dialog opens before the
request when the caller knows the step to need it (the release; a transition whose entry in `transitions` says
`"stepUp": true`), and otherwise after `403 STEP_UP_REQUIRED`, which the handler answers by asking and sending the same
request again with the password: a save, and a step that declares no step-up, go out without a question when the server
asks for none. `401 INVALID_CREDENTIALS` keeps the dialog open with the error and writes nothing; any other answer closes
the dialog and is the view's. The password is never kept, logged or shown

|`off`
|Sends the request; there is no dialog and no line in the margin
|===

*Where it lives in the web app.* `src/lib/stepup/stepUp.ts` (`StepUpHandler`: `run(request)` answers `done`, `refused` with
the view's own refusal, or `handled`) and `StepUpDialog.svelte` (the dialog and the notice). The release, the submit
for review (`transition`) and the save for everyone of a SAMM practice send through it; `POST
/api/v1/documents/{repository}/{id}/transitions/{t}` and `.../save` carry the member `password` like the release. The
rows of stage completion, configuration save and category activation use it when their steps add them.

*The line in the margin* ("You confirm your identity once more before the release.") is shown whenever `stepUp` is not
`off` and the control asks; the control itself names the domain act only
(xref:web-app.adoc#AUN-WEB-6[AUN-WEB-6]).

*The outcomes the handler owns:*

[cols="1,1,3"]
|===
|Status |`outcome` |Handling

|`403` (PROVISIONAL)
|`STEP_UP_REQUIRED`
|As above. With `stepUp: "password"` a server that answers it, with or without an address, is answered by opening the
dialog (when the dialog was opened already and the server asks again without an address, it stays open with the
error)

|`401`
|`INVALID_CREDENTIALS`
|A wrong password; not a lost session: the client decides a `401` by its `outcome` first and leaves for the login only
for `UNAUTHENTICATED` (decided provisionally, see <<_open_questions>>)

|`503` (PROVISIONAL status)
|`TOO_MANY_LOGINS`
|Every place of pending logins is taken, so no step-up can start; nothing is written, `Retry-After: 60`. The view shows
a notice that many people are logging in and the act can be tried again in a minute; the draft and the view stay
as they were

|`401`
|`UNAUTHENTICATED`
|The session ended meanwhile; the normal path to the login, back to the same address; a logout always wins over a
step-up still running
|===

The outcomes after the fresh values passed are those of the transition, and they are the view's, not the handler's:
`CHANGED_SINCE_REVIEW` when the document was saved meanwhile, `FORBIDDEN` when the right was withdrawn,
`MANDATORY_FIELDS_MISSING`, `REJECTED`. Nothing is written for any of them
(xref:../use-cases/01-access.adoc#UC-ACC-3[UC-ACC-3], `stepup.recheck`).

[#_a_session_without_rights]
== A Session Without Rights

A user whom no group maps to a right is logged in; the session answers `"rights": []` and `firstLoginRequired` as
usual (xref:../use-cases/01-access.adoc#UC-ACC-1[UC-ACC-1]). Every request that acts on a repository is refused
`403 FORBIDDEN`, the lists of the lenses included (the shell cannot read a list it has no right to). The shell's own
requests work: status, messages, session, events, logout, and with the default person directory the first login. The
Due list is not a request on a repository: it answers `{"items": []}` (PROVISIONAL: nothing is due for a user without
rights). The web app decides by `rights` being empty and `firstLoginRequired` being `false`: it shows a notice that the
organisation has granted no access yet, and the empty state in place of every list, and it never asks the user for
another login.

[#_a_session_that_is_replaced]
== A Session That Is Replaced

A new login in the same browser ends the session that browser held; the tabs of the old session carry the new session's
cookie with their next request (xref:../use-cases/01-access.adoc#UC-ACC-6[UC-ACC-6]). What the web app does:

. The event stream of the old session closes (<<_requests>>, `GET /api/v1/events`).
. The tab reads `GET /api/v1/session`. `401 UNAUTHENTICATED` is the normal path to the login. A `200` with the same
`csrfToken` the tab started with is a transient break: the tab opens the stream again. A `200` with another
`csrfToken` is another session: the tab reloads at its own address, so no tab goes on showing the state of the
replaced session. The token is the identity of the session in the contract (PROVISIONAL): the session view has no
session id, and the cookie is `HttpOnly`.
. A state-changing request of the old tab, sent before it noticed, carries the old token and answers `403 CSRF_REJECTED`;
the client reads the session again, as it already does.

[#_addresses_outside_the_shell]
== Addresses Outside the Shell

Three addresses of the web app are shown without the shell (no navigation rail, no session): `/login`, `/signed-out`
and `/login-problem`. They are listed in `canonical-addresses.json` under `outsideShell`, not under `addresses`, so that
the web app routes them but the check of a login's `return` (AUN-AUTH-1) never accepts them: a login never returns to
the page that started it. They read the status and the message catalogue, nothing else, and keep the notice of local
test accounts when `status.loginProvider` is `local`. All of this is PROVISIONAL except what AUN-AUTH-6 fixes
(`/login?return=<address>` with local users).

[cols="2,4,3"]
|===
|Address |Content |Requests

|`/login?return=<address>`
|With `local`: a form with username and password and the notice of local test accounts. The `return` is checked
against the canonical addresses on the client too (`/` when it fails). With `oidc` the page is not shown: it starts the
login by navigating to `/api/v1/auth/login?return=<address>` (PROVISIONAL)
|`POST /j_security_check`: `200` navigates to the checked `return`; `401` shows "The username or the password is wrong."
and keeps the form; the password field is cleared

|`/signed-out`
|"You are signed out." and one action, "Log in", which starts the login with `return=/`. No session is needed and none
is created by opening the page
|none

|`/login-problem?reason=<reason>`
|The reasons `idp-unavailable` (the login service of the organisation cannot be reached), `too-many-logins` (many
people are logging in; try again in a minute) and `unknown-transaction` (the login took too long or was interrupted).
Another or no `reason` is shown as the general failure. One action: "Try again", which starts the login with `return=/`
|none
|===

[#_notes]
== Notes

* *The assessment is a document.* The SAMM views read and write an assessment through the generic document requests;
only the scope list, the scope and its creation, the models, the creation of an assessment, the trend and the comparison
are SAMM-specific (<<_samm_requests>>).
* *The release names no reviewed revision yet.* `CHANGED_SINCE_REVIEW` is therefore answered by the state of the
server, not by a comparison with the revision the approver saw. A request that carries the reviewed revision would
make the check exact.
* *Status codes.* The register states a status only where a requirement fixes it. A view never decides by it alone.
* *Local users and the shell.* `status.loginProvider` is the only place the shell learns the provider from: the
`login` member of a `401` is `/login` with `local` and `/api/v1/auth/login` with `oidc`, and the logout lands on
`/signed-out` in both.

[#_open_questions]
== Open Questions

* *The step-up address.* The requirement names "a step-up address" without its format; the client keeps it opaque.
* *`status.stepUp`.* The shell needs to know the method of the confirmation before the release is pressed; whether the
member stays in `GET /api/v1/status` or moves into the session is open.

*Decided provisionally* with the access use cases (UC-ACC-1, -2, -3, -6, -7), so that no screen is blocked; the owner
may change each one:

. *`401 INVALID_CREDENTIALS` and the client.* AUN-WEB-9 answers a wrong step-up password with `401`; the specification
keeps it. The `ApiClient` decides a `401` by its `outcome` first and leaves for the login only for `UNAUTHENTICATED`;
the mock answers `401`, as the specification says (it answered `403` before). Replaces the earlier open question.
. *`status.loginProvider` absent* reads as `oidc`; *`status.stepUp` absent* reads as `mfa` with `oidc` and `off` with
`local`.
. *Login refusals for a browser.* A navigation (`Accept` contains `text/html`) to the login start or the callback is
answered with a `303` to `/login-problem?reason=` instead of raw JSON; the JSON, the statuses and `Retry-After` stay for
every other client. The outcome `UNKNOWN_TRANSACTION` (`400`) is new. The server's own error page for the callback
stays until the web app page exists, and goes away with the bootstrap login (ADR-0004).
. *`/signed-out` as the landing of a logout*, in place of "the start page" of AUN-AUTH-1 and AUN-AUTH-6. With the
identity provider the post-logout redirect address `/signed-out` must be registered at the provider, which is a duty
of the operator.
. *`/login` with `oidc`* starts the provider login at once; the page exists for `local` only in substance.
. *The identity of a session* in the browser is its `csrfToken`: there is no session id member, and no member would
be safe in a cookie-less answer.
. *The event stream* belongs to its session and closes with it (use case change `change-events`), and a closed stream
makes the tab read the session again.
. *The step-up carries no pending action across the redirect;* the user chooses the act again after the return. The
member `password` of the body generalises the release's `{"password"}` to every request that can ask.
. *`STEP_UP_REQUIRED` is `403`; `TOO_MANY_LOGINS` of a step-up is `503` with `Retry-After: 60`,* the status of the
login start.
. *A session without rights* gets an empty Due list and `FORBIDDEN` for every repository request; the shell decides by
`rights` being empty.
. *The refusal of `POST /j_security_check` for a foreign `Origin`* answers `403` with `CSRF_REJECTED`.

. *The pages outside the shell read the status and the texts only,* never the session; opening one neither needs nor
creates a session. A page moved into the shell without a page load reloads the tab so that the shell starts properly.
. *The local login posts by `fetch`,* not by a native form post: the page decides by `200` or `401` itself, and then
leaves by a full page load at the checked `return`. The dev server proxies `/j_security_check` to the mock.
. *The wrong-password text is general:* "The password is not right. Nothing was changed." serves every request that
asks, in place of the release's "Nothing was released."
. *A session without rights* shows both the notice and the empty state in place of every view on a repository, except
the first-login form and the settings; the empty view makes no request that the server would refuse.
. *Only a stream that had connected* makes the tab read the session again when it ends; a stream that never connected
is the ordinary retry.
. *The mascot* stands on `/signed-out` only; the login page, the login problem and the empty state without access show
none.

For the owner: whether `/signed-out` replaces the start page (4), whether `/login` should exist for `oidc` (5), and
whether the session needs an explicit identity member instead of the token (6).

[#_decided_forms]
*Decided provisionally* with the form kit (`SchemaForm` and its components), so that no screen is blocked; the owner may
change each one. The reasoning is in xref:web-app.adoc#AUN-WEB-4[AUN-WEB-4]:

. *One request for the schema of a category,* `GET /api/v1/categories/{category}/schema`, answering every document type
of the category with its repository alias and its schema file unchanged. A category with several document types
(ISMS, incident reports) is thus read once, and the request needs no query.
. *The texts of a field are catalogue keys,* `category.<category>.<kind>.field.<path>` with `.help` and
`.option.<value>`; the schema's `title` and `description` are not shown. Without a key the form shows the property name.
. *The component is chosen by an ordered rule list* (AUN-WEB-4, Choosing the Component). The additions to the
specified constructs are `format: date`, numbers, arrays of scalars (a `DataTable` of one column), sections of objects,
`format: gdr-link` without `x-catalog` as `DocumentRefField`, `x-free-text` as a text area, and `readOnly`. A
construct the form does not know is shown as plain data and kept unchanged.
. *The browser validates without Ajv,* with a hand-written check of the constraints its components can offer; the
requirement's earlier text named Ajv. No dependency is added.
. *A format error of the browser never stops a save.* The library's validator asserts no `format`
(https://github.com/cuioss/git-document-repository/blob/main/doc/specification/git-forms.adoc#GDR-FORMS-2[GDR-FORMS-2]),
so the browser's check is advice; the errors of the server replace the browser's.
. *A mandatory field is no error before a transition.* The browser lists the empty `required` fields for the transition
that needs them; the server's `MANDATORY_FIELDS_MISSING` decides.
. *The codes of a field error* are the capitalised keyword of the failing constraint, plus `REFERENCE_NOT_FOUND`
(specified) and `PSEUDONYM_UNKNOWN`; the text is the catalogue key `form.error.<code>`, with `form.error.invalid` for
another code.
. *The picker lists are whole lists:* `GET /api/v1/catalogs/{catalog}` carries `retired`, and
`GET /api/v1/directory/persons` is capped at 100 with `truncated`; the client filters locally as well, which is
complete only while `truncated` is `false` (with `true` it asks the server with `q`; the server filters by `q`). A
single pseudonym resolves with `GET /api/v1/directory/persons/{pseudonym}` to `bound`, `unbound` or `former`.

[#_decided_lifecycle]
*Decided provisionally* with the document lifecycle (UC-DOC-1, -2, -3, -4, -6, -7, -8, -9), so that no screen is
blocked; the owner may change each one. The bodies are in <<_document_lifecycle_requests>>, the addresses in
<<_the_generic_documents_lens>>:

. *A generic documents lens* shows the categories without a lens of their own (custom categories, `test-note`): the
  ninth entry of the rail, *Documents*, only while `GET /api/v1/categories` lists a `generic` category. The addresses are
  `/categories`, `/categories/{category}`, `/categories/{category}/new`, `/categories/{category}/{document}` and
  `/categories/{category}/{document}/release`. They differ from the reading of `change-web-3` in the use cases of the
  categories, which gives `/categories/<category>` to the definition and the editor: the definition and the editor take
  `/categories/{category}/edit` (step 10), the segments `new` and `edit` are reserved, and `/categories/{category}`
  lists the documents.
. *A document id is a ULID* and has a placeholder pattern of its own (`document`), case sensitive. The address names
  the category and the document, never the repository; the web app resolves the repository among the repositories of
  the category's document types.
. *An address has an allowed query set.* `?at=<revision>` on `categories.document`, `?kind=<kind>` on `categories.new`;
  unknown names are ignored when an address is read and refused in a login's `return`; a known name with a bad value,
  or twice, is an address that is not found. Later steps add `as-of` and the like.
. *`GET /api/v1/categories`* is the smallest request that tells the rail whether the lens exists; step 10 extends it
  with the administration of categories.
. *A revision is read with `GET …/{id}?at=`*, `at` being `v<n>`, a commit id or the full tag, and listed by
  `GET …/{id}/revisions` with the `ref` the picker passes on. A revision is read-only (`frozen: true`) and has no
  draft and no workflow acts.
. *The generic read has `parts.<part>.value`*, `version`, `frozen`, `draft`, `transitions` and `releaseRequest`; a
  single-file document type has one part, `data`. The workflow offers its transitions in the read, so that no view
  hard-codes a workflow; the release is the transition marked `release: true`, its text is "Release" in every case, and
  the text of any other is the catalogue key `category.<category>.transition.<transition id>`.
. *The first save after a release* of a document type released more than once makes the document `draft` again with
  the next `version`; `release` keeps the last release, which the diff compares with (UC-DOC-3, `change-reopen`). A
  document type released once, and a revision, are `frozen`.
. *A save and a draft carry `fields` keyed by JSON Pointer* into the value of the part (`null` removes a property), for
  every document type but the SAMM practice, whose keys stay as they are.
. *The pointers of a refusal of a save, a draft or a create* are into the value of the part named by the new member
  `part` of each error, so they are those of the form; this closes the last point of the form kit's decisions.
. *A draft with field errors is refused and nothing is written* (`422`), as the use case's flow shows; the web app
  keeps what the user typed in the page until a draft passes, and says so. A draft is never refused because the Git
  server is unreachable: it lives in the application.
. *A new document has no draft.* `/categories/{category}/new` holds the value in the page; the first save creates the
  document (`POST /api/v1/documents/{repository}`, `201 CREATED`, the server assigns the id) and the page moves to its
  address. The page asks before it is left with typed content. The mock answers a fixed id.
. *No "discard draft" in the web app* (UC-DOC-5, open point): a draft ends by a save or by expiry, as the use case says.
. *A release request is no web request.* It is an item of Due (`kind` `release`, with `requestId`, `requestedBy`,
  `requestedAt`, `comment`), the member `releaseRequest` of the document read, and the same four members on the
  `review` item of the approvers (the open point of UC-DOC-8: a pending request is shown to the approvers too). Its
  `address` follows the document's state: the document while it is in its first state, the release address in review.
  Where the request lives in Git stays the application's open question.
. *The release request carries no reviewed revision.* `POST /api/v1/releases/…` has no body but `password`; the mock
  answers `CHANGED_SINCE_REVIEW` by the state it is in, as the register's notes say. The web app re-reads the diff on
  that outcome. An exact check needs the field of `change-reviewed-revision`.
. *Statuses of the outcomes:* `409` for `CONFLICT`, `DOCUMENT_RELEASED` and `CHANGED_SINCE_REVIEW`, `422` for
  `MANDATORY_FIELDS_MISSING` and `VALIDATION`, `502` for `REJECTED`, `503` for `GIT_UNAVAILABLE`, `403` for
  `STEP_UP_REQUIRED`, `401` for `INVALID_CREDENTIALS`, `201` for `CREATED`.

  documents from the repositories the user may read, and is the palette's. It is read from the index, so it works while
  the Git server is unreachable.
. *The lists* hold at most 500 documents with `truncated`; the filters `kind` and `state` are done by the client as
  well, completely only while `truncated` is `false`.
. *Three events* join `document-saved`: `document-created`, `document-transitioned`, `release-requested`; `document-saved`
  gains the optional `part` and `by`. The open sheet re-reads the document on any of them.

. *The Due `lens` of the generic lens is `categories`*, and an item opens the address it names: a `review` item the

[#_decided_samm]
*Decided provisionally* with the SAMM completion (UC-SAMM-1 to UC-SAMM-5), so that no screen is blocked; the owner may
change each one. The bodies and addresses are in <<_samm_requests>>:

. *The addresses.* The lens *SAMM* gains `/samm/new` (`samm.new`, a new scope) and `/samm/{scope}/new`
  (`samm.assessment.new`, a new assessment), each before the route it would collide with. The segment `new` is reserved
  as a scope and as an assessment; so are `models` and `scopes` as scopes, which are paths below `/api/v1/samm/`.
. *The creates are requests of their own,* `POST /api/v1/samm/scopes` and `POST /api/v1/samm/{scope}/assessments`, because
  a scope names a subject and an assessment names its scope, and the server derives the address segment of both. The
  generic `POST /api/v1/documents/{repository}` would need the web app to know the layout of the two document kinds.
  The server assigns the address segment (a lower-case slug of the title, a number appended on a collision; a slug that is
  a reserved segment, `new`, or `models` and `scopes` for a scope, counts as a collision, so a scope titled "New" gets
  `new-2`) and the document id.
. *The scope is a document without a workflow.* Its targets are saved with the generic save of a document, the part
  `targets`, so the conflict, the validation and the step-up of the document controller serve it; there is no draft, no
  submit, no release and no `DOCUMENT_RELEASED`. The scope read gains `document` and `parts`.
. *The title and the subject of a scope cannot be changed* after the create; only the targets can. A scope of another
  subject is a new scope. A subject may have several scopes: the register does not forbid it.
. *A subject is written as the reference* `team:<id>`, `service:<id>` or `organisation` (AUN-SAMM-2) and read as
  `{kind, id, name}`.
. *A target is 0 to 3 in steps of 0.5,* with an optional due date; a practice without an entry has no target and no gap.
  AUN-SAMM-6 says "in steps of the model"; the model has no step, and 0.5 is the step of the targets of the mock (1.5,
  2, 2.5). The targets save sends the practices that changed, each as a whole entry, and `null` removes one.
. *The creator is always an assessor,* the first one; `assessors` names the further ones, none to 30. AUN-SAMM-1 says
  "assessors (pseudonyms)" without a minimum, and a first user of an empty installation has nobody to pick.
. *At most one assessment of a scope is open* (`draft` or `in-review`); a second one is refused with `409
  ASSESSMENT_OPEN` that names the open one. The scope list shows one open assessment per scope already.
. *A new assessment starts empty:* no answer is copied from an earlier one. The form of a new assessment prefills the model
  version of the assessment it was started from. Copying answers is a later decision.
. *Evidence belongs to the practice,* like the answers (the change `change-evidence-per-practice`): the read has
  `evidence` per practice, the practice's one file `answers/<practice-id>.yaml` and its blob cover answers, comments and
  evidence (no separate `evidence/<practice-id>.yaml`), and the save carries the whole list
  under the key `evidence`. A link has an optional `question`, a title and an absolute `https` address; a practice holds at
  most 50. `http`, relative and `file:` addresses are refused with `PATTERN`, there is no upload (AUN-SAMM-7).
. *The comment of an answer is AsciiDoc* of at most 8,000 characters, previewed by the server like every AsciiDoc field
  (`POST /api/v1/render/asciidoc`); the existing plain comments are valid AsciiDoc.
. *The pointers of a SAMM refusal* are those of the assessment as the SAMM read shows it
  (`/answers/<practice>/<question>/answer`, `/evidence/<practice>/<n>/<member>`), as the existing conflicts already are;
  the generic form keeps pointers into the value of a part. The scope's refusals are into the targets part
  (`/<practice>/target`).
. *A frozen assessment* is a released one: every write (draft, save, submit, release) answers `409 DOCUMENT_RELEASED` with
  the tag, the draft included, and the sheets are read-only. The way on is *Start a new assessment*, a link to
  `/samm/{scope}/new`; there is no request that copies or reopens a released assessment.
. *`MODEL_VERSIONS_DIFFER` is `422`* and names both assessments with their versions. AUN-SAMM-5 names the outcome, not the
  status. The comparison accepts an assessment in any state, as the first SAMM lens already uses it (an open assessment
  against the last release), reading the answers as saved.
. *The trend is one request per scope,* `GET /api/v1/samm/{scope}/trend`: released assessments of one model version, oldest
  first, with the overall, the function and the practice scores, and the number of the others (`omitted`). UC-SAMM-5 asks
  for a trend of several scopes as well; that is a report of the lens *Reports* (the next step). The scope sheet's chart
  reads this request instead of the assessments of the scope.
. *The pinned models are a list,* `GET /api/v1/samm/models`, with source, checksum, date and a default; pinning is not
  a web request (UC-SAMM-7 is configuration). The checksum is shown nowhere in the web app yet. The pickers offer only a
  pinned version; with none, the web app offers no new scope and no new assessment and says why.
. *The rights:* creating a scope, saving its targets and creating an assessment need `edit` on `samm-assessments`; reading
  needs `read`. Without `edit` the acts are shown disabled with the reason, and the requests answer `403 FORBIDDEN`.
. *The SAMM schemas are not served to the form kit:* the forms of a scope and an assessment are written for the SAMM lens
  (a subject picker, a targets table, an assessor picker), and the register fixes their limits. The scope and the
  assessment are not offered by `GET /api/v1/categories/{category}/schema`.
. *The mock answers the creates with fixed ids* (`mobile`, `2026-q4` of `shop`, `2026-h2` of `organisation`) and by the path of the scope: a scope that
  has an open assessment answers `ASSESSMENT_OPEN`, a scope that has none answers `CREATED`; the e2e flows type the same
  values.
