== Overview

The use cases describe what a person does with Audit Notary and what they get out of it, from their point of view
and in their words. They come before the xref:README.adoc#_specification[specification]: a use case names the
`AUN-*` requirements that serve it, and a use case that no requirement serves yet shows what the specification still
lacks. People act in the web app; an AI agent acts for a user through the MCP server, with that user's rights and
never beyond them (xref:concepts/mcp-server.adoc[MCP Server]). There is one set of use cases for both interfaces: a
use case says what the person achieves, never how a screen shows it. How the web app shows it is worked out in its
design (xref:concepts/web-app.adoc[Web App], xref:specification/web-app.adoc[Web App specification]); how the system
does it, in the xref:README.adoc#_specification[specification].

The use cases are the backlog of the application: the bootstrap built the shell, the login and the configuration
(xref:specification/architecture-and-modules.adoc#_maven_modules[Architecture and Modules, Maven Modules]); every
other use case is still to be implemented, in the order of <<order>>. Four requirements serve every use case alike
and no single one names them: the persistence only through the libraries
(xref:specification/architecture-and-modules.adoc#AUN-GEN-4[AUN-GEN-4]), the single-page application served
same-origin (xref:specification/web-app.adoc#AUN-WEB-1[AUN-WEB-1]), its visual language and accessibility
(xref:specification/web-app.adoc#AUN-WEB-2[AUN-WEB-2]), and the mock server the web app is tested against
(xref:specification/testing.adoc#AUN-TEST-1[AUN-TEST-1]).

== Conventions

* *Identifier*: every use case has a stable anchor `[#UC-<AREA>-<N>]` and the heading `== UC-<AREA>-<N>: <title>`. A
  number is never reused.
* *One module per area*: `use-cases/NN-<area>.adoc`, listed in <<index>>.
* *Interface-neutral*: a use case is cut by subject, never by interface; it names the web app or an agent at most as
  where someone acts, never its screens or its tools' parameters. Where an MCP tool serves the use case, the use case
  names the tool in its _Variations_, so that the rule of
  xref:specification/architecture-and-modules.adoc#AUN-GEN-2[AUN-GEN-2] (one rule set for both interfaces) can be
  traced.
* *Status*: each use case states one of `DRAFT` (not yet agreed by the owner; its open points named where there are
  any) and `AGREED` (the owner agreed to it; requirements and design may be derived from it). What the bootstrap
  already built is said in the use case's _Variations_ or _Open points_, not by a status.
* *Flow form*: the form of a flow follows what the use case is. A use case whose process the server runs (a save, a
  release, a first login) has a state diagram (*Processes*, below). A use case that only shows something, a view with
  no process of the server behind it, has numbered steps, one per part of the view as the person reads it.
* *Processes*: a flow is drawn as an ASCII state diagram in a `[source,text]` block: one line per state, named as the
  state would be named in the workflow or the service; the arrows carry the outcomes, which are those of
  xref:specification/architecture-and-modules.adoc#operation-outcomes[Operation Outcomes] where the operation has one.
  A step that is a process of its own is a sub-flow with a use case of its own. One legend holds for every diagram,
  and no diagram repeats it:
** `[S]` the server acts.
** `[U]` the user chooses or acts, in the web app.
** `[O]` the operator acts outside the application (files, configuration, command line, the Git server).
** `[G]` an AI agent acts for the user, through a tool of the MCP server.
** `[P]` the identity provider acts (login, step-up).
** `↳` a call of a sub-flow, named by its use case (`↳ UC-ACC-3`).
** `done`: the process ends; a sub-flow returns to its caller.
* *No macros in diagrams*: a `[source,text]` block renders no cross reference and no link; a diagram names a use case
  by its plain id, and where a link helps, the prose below the diagram carries it.
* *Requirements*: the part names first the requirements that serve the use case, each linked to its anchor with what
  it serves, and after them the library specifications the use case rests on; where no requirement serves the use
  case, or a part of it, it says "none yet". A requirement is never named that does not exist.
* *Design*: the part names the web-app concept and specification sections that show the use case; the reference for
  structure and visuals is `pm-web-app` (xref:specification/web-app.adoc[Web App specification]).
* [[changes]]*Changes*: a use case states what it needs. While it is `DRAFT`, the changes of the specification it
  needs are written in a _Changes to the Specification_ part of its module, each the fix of a gap, and named in its
  _Changes_; once it is `AGREED`, they are written into the concepts and specifications, and the part is removed.
* *Terms*: a *category* (SAMM, ISMS, a custom one) is the unit that is switched on and shown as a lens; a *document
  type* (`kind` in identifiers and files, the library's term) is one kind of document of a category, with its schema,
  workflow and template; a schema is a file of a document type, not a level of its own
  (xref:use-cases/09-categories.adoc[Categories]).
* *Sources*: a use case states no fact about an external product, standard or law of its own; it links the concept or
  specification that cites the source (`AGENTS.md`).
* *Shape*: each use case has the parts of the template below; a part that does not apply is left out, never filled
  with filler.

[source,asciidoc]
----
[#UC-<AREA>-<N>]
== UC-<AREA>-<N>: <title>

Status:: `DRAFT`
Actor:: who does it (a team member, an approver, an AI agent for a user, ...).
Goal:: what they want to achieve, in one sentence.
Trigger:: what makes them start.
Preconditions:: what holds before, rights included.
Flow:: the state diagram of the process the server runs; for a view, the steps, numbered, as the actor experiences
  them.
Variations:: other ways through, and what happens when something fails, one bullet and one clause each.
Outcome:: what holds afterwards.
Open points:: what is not decided yet.
Changes:: the changes of the specification it needs, each modelled as the fix of a gap (while DRAFT; *Changes*,
  above).
Requirements:: the requirements that serve it.
Design:: the web-app sections that show it.
----

[#actors]
== Actors

[cols="1,3",options="header"]
|===
|Actor |Who, and with which right (xref:specification/authentication.adoc#AUN-AUTH-2[AUN-AUTH-2])

|*Team member*
|A developer or assessor who reads and edits documents of a repository: right `edit` (and `read`).

|*Approver*
|A security officer, CISO or service owner who releases documents: right `approve`, with step-up.

|*Incident responder*
|Writes the report after the live phase of an incident: right `edit` on the incident repository of the year.

|*Catalog administrator*
|Maintains the catalogs, prefills and erases person entries, deletes expired repositories: right
`administer-catalogs`.

|*Category administrator*
|Creates and changes the custom categories of the organisation: the right `administer-categories`, which the
specification does not have yet (xref:use-cases/09-categories.adoc#changes-to-the-specification[Categories, Changes
to the Specification]).

|*AI agent*
|Acts for one named user through the MCP server, with the intersection of its token's scopes and the user's rights;
never releases (xref:concepts/mcp-server.adoc[MCP Server]).

|*Operator*
|Installs, configures and runs the application and the Git server's repositories; has no right in the application
by that role.
|===

[#order]
== Order of Implementation

Each milestone builds on the ones before it; the categories reuse the document use cases and add only what their
schema cannot express. `UC-OPS` runs beside the milestones: each operations use case is taken up with the milestone
that needs it.

[cols="1,2,3",options="header"]
|===
|Milestone |Use cases |Why here

|M1 Access
|UC-ACC-1 to UC-ACC-3, UC-ACC-6
|Partly built in the bootstrap; every other use case needs a session, and every release needs step-up. Designed against
Token Sheriff's planned session layer
(xref:adr/0004-Login_and_session_are_designed_against_Token_Sheriffs_planned_session_layer.adoc[ADR-0004]) and built on
it as its releases arrive (xref:use-cases/01-access.adoc#change-session[Access, the session layer]).

|M2 Documents
|UC-DOC-1 to UC-DOC-9, with the resources-only test category `test-note`
(xref:specification/architecture-and-modules.adoc#AUN-GEN-1[AUN-GEN-1])
|The shared life of every document, proven once before any category is built on it.

|M3 Directory and catalogs
|UC-ACC-4, UC-ACC-5, UC-CAT-1 to UC-CAT-5
|Persons, teams, roles and services are the references every category picks from.

|M4 SAMM
|UC-SAMM-1 to UC-SAMM-5, UC-SAMM-7
|The core of the application; the gaps that become risks wait for the register (M8).

|M5 Agents
|UC-AGT-1, UC-AGT-2, and the MCP variations of UC-DOC
|The tools call the services M2 built; threat models and incidents use agents.

|M6 Threat models
|UC-TM-1, UC-TM-2, UC-TM-4
|Needs the service catalog (M3); the transfer of a threat waits for the register (M8).

|M7 Incident reports
|UC-IR-1 to UC-IR-3
|Needs the service catalog and the deadline rules.

|M8 ISMS
|UC-ISMS-1 to UC-ISMS-3, then UC-SAMM-6 and UC-TM-3
|The extension; once the register exists, SAMM gaps and threats are carried into it.

|M9 Custom categories
|UC-KND-1 to UC-KND-5
|Needs the delivered categories as examples and the generated forms of M2.
|===

[#open-points]
== Open Points

An open point lives where it arises: in the _Open points_ part of a use case, or, where the concepts already hold it,
in the concept's _Open Questions_. This section lists every one of them; it holds no open point of its own.

* `UC-ACC`: which claims and groups reach the application, and whether groups arrive by token claim or by SCIM
  (xref:use-cases/01-access.adoc#UC-ACC-1[UC-ACC-1]; xref:concepts/authentication-and-identity.adoc#_open_questions[Authentication
  and Identity, Open Questions]); whether the provider puts the groups into refreshed ID
  tokens (xref:use-cases/01-access.adoc#UC-ACC-1[UC-ACC-1]); whether the session view's problem JSON carries the
  `outcome` and `login` of AUN-WEB-9 (xref:concepts/authentication-and-identity.adoc#_open_questions[Authentication
  and Identity, Open Questions]); whether the provider sends back-channel logouts and issues
  refresh tokens (xref:use-cases/01-access.adoc#UC-ACC-6[UC-ACC-6]); confirming and undoing the binding of a prefilled
  entry (xref:use-cases/01-access.adoc#UC-ACC-4[UC-ACC-4]).
* `UC-DOC`: how a release request is stored in Git (xref:use-cases/02-documents.adoc#UC-DOC-8[UC-DOC-8];
  xref:concepts/mcp-server.adoc#_open_questions[MCP Server, Open Questions]); whether the AsciiDoc preview runs on the
  server only (xref:use-cases/02-documents.adoc#UC-DOC-3[UC-DOC-3];
  xref:concepts/web-app.adoc#_open_questions[Web App, Open Questions]).
* `UC-CAT`: the direction in which protection needs flow along `dependsOn`, and whether a change of them needs a
  confirmation (xref:use-cases/03-catalogs.adoc#UC-CAT-2[UC-CAT-2];
  xref:concepts/service-catalog.adoc#_open_questions[Service Catalog, Open Questions]).
* `UC-SAMM`: the schemas of `scope` and `assessment`, and how the SAMM model is pinned and updated
  (xref:use-cases/04-samm.adoc#UC-SAMM-2[UC-SAMM-2], xref:use-cases/04-samm.adoc#UC-SAMM-7[UC-SAMM-7];
  xref:concepts/category-samm.adoc#_open_questions[SAMM, Open Questions]).
* `UC-TM`: the format of a threat model, how it fits the library's layout, which recipes ship, and the deadline rule
  of the review (xref:use-cases/05-threat-models.adoc#UC-TM-1[UC-TM-1],
  xref:use-cases/05-threat-models.adoc#UC-TM-2[UC-TM-2];
  xref:concepts/category-threat-models.adoc#_open_questions[Threat Models, Open Questions]).
* `UC-IR`: the schema of the report, the deadline rules the library still lacks, and how one document type
  addresses a repository per year (xref:use-cases/06-incidents.adoc#UC-IR-1[UC-IR-1],
  xref:use-cases/06-incidents.adoc#UC-IR-2[UC-IR-2]).
* `UC-ISMS`: the measurement of the index at register size before the register is built
  (xref:use-cases/07-isms.adoc#UC-ISMS-2[UC-ISMS-2]; xref:concepts/category-isms.adoc[ISMS]).
* `UC-AGT`: the protocol revisions besides 2026-07-28, Client ID Metadata Documents or pre-registered agents, and
  whether recipes are offered as MCP prompts (xref:use-cases/08-agents.adoc#UC-AGT-1[UC-AGT-1];
  xref:concepts/mcp-server.adoc#_open_questions[MCP Server, Open Questions]).
* `UC-KND`: durable state on the volume against xref:specification/architecture-and-modules.adoc#AUN-GEN-3[AUN-GEN-3],
  schema evolution of existing documents, the lens of a custom category, what an agent may read of a category, whether
  a change that invalidates documents is refused or confirmed, and whether categories are switched in the application
  (xref:use-cases/09-categories.adoc#open-points[Categories, Open Points]).
* `UC-OPS`: the rest of JGit in the native image (xref:use-cases/10-operations.adoc#UC-OPS-1[UC-OPS-1];
  xref:concepts/application-architecture.adoc#_open_questions[Application Architecture, Open Questions]).
