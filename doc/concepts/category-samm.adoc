An OWASP SAMM assessment kept as a spreadsheet such as `samm-final-v3-reviewed.xlsx` is compared with last year's
assessment by eye. That loses the one thing an assessment is for: the trend. SAMM is the core category of Audit Notary
because its model and its assessments map directly onto files in Git.

== What an Assessment Is

An OWASP SAMM assessment is a self-contained document at a date: answers per question of the model, comments,
evidence, and the scores computed from them. Its value is the comparison over time. It is edited as a draft, then
released and frozen as audit evidence. It refers to the SAMM model version it was taken with; since version 2 the
model itself is published as YAML files with semantic versioning. The data volume is small, and the only personal
data are the assessors, kept as pseudonyms and resolved through the directory.

Git therefore fits:

* the model is already YAML in Git;
* an assessment as YAML diffs well;
* release maps to a merge and a tag;
* history, rights, reviews and backups come from the existing infrastructure.

Drafts, the working branch per assessment, saving and release are mechanisms of the library's
https://github.com/cuioss/git-document-repository/blob/main/doc/concepts/storage-engine.adoc[storage engine]; this page names only what SAMM adds.

== Repository Layout

The layout follows the library's document layout `<collection>/<ulid>/document.yaml` with the split files a schema
declares. SAMM has two kinds of document, the scope and the assessment:

----
samm.yaml                              # pinned SAMM model version(s): repository configuration
scopes/<ulid>/
    document.yaml                      # kind scope; subject: team:<id>, service:<id> or organisation
    targets.yaml                       # declared split: target maturity, roadmap
assessments/<ulid>/
    document.yaml                      # kind assessment; header: scope (samm-assessments:scope/<ulid>), date,
                                       # model version, state, assessors
    answers/<practice-id>.yaml         # declared split, one file per practice: parallel editing without conflicts
    evidence.yaml                      # declared split: evidence as links, not as files
----

* *One file per practice* keeps concurrent edits of different practices conflict-free.
* *Deterministic serialisation* (fixed key order, stable formatting) makes diffs show real changes only; the
  serialisation is the library's (https://github.com/cuioss/git-document-repository/blob/main/doc/concepts/schema-driven-documents.adoc[Schema-Driven Documents]).
* *Evidence as links* (wiki, ticket, pipeline) avoids large files and Git LFS.
* *The scope* names its subject, a team, a service or the organisation, through the stable ids of the
  https://github.com/cuioss/git-document-repository/blob/main/doc/concepts/directory-and-catalogs.adoc[directory and catalogs]; an assessment refers to its scope by the
  typed reference `samm-assessments:scope/<ulid>`.
* *An assessment* is worked on in the working branch `refs/heads/assessments/<ulid>`; a practice is referenced as
  `samm-assessments:assessment/<ulid>#<practice-id>`.

The repository is `samm-assessments`, readable by development and security
(xref:data-protection-and-repository-layout.adoc[Data Protection and Repository Layout]).

== Workshop Mode: Save Often

SAMM is mostly filled in jointly in workshops. The application therefore uses the storage engine's _save often_
pattern: every explicit save lands on the assessment's working branch at once, as a small commit; the draft holds only
what is not yet saved. The UI remembers the blob id it loaded, like an ETag, and detects a concurrent change of the
same practice file. Two assessors on different practices never conflict. Two on the same practice get a conflict for
that practice file; the form shows the differing questions with both values, and they decide.

== Release, Comparison and Targets

* *Release* merges the assessment branch into `main` and creates the library's release tag `<collection>/<id>/v<n>`,
  here `assessments/<ulid>/v1`: an assessment is released once, so `n` is always 1. Protected branches and tags of the
  Git server make it immutable. The application merges the release itself; the signed release commit names the
  releasing user, who confirms the release with step-up (see xref:authentication-and-identity.adoc#_step_up[Step-Up]).
* *Scores* are computed as the OWASP SAMM toolbox computes them, so they stay comparable with toolbox results and the
  SAMM benchmark; the formula and its sources are in
  xref:../specification/category-samm.adoc#AUN-SAMM-5[AUN-SAMM-5]. The model has one question per activity, 90 in
  all (15 practices, 2 streams each, 3 maturity levels). The SAMM core team advises against changing the calculation
  for activities declared not applicable, because the results would no longer compare with the benchmark
  (https://owaspsamm.org/blog/the-not-applicable-question/[SAMM blog, 2023-02-28]); the application accepts only the
  answers of the model's answer sets, which contain no not-applicable answer.
* *Comparison* reads two released tags of the same model version from the in-memory index and shows the score
  difference per practice and stream. Dashboards and trends over hundreds of assessments come from the same index.
* *Targets* in `targets.yaml` name the target maturity per practice. A gap between the released score and the target
  can become a risk in the ISMS register (xref:category-isms.adoc#_the_bridge_to_samm[ISMS, the bridge to SAMM]).
* *Model versions*: an assessment keeps the model version it was taken with.

== Links to the Other Categories

* A maintained threat model is direct evidence for the SAMM practice _Threat Assessment_ (business function
  _Design_); the assessment links to the threat models of the services in its scope
  (xref:category-threat-models.adoc[Threat Models]).
* Once the ISMS keeps controls, a released assessment can serve as evidence for the secure-development controls of
  https://www.iso.org/standard/27001[ISO/IEC 27001:2022], among them A.8.25, by a reference to its tag
  (xref:category-isms.adoc#_the_bridge_to_samm[ISMS, the bridge to SAMM]).
* An ISMS product, verinice for example, refers to a released assessment by its release tag; the application delivers
  nothing into it (xref:audit-notary-overview.adoc#_positioning[Overview, Positioning]).

== Open Questions

. Draft the schemas of the kinds `scope` and `assessment` (their `document.yaml` and the splits `targets.yaml`,
  `answers/<practice-id>.yaml` and `evidence.yaml`).
. How the SAMM model YAML is pinned and updated (vendored copy in the repository or a fetched release).
. Deferred: a comparison across SAMM model versions (mapping practices by id and marking changed questions).
. Deferred: the pattern _private until submitted_ for single assessors, beside _save often_.

Decided provisionally with the SAMM completion (UC-SAMM-1 to UC-SAMM-5), recorded with the bodies in
xref:../specification/rest-api.adoc#_decided_samm[REST API Register, Open Questions]; the owner may change each one:

. The scope and the assessment are created by requests of their own; the server assigns their address segment. The title
  and the subject of a scope are fixed after the create, its targets are saved like a document (part `targets`, no
  workflow, never frozen).
. A target is 0 to 3 in steps of 0.5 with an optional due date; a practice without a target has no gap.
. At most one assessment of a scope is open at a time; a new assessment starts empty, its creator is always an assessor,
  and it may be started from a released one, which stays frozen.
. Evidence is kept per practice with the answers (`evidence` in the read, one list per practice, at most 50 absolute
  `https` links with a title); the comment of an answer is an AsciiDoc fragment of at most 8,000 characters.
. The comparison of two assessments of different model versions is refused with `MODEL_VERSIONS_DIFFER` (`422`); the
  trend of a scope reads the released assessments of one model version and counts the others as omitted.
. The pinned model versions are listed by `GET /api/v1/samm/models`; pinning stays configuration.

Decided provisionally with the Reports lens (UC-SAMM-5), recorded in
xref:../specification/rest-api.adoc#_decided_reports[REST API Register, Open Questions]; the owner may change each one:

. The trend of every scope is one request of the lens *Reports*, `GET /api/v1/reports/samm-trend`: the released assessments
  of each scope with the overall and the business function scores, without the practices. Scopes of different model
  versions share a chart with a notice that names the versions; a comparison across versions stays deferred.
. The comparison of two assessments of one scope has a page of its own, `/reports/samm-compare`, and no request beyond the
  one of the scope sheet; there is no comparison of two scopes.
. The screens read the register as follows (rest-api.adoc, Open Questions, points 20 to 26): a new assessment takes the model
  version of the scope's newest assessment; the targets of a scope are kept on the page until they are saved, and leaving
  asks (a scope has no draft); a due day belongs to a target; the evidence links are drawn as links only when they are
  absolute `https` addresses; the act that starts an assessment stands in the scope, in the frozen practice and in the
  released assessment.

Decided provisionally with the gaps (UC-SAMM-6), recorded in
xref:../specification/rest-api.adoc#_decided_isms[REST API Register, Open Questions]; the owner may change each one:

. The gaps of a scope are the practices of its latest released assessment whose score is below their target
  (`GET /api/v1/samm/{scope}/gaps`); a practice without a target has no gap. *Create risk* opens the new risk prefilled, and the
  risk keeps the reference to the practice of that assessment as its `origin`; one risk at a time per gap.
