xref:../README.adoc[Audit Notary documentation] » Concepts

Users of an ISMS or of an incident report need no account on the Git server, and the application does not require
one: a Git account per person only to fill in a form would be one more account to manage for each of them.
Audit Notary therefore authenticates people against the organisation's identity provider, or, where there is none,
against a file of local users, pushes with a technical user, and writes the identity of the person into every commit
in a form the application signs. This page is the application side of that design: the login, the claims used, the
local users, the first login, the rights, the Git credential and the step-up of a release.

The library side (the trailer schema, the commit signature, step-up, the signature check) is described in
https://github.com/cuioss/git-document-repository/blob/main/doc/concepts/identity-and-signing.adoc[Identity and Signing] and is not restated here.

== Login Through Token Sheriff

Token Sheriff provides authentication and the OAuth flows; this application takes it as given
(xref:../adr/0001-Authentication_is_delegated_to_Token_Sheriff_with_a_server-side_session_for_the_web_app.adoc[ADR-0001]).

* *Web app*: the server is a confidential client of the identity provider through `token-sheriff-client-quarkus`
  (authorization code with PKCE `S256` (https://www.rfc-editor.org/rfc/rfc7636[RFC 7636]), session-bound `state`
  and `nonce`, issuer check, optional pushed authorization requests (PAR,
  https://www.rfc-editor.org/rfc/rfc9126[RFC 9126])). The tokens stay
  in the server; the browser holds only cookies
  (xref:../specification/authentication.adoc#AUN-AUTH-1[Authentication, AUN-AUTH-1]). This is the
  backend-for-frontend shape Token Sheriff's client is built for; ADR-0001 explains why no API Sheriff BFF stands in
  front of the application.
* *MCP server*: AI agents present bearer access tokens. The server validates them with
  `token-sheriff-validation-quarkus` as an OAuth 2.1 resource server
  (https://www.ietf.org/archive/id/draft-ietf-oauth-v2-1-13.html[draft-ietf-oauth-v2-1-13], an Internet-Draft;
  xref:mcp-server.adoc[MCP Server]).
* *Logout* is RP-initiated
  (https://openid.net/specs/openid-connect-rpinitiated-1_0.html[OpenID Connect RP-Initiated Logout 1.0]) and revokes
  the tokens the server holds.

=== The Claims and What Becomes of Them

[cols="1,3"]
|===
|Claim |Use

|`iss`
|Which identity provider authenticated the user; written as `Actor-Issuer` trailer.

|`sub`
|Looked up in the person directory to find the user's pseudonym. *Never* written into the history: the trailer
carries the pseudonym (https://github.com/cuioss/git-document-repository/blob/main/doc/concepts/data-protection.adoc[Data Protection]).

|`auth_time`, `acr`, `amr`
|Time and strength of the authentication; written as `Auth-Time` and `Auth-Context` trailers; checked before a
release (step-up).

|`name`, `email`
|Prefill the first-login form. The e-mail is not stored in the directory; it comes from the token when needed.

|`groups` (or roles)
|The source of access rights (see <<_rights>>) and a prefill for the team in the directory.

|`azp` / `client_id`
|For tokens presented to the MCP server: which agent client acts for the user; written to the audit log
(xref:mcp-server.adoc#_attribution_of_agent_actions[MCP Server, Attribution]).
|===

[#_local_users]
== Local Users

WARNING: Local users are for evaluation, development, tests and demonstrations. For production, use the
organisation's identity provider: only it gives MFA, protection against guessing, and the withdrawal of access in one
place.

To try Audit Notary out without an identity provider, its users can be configured in files, as a servlet container
does with Tomcat's `tomcat-users.xml`
(xref:../adr/0005-Local_users_from_a_mounted_file_are_for_evaluation_and_testing_only.adoc[ADR-0005]). Audit Notary
follows Quarkus' lead here instead of building its own: Quarkus has a realm of users in properties files and calls it
"intended for development and testing purposes"
(https://quarkus.io/guides/security-properties[Quarkus, Using security with .properties file]), which is exactly this
purpose.

A deployment chooses one login provider in `audit-notary.yaml`, `oidc` or `local`, never both; the build is the same
for both. The users file holds Quarkus' own keys of its embedded realm:

[source,yaml]
----
login:
  provider: local
  local:
    users-ref: file:/run/secrets/audit-notary/local-users.properties
----

[source,properties]
----
# password: HEX( SHA-512( username ":Quarkus:" password ) ), Quarkus' default
quarkus.security.users.embedded.users.alice=<128 hex digits>
quarkus.security.users.embedded.roles.alice=isms-editors,isms-approvers
----

The operator mounts the file and restarts the application; the application hands its entries to Quarkus through the
same config source that already derives Token Sheriff's settings from `audit-notary.yaml`
(xref:../specification/authentication.adoc#AUN-AUTH-6[AUN-AUTH-6]). The application says what it runs on: a `WARN`
record at every start, and a notice on the login page and in the shell of the web app. It does not try to make the
file secure: an unsalted digest, no throttling, no lockout, no password rules, no second factor.

What stays as in production, and what does not:

* *Identity.* The application is the issuer (`web.origin`), the username is the `sub`, `amr` is `pwd`. The person
  directory and the signed trailers work unchanged, and every commit shows that a local user made it.
* *Rights.* The roles of the users file map to rights through the same `rights` mapping.
* *Login.* Quarkus' form authentication, whose encrypted cookie holds the user; there is no server-side session, so
  local users run beside Token Sheriff's planned session layer, not on it. A logout removes the cookie in the browser,
  but the server cannot withdraw a copy before its idle timeout. Tests of the session itself need an identity provider.
* *Step-up.* Off by default; switched on, a release asks for the password again and sends it with the release
  (<<_step_up>>).
* *Agents.* The MCP server takes Quarkus' Basic authentication, and the local MCP gateway keeps username and password
  as it keeps a refresh token (xref:mcp-server.adoc[MCP Server],
  xref:local-mcp-gateway.adoc#_basic_connections[Local MCP Gateway, Basic Connections]).

=== What Quarkus Provides

The full comparison, checked against Quarkus 3.40.1, is in ADR-0005.

[cols="2,3"]
|===
|Quarkus |Use

|Properties-file realm (`quarkus-elytron-security-properties-file`), embedded variant
|Used: users and roles are runtime configuration, fed from the users file; passwords as Quarkus' default SHA-512
digest. Switched on in every build, empty with `oidc`

|Properties-file realm, file variant
|Not used: its file paths are fixed at build time and the boot stops without the files

|Form authentication (`quarkus.http.auth.form.*`)
|Used for the web login, with its redirects switched off so that the single-page app gets `200` and `401`
(https://quarkus.io/guides/security-authentication-mechanisms#form-auth[Quarkus, Form-based authentication])

|Basic mechanism
|Used for the MCP server, restricted to `/mcp` (xref:../specification/mcp-server.adoc#AUN-MCP-8[AUN-MCP-8])

|`quarkus-security-jpa`
|Not used: users as database entities, and Audit Notary has no database
|===

What the application adds is small: the config source for the users file, the warnings, the notice, the password
check of a step-up, and the logout endpoint.

== First Login

The person directory is a library interface (https://github.com/cuioss/git-document-repository/blob/main/doc/concepts/directory-and-catalogs.adoc[Directory and
Catalogs]); the application supplies the flow and the form. The first login below applies to the default directory
(`git`); with a directory for the organisation's own source the person already exists there, and there is no form.

The library flow (https://github.com/cuioss/git-document-repository/blob/main/doc/concepts/directory-and-catalogs.adoc#_first_login[Directory and Catalogs, First Login])
applies unchanged; the application adds three things:

* *A gate.* Until the entry is saved, no other view opens and every other request is refused
  (xref:../specification/directory.adoc#AUN-DIR-2[AUN-DIR-2]).
* *The information duty* under GDPR Art. 13 (https://eur-lex.europa.eu/eli/reg/2016/679/oj[Regulation (EU)
  2016/679]): the form shows the operator's text on what the directory is for, what it holds, how long it is kept, and
  the legal basis agreed with the data protection officer.
* *The yearly confirmation* ("Is your team still right?") through the same form
  (xref:../specification/directory.adoc#AUN-DIR-3[AUN-DIR-3]).

[#_rights]
== Rights

Who may read and write a repository through the application comes from the identity provider through Token Sheriff:
a configured mapping from groups to repositories and to the actions *read*, *edit*, *approve* and *administer
catalogs*. In the first iteration no right is derived from the roles of the directory; who may approve is a matter of
access, not of the catalog of roles. A later iteration may derive rights from roles; then the assignment of such a role
needs a confirmation or comes from the identity provider.

The application enforces the rights for every request, in the web app and in the MCP server alike. The Git server sees
only the technical user.

== The Git Credential

The application reaches every Git server as one technical user, with a credential per repository (an access token
of a bot account, used over HTTPS, the only network transport of the library).
The commit names the user's pseudonym as author and the bot as committer; the signed trailers carry
the identity. No user needs an account on the Git server, and nothing is pushed in a user's name.

The application merges releases itself, so the signed release commit names the releasing user; protecting `main` on
the Git server is an operating duty (xref:deployment.adoc#_operating_duties[Deployment, Operating Duties]).

[#_step_up]
== Step-Up

Step-up is a setting (`step-up.enabled`): not every organisation wants a confirmation per release. It is on by default
with the identity provider and off by default with local users. When it is off, no transition requires step-up and the
trailers record the authentication of the session. With local users it is a renewed password check of the same user,
recorded as `amr=pwd` with a fresh `auth_time`, not a second factor
(xref:../specification/authentication.adoc#AUN-AUTH-4[AUN-AUTH-4],
xref:../specification/authentication.adoc#AUN-AUTH-6[AUN-AUTH-6]). The rest of this section is the identity provider's
case.

Every commit is signed by the application with the identity trailers. Where more is needed, the workflow of the
category decides per transition. The shipped categories keep the library default: *every release requires step-up,
and nothing else does*. Another rule is a change of the category's `workflow.yaml`, not of code. Before a transition
that requires step-up the server checks `acr` or `amr` and `auth_time` of the session against one global setting. If
they do not meet it, the server re-drives authorization with `acr_values` and `max_age`
(https://www.rfc-editor.org/rfc/rfc9470[RFC 9470], provided by Token Sheriff's client) and verifies the result before
it writes the transition; the trailers record the fresh authentication. For the user that is one MFA confirmation per
such transition; under the shipped workflows saves need none, and the first-login entry and changes of the own entry
never do.

An AI agent can never release; it hands the release to the human (xref:mcp-server.adoc[MCP Server]). A document that
needs a qualified electronic signature is signed outside the application.

[#_token_sheriffs_session_layer]
== Token Sheriff's Session Layer

The login, the session, its end, the CSRF check, the session view and the step-up are designed against Token
Sheriff's planned session layer, as if its epic `client-framework-aspects` were implemented
(xref:../adr/0004-Login_and_session_are_designed_against_Token_Sheriffs_planned_session_layer.adoc[ADR-0004]). The
state below is Token Sheriff's answer of 2026-11-23, checked against its source: 0.9.10 is released and pinned
(`version.token-sheriff` in the root `pom.xml`), `main` is 0.9.11-SNAPSHOT. The requirement identifiers of the planned
parts and the module names may still be renamed in Token Sheriff's ADR-0032.

=== Taken Over From 0.9.10

The first three rows are done; the last waits for a release.

|`security/TokenClientNativeRegistration` (removed)

converters and their types (CLIENT-26), which the native integration tests have proven; `NativeRegistrationTest`
checks that file, and its JGit part stays

|The provider metadata in `LoginService`, read once and never refreshed
|`CachingDiscoveryResolver` (CLIENT-29), enabled through `sheriff.client.discovery-cache.*` in

|===

=== Planned, Not Yet Released

Nothing here can be built against 0.9.10; each item needs the Token Sheriff release that contains it. All of it is
additive and opt-in.

[cols="1,4"]
|===
|Part |What Audit Notary gets

|`token-sheriff-client`
|CLIENT-31, a bounded pending-authorization store (total and per-source bounds, single use, released after a failed
PAR); CLIENT-32, the published refresh-disposition table; CLIENT-33, the logout step (best-effort revocation, the
end-session address); CLIENT-34, the step-up result bound to the session's `iss` and `sub`, compared in constant time
(AUN-AUTH-4); CLIENT-35, the back-channel logout handler that selects the sessions by `sid`, or all sessions of a `sub`;
CLIENT-36, the `resource` parameter of RFC 8707 on authorization, PAR, code, refresh and client-credentials requests;
the ID-token groups accessor (AUN-AUTH-2)

|`token-sheriff-session`
|SESSION-1 to SESSION-3, the record, the bounded store, the deadlines (replaces `SessionStore`, `SessionJanitor`,
`UserSession`, `LoginIdentity`); SESSION-4 to SESSION-7, the end at a new login, refresh, logout and back-channel
termination, the session-ended event; SESSION-8, step-up into the same session with an opaque pending action;
SESSION-9, the `SessionBinding` seam; SESSION-10, the session view

|`token-sheriff-bff-quarkus`
|BFF-1 the endpoints, BFF-2 the cookies, BFF-3 the flow defaults, BFF-4 CSRF, BFF-5 `SecurityIdentity`, BFF-6 the hooks
`ReturnAddressPolicy`, `SessionAugmentor`, `StepUpRequirement` and `SessionViewContributor`, BFF-7 the limits and
answers, BFF-8 the configuration (`sheriff.bff.*`), BFF-9 the session-info endpoint over SESSION-10 (replaces
`web/AuthResource`, `web/Cookies`, `security/LoginFlowProducer`, most of `LoginService`, and the generic parts of
`web/RequestGate`, `security/ReturnAddresses` and `web/SessionResource`)
|===

The session view (SESSION-10) is one implementation shared with API Sheriff's gateway: a claim allow-list and a default
view, the claims in their JSON types with `expires_at`, `auth_time` and `acr`, `401` as problem JSON without a session
and never a redirect, `403` for a claim outside the allow-list, `Cache-Control: no-store` on every answer, and a poll
that never renews the session. Audit Notary adds the rights, the pseudonym and the first-login flag through its
`SessionViewContributor`.

The order is the engine seams first (PLAN-02, then PLAN-03, PLAN-04, PLAN-11), the session module next (PLAN-05 to
PLAN-07), the extension last (PLAN-08 to PLAN-10).

=== Token Sheriff's ADR-0032

Decided: the session view is one shared aspect whose domain content comes through a hook; both modules live in the
Token Sheriff repository and share its version.

Open:

* whether the two modules are built at all, or the Quarkus OIDC extension in web-app mode is used instead. If only
  the extension is rejected, PLAN-08 to PLAN-10 drop out and the engine seams and the session module stand; if both
  modules are rejected, PLAN-05 to PLAN-07 drop out as well and only the engine seams stand;
* whether the access token is revoked at logout too (Audit Notary: yes);
* the pending-login lifetime (5 or 10 minutes) and the session defaults;
* whether the session cookie defaults to `SameSite=Lax` or `Strict` (Audit Notary: `Strict`, AUN-AUTH-1);
* the CSRF model: `Origin` or `Sec-Fetch-Site`, and an optional or mandatory token (Audit Notary: mandatory,
  AUN-WEB-8);
* whether DPoP and `private_key_jwt` are defaults;
* the names and the requirement prefixes.

== Open Questions

. Clarify with Token Sheriff which claims (`sub`, `acr`, `amr`, `auth_time`) reach the application, and whether the
  identity provider puts the groups into refreshed ID tokens, from which SESSION-5 takes them.
. Whether the problem JSON of SESSION-10 carries the `outcome` and `login` members every refused `/api/v1` request
  answers (xref:../specification/web-app.adoc#AUN-WEB-9[AUN-WEB-9]).
. Whether groups arrive by token claim or by SCIM.
. Deferred: the `Session` trailer, an HMAC of the session id `sid` that would correlate a commit with the login logs.
. The step-up switch: `step-up.enabled: false` needs a library setting that turns the step-up check of GDR-FORMS-7 off for
  every transition; today the library decides per transition from the workflow. Requested in the library's
  orchestrator inbox (`libraries-initial-implementation`, `audit-notary-001`), together with allowing `pwd` in
  `step-up.amr`.
. Local users on Token Sheriff's session layer: possible only if the layer offers a public way to create a session from
  a non-OIDC identity without tokens; its planned record (SESSION-1) and entry point (BFF-1) are OIDC-only. Until then
  local users run on Quarkus' form authentication.
