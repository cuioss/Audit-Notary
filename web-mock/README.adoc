= Audit Notary Web Mock
:toc: left
:toclevels: 2
:source-highlighter: highlight.js

A mock server of the `/api/v1` requests of the Audit Notary web app, driven by scenario files. The web unit tests, the
end-to-end suite (`web-e2e`) and manual work on views run against it instead of the application, the identity provider
and a Git server. Specification: `doc/specification/testing.adoc`, AUN-TEST-1; decision:
`doc/adr/0003-UI_tests_run_against_a_scenario_mock_server.adoc`. Development and tests only; never deployed.

Plain Java 25: the JDK HTTP server on `127.0.0.1`, one virtual thread per request, Jackson. The message catalogue
and the canonical addresses come from the `audit-notary-web-app` JAR (`META-INF/audit-notary/`).

== Start and Stop

[source,bash]
----
web-mock/start.sh -s workshop            # background; PID and log in web-mock/target/
web-mock/start.sh -s first-login -p 7421 -t ordered
web-mock/start.sh -f                     # foreground
web-mock/stop.sh
----

`start.sh` compiles when a source is newer than the last build; the build of `web-app` then contributes its resources
only (no Node build). On start the mock logs one line, which `start.sh` waits for:

----
WEB_MOCK-1: Web mock listening on http://127.0.0.1:7420 with scenario workshop#ready, timing REALISTIC
----

[cols="1,1,3"]
|===
|Option |Default |Meaning

|`-s`, `--scenario`
|`workshop`
|A profile name, `name#state`, or the path of a scenario file (optionally with `#state`)

|`-p`, `--port`
|`$AUDIT_NOTARY_MOCK_PORT` or `7420`
|Port on `127.0.0.1`; `0` takes any free port

|`-t`, `--timing`
|`realistic`
|`realistic` waits for the delays of events and timed transitions; `ordered` plays them at once, in file order

|`-h`, `--help`
|
|Prints the usage
|===

Without the scripts: `java -cp … de.cuioss.notary.audit.mock.cli.WebMockCli --scenario workshop`, or
`./mvnw -pl web-mock exec:java -Dexec.args="--scenario workshop"`. From a JUnit test:
`try (var mock = WebMock.start("workshop", 0, Timing.ORDERED)) { … }`.

== Profiles

[cols="1,1,3"]
|===
|Profile |States |Represents

|`workshop` (default)
|`ready`, `saved-by-other`, `conflict`, `forbidden`, `session-replaced`, `session-ended`
|An assessor in a populated installation: Due list with every kind, catalogs, and the SAMM lens — four scopes, the
open workshop *Payments 2026 Q4* (draft, eleven practices answered) and released assessments to compare with; a draft
and a save for everyone succeed. `saved-by-other` pushes a `document-saved` event and serves the assessment with
another assessor's two answers in *Strategy and Metrics*; `conflict` answers a save with `CONFLICT` and both values;
`forbidden` refuses the Due list; `session-replaced` closes the open event streams and gives every session a new
anti-CSRF token (another login in the same browser replaced the session); `session-ended` closes the streams and drops
every session, so the next request answers `UNAUTHENTICATED` (a back-channel logout; an addition to the profile list of
the plan, because UC-ACC-6 needs it)

|`first-login`
|`form`, `invalid-team`, `registered`
|A user without directory entry: everything outside the first-login allow-list answers `FIRST_LOGIN_REQUIRED`;
`PUT /api/v1/directory/me` saves the entry (`registered`) or is refused with `REFERENCE_NOT_FOUND`
(`invalid-team`)

|`read-only`
|`ready`
|The right `read` only, with the SAMM data of `workshop`; an edit answers `FORBIDDEN`

|`degraded`
|`unreachable`, `recovered`
|The fetch of `samm-assessments` fails: status `degraded`, a save answers `GIT_UNAVAILABLE` (a draft is still kept);
`recovered` pushes the `status` event with the healthy status

|`empty`
|`ready`
|A fresh installation: nothing due

|`no-rights`
|`ready`
|A logged-in user whom no group maps to a right (`"rights": []`): the shell works (status, messages, session, Due
list, events, logout, directory, catalogs) and every other request on a repository answers `403 FORBIDDEN`; the Due
list is empty
|===

`src/main/resources/scenarios/primary.txt` lists the primary profiles; a test module can add its own under
`src/test/resources/scenarios/<name>.json`.

One more profile is not primary, because it serves one flow rather than a kind of installation:

[cols="1,1,3"]
|===
|Profile |States |Represents

|`release`
|`review`, `stepped-up`, `password`, `wrong-password`, `changed`, `too-many-logins`, `released`
|An approver (right `approve`) releases *Payments 2026 Q4*, which is in review with every practice answered
(AUN-WEB-6). `review`: the release answers `STEP_UP_REQUIRED` with a step-up address and moves to `stepped-up`, where
it answers `RELEASED`; `password`: the status names the step-up by password (local users) and the release, sent with
the password, answers `RELEASED`; `wrong-password` answers `401 INVALID_CREDENTIALS`; both name `loginProvider: local` in the status, while the login
stays the one of the identity provider; `changed` answers `CHANGED_SINCE_REVIEW`; `too-many-logins` answers the release
`503 TOO_MANY_LOGINS` with `Retry-After: 60`, writes nothing and keeps the state (`POST /mock/goto/review` leaves it);
`released` serves the frozen assessment with its tag `assessments/payments-2026-q4/v1`

|`local`
|`ready`
|The login provider is `local`: `GET /api/v1/auth/login` answers `302` to the web app's page `/login?return=<address>`
and `POST /j_security_check` with the user `alex` and the password `local-password` signs in (`Origin` required); the
status names `loginProvider: local` and `stepUp: off`. The data and the user are those of `workshop`

|`login-trouble`
|`idp-unavailable` (start), `too-many-logins`, `unknown-transaction`, `recovered`
|The login cannot start or complete. `idp-unavailable` answers the login start `502 IDENTITY_PROVIDER_UNAVAILABLE`,
`too-many-logins` answers it `503 TOO_MANY_LOGINS` with `Retry-After: 60`, `unknown-transaction` lets the start
navigate to the callback, which answers `400 UNKNOWN_TRANSACTION`; a browser navigation (`Accept` contains
`text/html`) is sent to `/login-problem?reason=<reason>` instead. In `recovered` the built-in login signs in
|===

== What the Mock Emulates

* *Login provider:* the scenario's `login` names `oidc` (default) or `local`. With `oidc`,
  `GET /api/v1/auth/login?return=<address>` signs in as the scenario's user without an identity provider: it sets the
  cookie `audit-notary-mock-session` (`HttpOnly`, `SameSite=Strict`, `Path=/`; not `Secure`, the mock runs
  on plain HTTP) and answers a page that navigates to the checked `return` by `<meta http-equiv="refresh">`, no
  script. A `return` that is not a canonical address becomes `/` (the pages outside the shell, such as `/login`, are no
  valid `return`). Every other `/api/v1` request without session answers `401 UNAUTHENTICATED` with `login`:
  `/api/v1/auth/login` with `oidc`, `/login` with `local`. With `local` the login start creates no session: it answers
  `302` to `/login?return=<checked address>`, and `POST /j_security_check` (form body `j_username`, `j_password`; `404`
  with `oidc`) answers `200` with an empty body and the cookie for a user of `login.users`, `401` with an empty body for
  anyone else, and `403 CSRF_REJECTED` when `Origin` is missing or foreign. No anti-CSRF header is needed there. The
  password is never recorded in `/mock/acts`: the field `j_password` is redacted like `password`.
* *Refused logins:* a route of a scenario or state for `GET /api/v1/auth/login` or `GET /api/v1/auth/callback` is the
  answer of that request (it replaces the built-in login; with a callback route the built-in login does not sign in
  but navigates to the callback). For a browser navigation (`Accept` contains `text/html`) the outcomes
  `IDENTITY_PROVIDER_UNAVAILABLE`, `TOO_MANY_LOGINS` and `UNKNOWN_TRANSACTION` are answered as `303` to
  `/login-problem?reason=idp-unavailable|too-many-logins|unknown-transaction` without body; every other client gets the
  JSON. A `503` with the outcome `TOO_MANY_LOGINS` carries `Retry-After: 60`, whichever request it answers.
* *No rights:* with `"rights": []` and no first login, every `/api/v1` request outside the shell answers
  `403 FORBIDDEN` before the routes are looked at.
* *Session changes:* a state with `"session_replaced": true` closes every open event stream on entry and replaces the
  anti-CSRF token of every session (the cookie stays valid; a request with the old token answers `403 CSRF_REJECTED`);
  a state with `"session_ended": true` closes the streams and drops every session.
* *Anti-CSRF and Origin:* every state-changing request must carry `X-CSRF-Token` with the token of
  `GET /api/v1/session`; an `Origin` header must be the own origin, which is `X-Forwarded-Proto://X-Forwarded-Host`
  behind the Vite proxy (`xfwd: true`), otherwise `http://<Host>`. Otherwise `403 CSRF_REJECTED`.
* *First login:* while `first_login_required` holds, every request outside the allow-list of AUN-DIR-2 answers
  `403 FIRST_LOGIN_REQUIRED`.
* *Built in:* `GET /api/v1/session`, `POST /api/v1/auth/logout` (answers `{"redirect": "/signed-out"}`, the
  page of the web app, and clears the cookie), `GET /api/v1/messages?lang=en|de` (`400` for another language) and
  `GET /api/v1/events`.
* *Event stream:* `text/event-stream`, frames `id:`, `event:`, `data:`; a `: keepalive` comment every 15 s. Events
  come from entered states and `POST /mock/broadcast`; switching, resetting or jumping first announces the new
  `status`.

== Control Routes

No login; the Vite dev server forwards `/mock` for loopback clients only.

[cols="1,3"]
|===
|Request |Effect

|`GET /mock/state`
|`{"scenario", "state", "description", "first_login_required", "timing", "links": [{name, method, path, next}]}`

|`GET /mock/scenarios`
|`{"primary": [...]}`

|`POST /mock/scenario`
|Body `{"scenario": "name[#state]"}` (or `?name=`): switches the profile; keeps the sessions, clears the acts

|`POST /mock/goto/{state}`
|Moves to a state of the active profile and plays its events

|`POST /mock/reset`
|Back to the start state; clears the acts; keeps the sessions

|`POST /mock/broadcast`
|Body `{"event", "data"}`: pushes one event to every open stream

|`GET /mock/acts`, `DELETE /mock/acts`
|The recorded state-changing `/api/v1` requests `{method, path, state, body}`; clears them

|`POST /mock/sessions/clear`
|Drops every session
|===

== Scenario Format

[source,json]
----
{
  "format_version": 1,
  "name": "workshop",
  "description": "…",
  "login": { "provider": "local", "users": [ { "username": "alex", "password": "local-password" } ] },
  "user": { "pseudonym": "p-4c1a9e", "name": "Alex Example", "groups": ["samm-assessors"] },
  "rights": [ { "repository": "samm-assessments", "actions": ["read", "edit"] } ],
  "first_login_required": false,
  "start": "ready",
  "routes": { "GET /api/v1/status": { "status": 200, "body": { } } },
  "states": {
    "ready": {
      "description": "…",
      "first_login_required": false,
      "session_replaced": false,
      "session_ended": false,
      "routes": { "GET /api/v1/due": { "status": 200, "body": { } } },
      "links": { "save-entry": { "method": "PUT", "path": "/api/v1/directory/me", "next": "registered",
                                  "status": 200, "body": { } } },
      "events": [ { "after_ms": 0, "event": "document-saved", "data": { } } ],
      "auto": { "after_ms": 1500, "next": "other" }
    }
  }
}
----

* A request is answered by the first of: a link of the current state with the same method and path (moves to `next`
  and plays that state's events and timed transition), a route of the state, a route of the scenario; otherwise
  `404 MOCK_NO_ROUTE`.
* `login` is optional; the default is `{"provider": "oidc"}`. `users` belongs to `local` only, each user has a
  non-empty `username` and `password`. `session_replaced` and `session_ended` are optional booleans of a state (default
  `false`).
* Route keys are `"METHOD /path"` without query; `status` defaults to `200`, `body` to `{}`, `after_ms` to `0`.
* A route or a link answers either its `body` or the JSON of the data file its `body_file` names, below
  `src/main/resources/scenarios/data/` (`"body_file": "samm-scopes.json"`). Large or shared answers live there once
  instead of inline in every profile. The file name matches `[a-z0-9][a-z0-9.-]*.json`; a name that resolves to no
  file, a file that is no JSON, or `body` and `body_file` together fail the load.

=== Data Files

[cols="1,3"]
|===
|File |Content

|`samm-model-v2.2.0.json`
|The OWASP SAMM core model v2.2.0 (business functions, practices, streams, questions, answer sets), converted from
the YAML of https://github.com/owaspsamm/core/tree/v2.2.0/model[`owaspsamm/core`] with unchanged texts. Licensed
under CC BY-SA 4.0, not under the licence of this repository: see `samm-model-v2.2.0.NOTICE.txt` beside it

|`samm-scopes.json`, `samm-scope-<scope>.json`
|The scopes, their targets and assessments (`-in-review`, `-released` for the `release` profile)

|`samm-assessment-<document>.json`
|The assessments with their answers, parts and signed history; `payments-2026-q4` also as `-saved-by-other`,
`-in-review` and `-released`

|`samm-compare-payments*.json`, `samm-diff-payments-2026-q4.json`
|The comparison with *Payments 2026 Q2* and the diff of the release
|===

The answers are generated once from the model and are consistent with each other: the comparison holds the scores the
answers give (`web-app` checks this in `scores.test.ts`).
* Checked on load: format version `1`; the login provider `oidc` or `local`, users with `local` only; name, user name and start present; every `next` names a state; methods `GET`,
  `POST`, `PUT`, `DELETE`; paths below `/api/v1/` without query; status 100 to 599; actions `read`, `edit`,
  `approve`, `administer-catalogs`; no negative delay. A violation names file, location and rule.

== Use by the Web App and the End-to-End Suite

* *Vite dev server:* proxies `/api` and `/mock` to `http://127.0.0.1:$AUDIT_NOTARY_MOCK_PORT` with `changeOrigin` and
  `xfwd`; `/mock` only for loopback clients.
* *Web unit tests:* read the scenario files directly as fixtures.
* *End-to-end suite:* starts the mock in its global setup on a fixed port with `--timing ordered`, switches profiles
  with `POST /mock/scenario` and asserts the sent requests with `GET /mock/acts`.
